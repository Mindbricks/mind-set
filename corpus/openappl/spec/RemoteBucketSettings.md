# RemoteBucketSettings

**Level:** `section` · **Family:** [RemoteBucket](../ontology/families.md#remotebucket) (domain `Service`)

**Ontology:** [RemoteBucketSettings in Part 1](../ontology/RemoteBucketSettings.md)

Extension settings of a RemoteBucket's auto-generated {name}RemoteFile metadata data object. The twin keeps its framework-owned base columns; this section adds designer-declared columns to it.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `additionalColumns` | [`DataProperty`](./DataProperty.md)[] | no |  |  |  | Extra columns of the {name}RemoteFile twin: full DataProperty declarations (type, enum options, default, relation, index settings), validated like the properties of an authored data object and appended after the base columns (fileName, mimeType, fileSize, storageKey, accessKey, uploaderUserId, scanStatus, scanResult, scannedAt), the owner foreign key and the tenant column. A name may not repeat one of those columns or a framework system column, case-insensitively (REMOTE_BUCKET_COLUMN_NAME_RESERVED). The upload route writes the base columns plus the columns flagged uploadSettings.fromUploadField (from the multipart field of the same name, when sent), so a required column must declare a defaultValue or defaultFn (REMOTE_BUCKET_COLUMN_REQUIRED_WITHOUT_DEFAULT); the other extra columns are written through createCrudActions / updateCrudActions and BusinessApis on the twin. A relation column may not point at a virtual data object. Adding a column to an already deployed twin goes through the boot-time schema sync, which adds it to the existing table and fills existing rows with its default (NULL for an optional column without one). Generated by the nodejs, java, dotnet, rust and python lanes; golang persists no twin, so the columns have no effect there. |
| `compositeIndexSettings` | [`CompositeIndex`](./CompositeIndex.md)[] | no |  |  |  | Composite indexes on the {name}RemoteFile twin, for RemoteBucket and NativeBucket. Each entry uses the normal CompositeIndex contract: indexName, ordered indexFields, onDuplicate and optional partialWhere. Field references must resolve to a base column, the configured owner foreign key, the tenant column or an additionalColumn. Use onDuplicate exactly as on a DataObject to select duplicate handling and uniqueness; there is no isUnique flag. For example, an index named ticketStatus with indexFields [ticketId, status] and onDuplicate doInsert is a lookup index. The same property validation and partial-index restrictions as an authored data object apply. The nodejs, java, dotnet and python generators share the twin injector. Rust has a separate twin injector that must mirror these indexes; golang persists no twin. |

## Constraints

Property rules:

- The items of `additionalColumns` must have distinct names (`basicSettings.name`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)
- The items of `compositeIndexSettings` must have distinct names (`indexName`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)

# ObjectBasicSettings

**Level:** `section` · **Family:** [ObjectSettings](../ontology/families.md#objectsettings) (domain `DataObject`)

**Ontology:** [ObjectBasicSettings in Part 1](../ontology/ObjectBasicSettings.md)

Basic configuration for a data object, including its identity, documentation, and deletion strategy. A data object acts as a logical model for a database table or MongoDB collection, and is central to defining how data is stored, queried, and managed within a microservice.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `name` | `String` | yes |  |  | format [codeName](./value-formats.md#codename) | A unique identifier for the data object used consistently across generated code, API routes, and documentation. The name must be a single, camelCase word without spaces or special characters, and should be unique within the project. Use a singular noun that clearly represents the entity (e.g., 'product', 'order', 'task'). |
| `description` | `Text` | no |  |  |  | A descriptive explanation of what the data object represents. This description is used in documentation and helps clarify the business domain the object serves. |
| `frontendDocument` | `Text` | no |  |  |  | A text based information to inform the frontend developer or frontend AI agent about the data object specific UX behaviour of the data object logic based on user stories and use cases. The format may be either text or markdown(recommended). Write the document as an AI prompt and describe data object specific UX behaviours. Note that this document will be given to the AI agent or human developer combined with all technical details that is generated from the data object design,so this document should only focus on data object-specific behavioral UX business logic. |
| `useSoftDelete` | `Boolean` | no | `true` |  |  | Overrides the default data model setting to enable or disable soft deletion for this object. If enabled, records will not be physically deleted but marked inactive using an 'isActive' flag. These records will be excluded from normal queries unless explicitly requested. |
| `virtual` | `Boolean` | no | `false` |  |  | Declares a response-only (virtual) data object. Its properties describe a RESPONSE SHAPE only: no table or collection, no migration, no model, no db-layer module, no index, no seed and no Elasticsearch mapping is generated for it, and no tenant id column is injected. The object still yields its typed response record, so a BusinessApi bound to it keeps a typed response in the api layer, swagger and api docs. Such an api may only be a `get` or a `list` (create/update/delete is an ERROR); its main operation reads no database: `this.result` starts as an empty object (get, no id route parameter - so author its restSettings.routePath beside a default-routed list, or both take the bare resource path: ROUTE_COLLISION) or an empty array (list), and the api's own actions produce the response - AddToResponse / functionCall entries on a get, a ListMapAction with `replacesResult: true` in `afterMainListOperation` on a list. A relation, a crud or fetch action, a view, a seed or any other storage reference that points at a virtual object is an ERROR, and so is a storage-backed feature section (checkout, subscription, marketplace, invoicing, fiscalization, ledger, membership, graph or enterprise projection, geo, object moderation) activated on it. `useSoftDelete` and the access settings are ignored; indexes and entity cache settings are ignored with a WARNING. Leave false (the default) for every object that stores rows. |
| `publishDbEvents` | `Boolean` | no | `true` |  |  | Whether a write to this object publishes its row-level Kafka events: the db events `<serviceCodename>-dbevent-<object>-{created\|updated\|deleted}` and the elastic-index events `elastic-index-<codename>_<object>-{created\|updated\|deleted}`. `true` (the default) publishes both on every create, update and delete, bulk and by-query writes included. `false` turns both families off for an object nothing in the project consumes, such as an internal log or bookkeeping table: the Elasticsearch index of the object is STILL written (search, dynamic DataViews and cross-service reads keep working), only the Kafka copies stop, and their topics are no longer pre-created at boot. Route events of the object's apis follow each api's own `raiseApiEvent` and are not affected. Validation REFUSES `false` (ERROR DB_EVENTS_SWITCH_CONSUMED, naming the consumer) on an object that a stored DataView (main object, aggregate or stat source), an eventSubscription, a kafka-triggered business api, an edge controller kafka trigger, an agent kafka controller, a realtime hub (an `autoBridgeDataEvents` hub of its service, a hub kafkaEvent, or a hub `roomSettings.authSources` entry naming the object in any service, whose membership eviction is always on), an agent harness kafka trigger, a business api SSE `kafkaProgressListeners` topic, an event notification, an external feed or a content model consumes, because those consumers read exactly these events. A consumer that exists only at runtime (for example a dynamic agent's kafka controller stored by the agentHub) is not seen by validation. Framework system objects that nobody consumes (the agent run records, the tool catalog, the notification logs, the cron run log) ship with `false`; when a project does consume one of them, it keeps publishing and validation says so (DB_EVENTS_SWITCH_SYSTEM_OBJECT_CONSUMED). This is a separate setting from the retired api-level `raiseDbLevelEvents`, which still has no effect. |

## Constraints

Property rules:

- `name` must be present. (`REQUIRED_FIELD_MISSING`)
- `name` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)

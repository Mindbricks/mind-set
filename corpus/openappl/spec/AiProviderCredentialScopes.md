# AiProviderCredentialScopes

**Level:** `subsection` · **Family:** [ProjectSettings](../ontology/families.md#projectsettings) (domain `Project`)

**Ontology:** [AiProviderCredentialScopes in Part 1](../ontology/AiProviderCredentialScopes.md)

Which credential levels below the application owner (saas) may supply the key for one AI provider entry, and who pays for calls made with those keys. Every scope is `off` by default, which keeps the entry exactly as it was. `optional` lets the tenant or user save a key that is used when present, with fallback to the next level. `required` means the level must have a key: a call without one fails with HTTP 428 and the code `AI_PROVIDER_CREDENTIAL_REQUIRED` (the problem body's `errorCode`, the mcpbff chat's `code`; the message names the provider and the scope) and the saas key is never used, so a frontend can ask the user to add their key. When a lower scope is `required` the saas key in `configuration` becomes optional and a BYOK-only project needs none. Validation: `tenant` must stay `off` in a single-tenant project (the chain there is saas then user); a scope cannot be enabled on a brand that does not support scoped keys; and on a brand without a cheap live check (fal, custom) a warning says saved keys will be stored as `unverified`. Covered callers on nodejs services: AI agents and each of their fallback providers, agentHub agents, AiCallAction, the mcpbff chat and AI completion, and the AgentHarness model gateway. Dotnet and java services cover AI agents (the primary and each fallback provider) and AiCallAction at the tenant and user levels, and golang services resolve the tenant and user levels; none of these three reads the resource level. Python and rust services cover AI agents (the primary and each fallback provider) and AiCallAction at the user, resource and tenant levels. Video-layer and content-layer AI calls always use the saas key. Kafka and cron runs have no user, so they resolve tenant then saas. Stored keys are sealed under the deploy secret `PROVIDER_CREDENTIAL_KEY`, which auth, the AI-calling services and the mcpbff must receive in every slot. The `resource` block adds a fourth level between the user and the tenant: a key owned by one row of a membership-bearing data object (a workspace), managed by the row's creator and the member roles named in `managers`, and used by the members named in `users`. The full order is user, then resource, then tenant, then saas; set `user` to `off` when the workspace key must win over a personal one. Like the other levels it is `off` by default, and an entry without it is unchanged.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `tenant` | `ProviderCredentialScopeMode` | no | `"off"` | `off`, `optional`, `required` |  | Tenant level: `off` (default), `optional` or `required`. A tenant owner or tenant admin saves the tenant's key with `PUT /tenant-provider-credentials/:providerName` on the auth service; saas admins and super admins may manage any tenant with `?tenantId=`, and each such action on another tenant is audited. Only valid in a multi-tenant project: anything other than `off` in a single-tenant project is a validation error. |
| `user` | `ProviderCredentialScopeMode` | no | `"off"` | `off`, `optional`, `required` |  | User level: `off` (default), `optional` or `required`. Each user saves their own key with `PUT /my-provider-credentials/:providerName` on the auth service and reads the status (has a key, last 4 characters, valid / invalid / unverified, last verified and last used times) with `GET /my-provider-credentials`. A user key wins over the tenant and saas keys. Calls with no user (Kafka or cron runs) skip this level, even when it is `required`. |
| `costPolicy` | `ProviderCredentialCostPolicy` | no | `"ownerPays"` | `ownerPays`, `saasPays` |  | Who pays for calls made on a tenant, resource or user key. `ownerPays` (default): usage on a user key is charged to that user's own budget only; usage on a tenant key is charged to the user and to the tenant's own-key budget, which no ceiling reads; usage on a resource key is charged to the user and to that row's own budget, which only the row's `resource.budget.dailyCostCeilingUsd` reads. None of them is charged to the tenant, agent or project (saas) budgets, and the daily cost ceiling does not apply to them; the per-user daily token budget still does. Usage is still recorded so each owner can see their own spend. `saasPays`: every call counts toward the saas budgets as it does today. |
| `resource` | [`AiProviderResourceCredentialScope`](./AiProviderResourceCredentialScope.md) | no |  |  |  | Optional. The resource level: a key owned by ONE ROW of a data object that carries a membership configuration (a workspace, a team, a company, a project), set by that row's creator or its admins and used by its members. Use it when users group themselves into several such rows without the project being multi-tenant, or inside one tenant, and each row must run on its own provider key; a user may belong to several rows, each with its own key. Leave it empty, or set `mode` to `off`, and nothing changes. The block names the data object, how the row id is read from the call (`idFrom`), and which member roles may set the key (`managers`) and use it (`users`); the row's creator always may do both. Before a resource key is ever used, the caller's membership in the named row is verified by the service that owns the data object, so a row id read from the call is never trusted on its own: a caller who is not a member gets the same answer as when the row has no key. The level adds no session field, no role and no permission of its own: a member is whoever the data object's membership configuration already says is one. Both single-tenant and multi-tenant projects take it. It cannot be combined with an AgentHarness that runs on the owner's subscription (`modelSettings.auth: userSubscription`). The owning service serves the routes that set, read and delete a row's key (managers set and delete it; plain members see only whether a key is stored and its status), and agents, `AiCallAction`, agentHub, AgentHarness `providerKey` sessions and the MCP-BFF chat resolve it at call time in the order user, resource, tenant, saas. Under `costPolicy: ownerPays` usage on a row's key is charged to the caller and to that row's own budget, never to the application owner's, and `budget.dailyCostCeilingUsd` caps the row's daily spend. |

## Constraints

Property rules:

- `tenant`, `user`, `costPolicy` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)

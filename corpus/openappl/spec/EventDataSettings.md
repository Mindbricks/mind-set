# EventDataSettings

**Level:** `section` · **Family:** [EventNotification](../ontology/families.md#eventnotification) (domain `NotificationService`)

**Ontology:** [EventDataSettings in Part 1](../ontology/EventDataSettings.md)

Defines how the event notification extracts and processes data from incoming Kafka messages. This includes the data source, paths to relevant information, and any additional data to include in the notification.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `channel` | `String` | yes |  |  |  | The Kafka topic name that will trigger this notification. The notification manager listens on this channel. |
| `condition` | [`MScript`](./MScript.md) | no |  |  | MScript kind `code` | An optional MScript condition to determine whether the notification should be triggered, based on the incoming Kafka message payload. To access data from both data source and the received Kafka event, use `this.dataSource`. The receiver carries exactly five members, `this.payload`, `this.dataSource`, `this.old`, `this.actor` and `this.metadata`, and it is NULL-NORMALIZED before the expression runs: a member the event does not carry is substituted with an empty object. A chain ROOTED at one of those five is additionally made null-safe at every link past the root (a read of `this.dataSource.owner.tier` on an event with no `owner` yields `undefined` instead of failing; the nodejs listener implements this by splicing optional-chaining into the compiled expression, other listeners by their own null-safe accessor), so a read through absent data reads `undefined` at ANY DEPTH and the expression is EVALUATED on that instead of throwing. Nothing is recorded when that happens: the condition simply answers, and a false answer skips the notification silently, with no NotificationDeliveryLog and no NotificationLog row. Evaluating instead of throwing can flip the answer EITHER WAY, so re-read any event-level condition that reads through `this.dataSource` on an event with no `dataViewName`: `this.dataSource.tier === 'gold'` and `this.dataSource.owner.tier === 'gold'` both fold to false and skip the notification, while a negated or absence-testing condition (`!this.dataSource.blocked`, `!this.dataSource.owner.tier`, `this.dataSource.tier === undefined`) evaluates TRUE and the notification FIRES, where the earlier throw used to suppress it. On the NODEJS listener, only a chain rooted OUTSIDE those five members still throws (`this.target.isPublic`, `this.data.x`). The two BARE bindings (no leading `this.`) differ in this EVENT-LEVEL slot: a bare `target` identifier is not bound at all here — the event-level condition is evaluated BEFORE any target is resolved, so there is no `target` binding here at all, and target-dependent logic belongs in the per-target `condition` slot instead; a bare `data` IS bound here, to `this.dataSource ?? this.payload` (the script root, the same one `includeData` values read). Only the rooted-chain throw case is recorded as a failed NotificationDeliveryLog + NotificationLog row naming the event. LANGUAGE NOTE: the throw-versus-fold boundary is a per-listener property, not a portable guarantee. The null-safe fold landed in the nodejs tree only. The dotnet, rust and golang listeners resolve member reads through a null-safe accessor REGARDLESS of the chain root, so they fold an out-of-contract read to false with no throw and no failed row; dotnet does print a ONE-SHOT runtime warning naming the undeclared member, which is the only trace the skip leaves there, and rust and golang leave none. The python listener is NOT in that group: it applies the same root-keyed boundary as nodejs, so an out-of-contract read RAISES and takes the durable failed-row path. The java listener does not reach a runtime at all - it lowers `this.<member>` to a literal field read against a condition context that declares a fixed set, so an out-of-contract member is a missing symbol and the generated service does not compile. Do not rely on the durable failure row as a portable suppression backstop: write the condition so that its TRUE branch is the one you want on every target language. Three authoring shapes keep throwing as well, because `?.` cannot legally be spliced into them, namely a chain inside a `new` callee or a tagged-template tag, a chain re-entered through parentheses (`(this.dataSource.a).b.c`), and a chain continued past a call (`this.payload.fn().x.y`). CAUTION: the fold keys on the chain ROOT, so a MISSPELLED member deeper in a declared chain (`this.dataSource.ownr.tier`) is indistinguishable from absent data. It reads `undefined`, the condition answers false, and the notification is never sent, with no runtime row and no design-time warning, because the receiver-unknown check (NOTIF_TARGET_CONDITION_RECEIVER_UNKNOWN) inspects chain ROOTS only. That check runs on BOTH condition slots - this one and the per-target one - at the ERROR tier, with the same code and the same reported shape, so a root outside the five members is refused here at design time and never reaches a runtime. A misspelled member DEEPER in a declared chain is a different case and is still not caught, because the root is legitimate. Measured before that tier was raised: the corpus carried 109 event-level condition slots, 54 of them live, and every one of the 54 roots at a declared member, so the refusal rejects nothing that exists. Where an out-of-contract root did already ship, the dotnet listener's one-shot runtime warning is what names it. Spell deep chains against the DataView's own shape. |
| `dataViewName` | `String` | no |  |  | format [codeName](./value-formats.md#codename) | The name of the data view to use when the data source is 'dataView'. |
| `dataViewIdPathInPayload` | `String` | no | `"id"` |  | format [dotPath](./value-formats.md#dotpath) | The dot-path of the id used to fetch the data view document, resolved against the event RECORD (the unified event envelope's `data` — the same root targetPathInData reads), never against the envelope itself. Defaults to 'id', the record's own id. |
| `includeData` | [`DataMapItem`](./DataMapItem.md)[] | no |  |  |  | An optional list of key-value mappings to merge additional values into the notification metadata: each entry writes `metadata[name] = value`, where `value` is an MScript evaluated per event against the same receiver as `condition` (`this.payload` is the event record, `this.dataSource` the fetched DataView document when `dataViewName` is set, plus `this.old`, `this.actor`, `this.metadata`; the bare root `data` is `this.dataSource ?? this.payload`). The metadata is the stored Notification row's `metadata` column and the template render scope; the NotificationLog row keeps the entry's value bounded (strings cut at 256 characters, objects reduced to a marker) next to references to the source event, and the NotificationDeliveryLog row carries no metadata, so an entry named `targetType` is read by the template as `<%= targetType %>`. ORDER: the entries are applied AFTER the DataView merge (so a value may read `this.dataSource.<field>`) and BEFORE the `actionDeepLink` / `actionText` slots. An entry whose value evaluates to `null` or `undefined` (or whose script throws; the throw is logged once) removes the key, including any value inherited from the event record. Non-null falsy values (`0`, the empty string and `false`) are preserved. RESERVED NAMES: `_old`, `_actor`, `actionDeepLink`, `actionText` and `dataSource` are framework-managed metadata keys and are rejected at validation (NOTIF_INCLUDE_DATA_RESERVED_KEY). LANGUAGE NOTE: all six active target languages - nodejs, python, rust, golang, java and dotnet - emit these entries through their notification listeners. |

## Constraints

Property rules:

- `channel` must be present. (`REQUIRED_FIELD_MISSING`)
- `dataViewName` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)
- `dataViewIdPathInPayload` must be in the [`dotPath`](./value-formats.md#dotpath) format. (`INVALID_DOT_PATH`)
- The items of `includeData` must have distinct names (`name`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)

Pattern rules:

| Code | Severity | Rule |
| --- | --- | --- |
| `DATAVIEW_NOT_FOUND` | error | DataView "…" not found in BFF service. |
| `NOTIF_INCLUDE_DATA_DUPLICATE_NAME` | error | includeData entry […] names "…", which is the same metadata key as "…" at includeData[…] once the surrounding whitespace is trimmed and the name is case-folded - the form the listener actually writes. |
| `NOTIF_INCLUDE_DATA_NOT_EMITTED` | warning | includeData declares … entr…, but the "…" notification listener does not emit includeData yet: the keys will be ABSENT from the stored Notification metadata and from the template render scope on this service. |
| `NOTIF_INCLUDE_DATA_RESERVED_KEY` | error | includeData entry "…" would overwrite a framework-managed notification metadata key. |

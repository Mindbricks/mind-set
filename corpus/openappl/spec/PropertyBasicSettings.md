# PropertyBasicSettings

**Level:** `section` · **Family:** [DataProperty](../ontology/families.md#dataproperty) (domain `DataObject`)

**Ontology:** [PropertyBasicSettings in Part 1](../ontology/PropertyBasicSettings.md)

Defines the core structure and behavior of a data property. Beyond basic typing, this section governs how the property participates in data integrity, mutability, API exposure, and logic-driven behaviors such as hashing or auto-increment. Use this section to establish the foundational logic and identity of the property within your data object.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |

| `name` | `String` | yes |  |  |  | Unique identifier for the property within the data object. This name is used throughout route definitions, generated code, and logic expressions. Use camelCase formatting, avoid spaces and special characters, and ensure the name is unique within the same data object. Do not name a property `session`: a create / update api binds every column it writes as `this.<name>`, where designer MScript reads `this.session` as the caller's session, so such an api is refused (PARAM_NAMED_SESSION). |
| `type` | `DataTypes` | yes |  | 16 values, see [DataTypes](#datatypes) |  | Defines the property's data type. Use a value from the `DataTypes`. The selected type impacts validation, storage schema, and frontend component inference. |
| `decimalScale` | `Integer` | no | `null` |  | min 0, max 6 | How many FRACTIONAL DIGITS a `Decimal` column carries - the scale in `Decimal(scale)`. Only meaningful when `basicSettings.type` is `Decimal`; leave it null (the key absent) on every other type, where setting it is a design-time ERROR (`DECIMAL_SCALE_ON_NON_DECIMAL`) rather than a number nothing reads. An omitted scale on a Decimal column resolves to 2, the money default. Legal range 0..6 inclusive (`VALUE_OUT_OF_RANGE`, a fractional one `INVALID_FIELD_TYPE`): 0 for a whole-unit currency (JPY, KRW), 2 for the ordinary case, 3-6 for a rate or a unit price quoted below the currency's smallest unit. The scale is a STATEMENT ABOUT THE COLUMN, not a display hint: the framework rounds every value written to the column to exactly this many digits, half-to-even (banker's rounding, so a long series of .5 cases does not drift upward the way half-up does), at each write boundary - every generated db-layer write helper (create, bulk create, update by id / id list / query, and the upsert of an `onDuplicate: doUpdate` index), which business APIs, create / bulk-create / update CRUD actions, seed data and custom code calling dbLayer all write through; plus a request-parameter transform and the amount handed to a payment or invoice provider. Rounding an already-rounded value changes nothing, so the boundaries agree. Two columns in the same money flow must declare the SAME scale, or a value rounded to 2 on one row and 4 on the next stops reconciling. |
| `maxLength` | `Integer` | no | `null` |  | min 1, max 10485760 | The maximum number of CHARACTERS a `String` column holds - the n of its `varchar(n)` column. Optional: leave it null (the key absent) and the column keeps the default of 255. Only meaningful when `basicSettings.type` is `String`; on any other type (Text, Enum, ID, ...) setting it is a design-time ERROR (`MAX_LENGTH_ON_NON_STRING`), and it must be a whole number from 1 to 10485760, the PostgreSQL varchar limit (`VALUE_OUT_OF_RANGE`, a fractional one `INVALID_FIELD_TYPE`). The nodejs codegen emits the column as `DataTypes.STRING(n)` - `DataTypes.STRING(255)` when absent, the same varchar(255) column as before - and checks the length BEFORE the write: a value longer than n characters is refused with `422 VALIDATION_ERROR` naming the field (never the value), on the api pipeline and on a hand-written route alike. Characters are counted the way PostgreSQL counts them (Unicode code points, so an emoji is one character), a list is checked per element, and trailing spaces PostgreSQL would trim are not counted. The check reads the STORED value, so a `hashed` column is checked on its 60-character bcrypt digest and a `maxLength` below 60 there is an ERROR (`MAX_LENGTH_BELOW_HASH_DIGEST`). The check also runs on the writes that skip the rest of the model validation: the plain values of a numeric-mutation update (`$inc` and friends) are checked before its single statement. A raw query in custom code bypasses the check and still reaches PostgreSQL, which answers the sanitized `400 BAD_REQUEST`. Raising n on an existing database is a varchar widening the boot reconcile applies on dev/preview; lowering it is a narrowing that is reported and never applied, so longer values already stored are kept. On a MongoDB-backed object only an explicit `maxLength` is enforced (there is no varchar column to default); the generated create, update and upsert writers all check it before the write, with the same 422. Services generated in rust and python enforce it the same way (a varchar(n) column, the same pre-write 422). Services generated in another language declare it but do not enforce it yet (WARNING `MAX_LENGTH_NOT_ENFORCED`). |
| `isArray` | `Boolean` | no | `false` |  |  | Indicates if the property stores multiple values (array). Supported by databases like PostgreSQL and MongoDB. Default is `false`. |
| `description` | `Text` | no |  |  |  | Optional textual description of the property's role in the domain. Useful for documentation and as a semantic hint across logic and UI components. |
| `isRequired` | `Boolean` | no | `false` |  |  | If `true`, the underlying DB column is NOT NULL — the persisted record must hold a non-null value. This is independent of where the value comes from at runtime; the framework will reject the write if no value reaches the column from any of: a `requestParameters` binding consumed by `dataClauseItems`, a `sessionSettings` auto-inject, a `staticJoin` resolution, or a `basicSettings.defaultValue` DB default. Default is `false` — an OMITTED `isRequired` means the column is NULLABLE, and `BusinessApi.validate` reads the same resolution, so a create API is never asked for a value the column does not demand. Say `true` explicitly when the column must be NOT NULL; validation reports `IS_REQUIRED_UNSPECIFIED` while the key is missing so the intent is written down rather than inherited from the default. |
| `allowUpdate` | `Boolean` | no | `true` | also `untilSet` |  | Controls whether the property can be modified after creation. THREE values:  - `true` (the default) — an update api may write the column as often as it likes. - `false` — the column is immutable after create. The update codegen filters it out of the write set entirely, so an update `dataClauseItems` entry naming it is a design-time ERROR (`DATA_CLAUSE_ITEM_NOT_EMITTED`) rather than a write that silently never happens. - `'untilSet'` — WRITE-ONCE. The update path EMITS the clause, guarded `WHERE <column> IS NULL`, so the first write after create wins ATOMICALLY at the database: no read-then-write race, no application-level check. A write aimed at a column that already holds a value answers the typed refusal `WRITE_ONCE_ALREADY_SET` (409) — never a silent no-op. The guard is on every db-layer update helper (by id, by id list, by query - the one every updateCrudAction uses): a bulk or query-scoped write matching a row that already holds the value is refused whole, and each loser of a concurrent first write gets the same 409. A create that lands on an EXISTING row (an `onDuplicate: doUpdate` upsert, a bulk create over an existing id) never overwrites a set write-once column: a replay carrying the SAME value is an idempotent no-op on it, a DIFFERENT value (null included) is refused with the same WRITE_ONCE_ALREADY_SET (409) before anything is written (a bulk create refuses the whole batch), and a column that is still null is filled. Use it for a value that is computable only after the row exists and must then never change again: a capture-time commission snapshot, a settlement reference, an issued document number. Accepted ONLY on a NULLABLE column (`isRequired: false`): the guard is `IS NULL`, so on a NOT NULL column it could never match and every update would be refused (validation reports `WRITE_ONCE_REQUIRES_NULLABLE`).  `'untilSet'` is the remedy the `DATA_CLAUSE_ITEM_NOT_EMITTED` message names for the write-once case; the alternative it replaces — flipping the column to `allowUpdate: true` so one hook can stamp it — leaves captured financial history permanently rewritable by every later update. |
| `autoIncrement` | `Boolean` | no | `false` |  |  | If `true`, this property will be auto-generated by incrementing the latest existing value. Suitable for numeric IDs or sequences managed internally. |
| `hashed` | `Boolean` | no | `false` |  |  | If `true`, the property is a CREDENTIAL that is one-way hashed before storage. Two things follow, both enforced by codegen: the db-layer bcrypts the value on every create/update (irreversible — the plaintext is unrecoverable, so only a hash-compare can verify it), and the property name is scrubbed from every outgoing response, event and streamed chunk by the api layer. Use it for passwords. Do NOT use it for a value something has to read back verbatim (a digest looked up by exact match, an external token replayed to a third party): bcrypt at write makes that lookup impossible — declare `isSecret` instead, which is the response half without the storage half. |
| `isSecret` | `Boolean` | no | `false` |  |  | If `true`, this property holds a secret value (e.g. an API-key digest, a QR code, a token) that is stored in CLEARTEXT — because something has to read it back verbatim — and must still never leave the service on a payload. The api layer scrubs the property name from every response, event and streamed chunk, exactly as it does for `hashed`, and the emitted OpenAPI response schema and gRPC response message omit it. The difference from `hashed` is the STORAGE half only: `hashed` bcrypts the column on write, `isSecret` leaves it untouched, so a column that is looked up by exact match (auth's `apiKey.keyHash`) can be declared secret without becoming un-lookupable. A value the caller legitimately receives (a freshly minted plaintext key) must be put on the response by the api itself, not read off the record. The ONE opening is per API: a BusinessApi may name this column in `apiOptions.exposeSecrets`, and then THAT api carries it in its own response (a ticket code its owner has to read back); every other api, every event payload and every log keeps the scrub. NOTE: the MCP `***` masking + `__proxyCode` frontend-rendering flow this field once described is NOT implemented in any lane; the realised meaning is the response/event exclusion above. Never name a secret property `accessToken` or `refreshToken` (this applies to `hashed` too): those are the exact keys every login, relogin, social-login and register auto-login answer carries the session token under, the scrub matches by name, so validation refuses the declaration (`SECRET_NAME_SESSION_TOKEN`) - rename it, for example to `providerAccessToken`. |
| `defaultName` | `Boolean` | no | `false` |  |  | If `true`, this property is used as the default display label for records of this data object. When rendering relation dropdowns or record references in the frontend, the value of this property will be shown as the human-readable label. Only one property per data object should be marked as defaultName. If none is set, the frontend will fall back to common field names like 'name', 'title', or the first String property. |
| `isFilterParameter` | `Boolean` | no | `false` |  |  | If `true`, the property is exposed as a declared filter parameter on the data object's auto-generated list APIs — on EVERY surface the API exposes (the REST query string or body, an MCP tool call, a gRPC message, a kafka event payload, a cron input, an internal API call), not the REST route alone. The filter name is the property name itself (no separate alias). Filter type/operator follows the property's `type` automatically. An EMPTY value (`?status=`) means no constraint, exactly like omitting the parameter.  The filter is only as good as the column behind it. In explicit mode a column is written ONLY from a create/update api's `requestParameters`, any api's `dataClauseItems`, the property's own `sessionSettings` / `staticJoin` / `defaultValue`, or a framework subsystem binding declared on the object (an invoicing `statusProperty`, say). A filter column in none of those is guaranteed NULL for every row the api creates, so the filter can only ever match rows written from outside the api - a seed, a migration, a direct index write. Validation reports that as the warning `FILTER_COLUMN_NEVER_WRITABLE`: either add the column to a write source, or drop `isFilterParameter`. The check stands down for an object the service declares no create api for at all, since such rows come from somewhere it cannot see. |
| `enumOptions` | `String`[] | no |  |  |  | Required when `type === 'Enum'`. Ordered list of string values the property can take. Must contain at least 2 options. Leave null/absent for non-enum properties. Enum options are DATA, not code identifiers: the value is stored verbatim in the column and compared verbatim in MScript, and every generator emits it as a string literal (a language identifier, where one is needed at all, is derived by prefixing it with the model + property name). Reserved words (`public`, `default`, `class`, …) are therefore legal option values and are never renamed — write the value you want stored, and use exactly that spelling in MScript. |
| `defaultValue` | `Any` | no |  |  |  | DB-level LITERAL default for the property's column. Applied at write time when no other source supplies a value (no requestParameter, no sessionSettings auto-inject, no staticJoin, no dataClauseItems entry). Type must match `basicSettings.type` and respect `isArray`, and the value is type-checked at validation. For a SCALAR column (numeric / String / Text / ID / Enum / Boolean) it must be a matching literal — an object, an array, or an MScript-wrapper object (`{ "js": … }`) is rejected with `INVALID_DEFAULT_VALUE` (a string that encodes a number/boolean, e.g. `"0"` on a Double, is coerced to the typed literal with a non-blocking `DEFAULT_VALUE_TYPE_COERCED` warning). For an `Object` column (JSONB / Mongoose Mixed) an object OR array literal is legal data — but an MScript-wrapper object is still rejected there, because it is code, not data. `defaultValue` must NEVER carry code: it is a DB-level literal, applied where MScript cannot run. For a DB-native computed default (current timestamp, …) use the sibling `defaultFn` field and leave `defaultValue` null (if both are set, the literal `defaultValue` wins and `defaultFn` is ignored with a non-blocking warning); for business/computed defaults like `LIB.<fn>()` leave both null and write a per-API `dataClauseItems` MScript entry instead. |
| `defaultFn` | `DefaultFunction` | no | `null` | `now` |  | A DB-native default FUNCTION for the column, selected from the `DefaultFunction` enum and mapped by each generator to the correct per-engine spelling (e.g. `now` → Sequelize `DataTypes.NOW` / Mongoose `Date.now` / SQL `CURRENT_TIMESTAMP`). Use this — not a magic-string `defaultValue` like `now()` — for computed DB defaults. Set it only when `defaultValue` is null: if both are set, the literal `defaultValue` wins and `defaultFn` is ignored (reported as a non-blocking warning). `now` is only valid on a `Date` property; on all other types leave this field null (most properties never set it). |
| `requirementCheck` | [`MScript`](./MScript.md) | no | `null` |  | MScript kind `code` | Conditional requiredness: an MScript boolean expression over the record as it will be stored. When it holds, an EMPTY value of this property (null, undefined, '' or an empty array []) is refused with 400 `PROPERTY_REQUIRED_BY_CONDITION` naming the property, on EVERY write path that stores the object: built-in and custom create and update APIs, CRUD actions, bulk creates, updates by id, by id list and by query, and seed data. `this` is the record as it will be stored, the stored row merged with the write (on create the values being inserted; on update the current row overlaid with the patch), so a later update that changes only the condition field (e.g. `roleId`) is refused while this property is still empty. An update is judged when it writes this property or a field the expression reads (an update of other fields cannot change the answer and is not judged), and an update by id is applied compare-and-set on the stored values the expression read (a lost race re-reads the row and judges it again; the bulk updates by id list and by query judge every matched row and pin nothing). There is no session, request or api context: the expression is pure and may read only `this.<property>` of the same data object, e.g. `{ "js": "['clinicManager', 'receptionist'].includes(this.roleId)" }` on `clinicId`. The column stays NULLABLE; a value that is always required is `isRequired: true` instead (the two together are redundant). Default `null` (no condition). |
| `sortByEnumOrder` | `Boolean` | no | `false` |  |  | Enum only. When true, every sort on this property orders by the DECLARATION ORDER of `enumOptions` instead of alphabetically by the stored string: an ascending sort puts the first declared option first (e.g. `monday` before `tuesday` ... `sunday`, where the alphabetical order would put `friday` first). It applies to every sort path of the generated service - an API's declared sort order, a sort the caller chooses, a paged and an unpaged list - and changes nothing else: the stored values stay the option strings, and filters and equality are unchanged. Supported on SQL-stored data objects in this version (the order is computed from the option position in the query); a data object stored in MongoDB, or a sort served from the Elasticsearch index, is refused at design time (`ENUM_ORDER_UNSUPPORTED_STORE`), and so is the key on a property that is not an Enum (`ENUM_ORDER_ON_NON_ENUM`). Use it instead of an extra Integer ordinal column. Default `false` (alphabetical). |

## Allowed values

### DataTypes

`ID`, `String`, `Text`, `Integer`, `Boolean`, `Double`, `Decimal`, `Float`, `Short`, `Object`, `Date`, `Enum`, `GeoPoint`, `GeoRoute`, `GeoArea`, `Blob`

## Constraints

Property rules:

- `name`, `type` must be present. (`REQUIRED_FIELD_MISSING`)
- `type`, `defaultFn` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- `decimalScale` must be between 0 and 6. (`VALUE_OUT_OF_RANGE`)
- `maxLength` must be between 1 and 10485760. (`VALUE_OUT_OF_RANGE`)

Pattern rules:

| Code | Severity | Rule |
| --- | --- | --- |
| `AUTOINCREMENT_DEFAULT_IGNORED` | warning | Property "…" is 'autoIncrement' and also sets 'defaultValue' (…). |
| `DECIMAL_SCALE_ON_NON_DECIMAL` | error | Property "…" declares 'decimalScale' on a '…' column. |
| `DEFAULT_FN_TYPE_MISMATCH` | error | defaultFn 'now' is only valid on a 'Date' property (got '…'). |
| `DEFAULT_FN_VALUE_CONFLICT` | warning | 'defaultFn' is ignored because 'defaultValue' is also set — the literal 'defaultValue' wins. |
| `DEFAULT_VALUE_LEGACY_NOW_SENTINEL` | error | Current-time defaults are no longer expressed as a 'defaultValue' string like '…'. |
| `IS_REQUIRED_UNSPECIFIED` | warning | Property "…" does not say whether its column is required. |
| `MAX_LENGTH_BELOW_HASH_DIGEST` | error | Property "…" is 'hashed' and declares 'maxLength': …. |
| `MAX_LENGTH_NOT_ENFORCED` | warning | Property "…" declares 'maxLength': …, but its service is generated in '…'. |
| `MAX_LENGTH_ON_NON_STRING` | error | Property "…" declares 'maxLength' on a '…' column. |
| `WRITE_ONCE_REQUIRES_NULLABLE` | error | Property "…" declares 'allowUpdate': 'untilSet' (write-once) on a REQUIRED column. |

# PropertySessionSettings

**Level:** `section` · **Family:** [DataProperty](../ontology/families.md#dataproperty) (domain `DataObject`)

**Ontology:** [PropertySessionSettings in Part 1](../ontology/PropertySessionSettings.md)

Defines how this property is populated from the session context when this block is populated. Session-driven properties are commonly used to associate records with the current user automatically. The binding is applied on CREATE: on the main dataObject of a create Business API, and on a child row written by another API's CreateCrudAction or CreateBulkCrudAction, which fills any session-bound column its own mappings do not name. An UPDATE does not refresh the column - map it in the update dataClause to change it. On either create path an authored mapping wins, and a session that carries no value leaves the key ABSENT, so a required column refuses the row rather than being written null. Leave the wrapping object null when no session-binding is configured.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `sessionParam` | `String` | no |  |  |  | Specifies the name of the session field to bind to this property. Defaults to the property name if not explicitly provided. For example, if the session contains `userId`, that can be mapped to this field. The name is CHECKED against the project's session canon at design time (`SESSION_PARAM_UNKNOWN`): the generated data clause reads `this.session['<sessionParam>']` verbatim, so a field the session does not carry writes null into the column on every request -- a 422 `notNull Violation` when the column is required and completely silent when it is not. On a multi-tenant project the tenant id rides the session under the name the project gave its tenant (`workspaceId`, `storeId`, ...), NOT under a generic `tenantId`, which is stamped by nothing; the tenant CODENAME is the one generic spelling that is real (`tenantCodename`). Required for every declaration EXCEPT `ownerProvenance: "payload"`: an event-sourced owner column is written by the create's `dataClauseItems` entry from the trusted event, so it carries no session binding - omit `sessionParam` there (a sessionParam beside `payload` is refused, OWNER_PROVENANCE_PAYLOAD_WITH_SESSION_PARAM). Leaving it blank on any other declaration answers REQUIRED_FIELD_MISSING. |
| `isOwnerField` | `Boolean` | yes |  |  |  | Marks this property as the ownership field for the data object. When true, the property is used to enforce ownership-based access control (e.g., ensuring users can only modify their own records). This should be used when the property semantically identifies the owner of the record, typically a userId. Ownership is session-fed, directly or carried by a trusted internal event - never derived from row data. `ownerProvenance` says which of the two applies; leave it at its default `session` unless the object's create paths are exclusively internal. |
| `ownerProvenance` | `OwnerProvenance` | no | `"session"` | `session`, `payload`, `sessionOrInternalPayload` |  | WHERE the owner column's value comes from. `session` (the default, and the original session rule) means the framework stamps the column from the creating caller's own session on every create, and a body-supplied value is never an ownership claim. `payload` means the value is carried by a TRUSTED INTERNAL EVENT instead: the row is created by a kafka consumer or another internal path that has no session of its own, and the owner id it writes was stamped at the ORIGINAL session edge by the producing service and carried through an M2M-verified pipe. Declaring `payload` lets an event-sourced object (an order created from an order-intent event, for example) answer the ownership question that `ownershipCheck` and the payment lifecycle routes ask, instead of silently degrading to a login-only boundary. It is REFUSED on an object that has any caller-facing create path - REST, gRPC or SSE (OWNER_PROVENANCE_PAYLOAD_WITH_REST_CREATE; also gRPC and SSE): where a caller can create the row the session rule stands unchanged. kafka, cron and internal-call creates are the internal producers the declaration is for. It never authorizes deriving the owner from row data. `sessionOrInternalPayload` is the explicit opt-in for an object created BOTH by its owner and by a trusted internal job (a buyer's REST create beside a cron that creates scheduled charges): every caller-facing create (REST, gRPC, SSE) stamps the owner from the session exactly as `session` does (an owner `dataClauseItems` entry stays refused there, OWNER_CLAUSE_SHADOWED_BY_SESSION), and a create whose controllers are ALL trusted internal ones (kafka, cron, internal call) writes its authored owner `dataClauseItems` entry. The column keeps its `sessionParam` (the caller-facing creates need it; only `payload` may omit it, REQUIRED_FIELD_MISSING), stays the object's owner for `ownershipCheck` and the payment start gate, and is generated by the nodejs, python, rust, java and dotnet emitters (another build language refuses it, OWNER_PROVENANCE_SESSION_OR_INTERNAL_LANGUAGE). Optional - omit for the `session` default. |

## Constraints

Property rules:

- `isOwnerField` must be present. (`REQUIRED_FIELD_MISSING`)
- `ownerProvenance` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)

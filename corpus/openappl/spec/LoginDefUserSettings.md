# LoginDefUserSettings

**Level:** `section` · **Family:** [LoginDefinition](../ontology/families.md#logindefinition) (domain `ProjectAuthentication`)

**Ontology:** [LoginDefUserSettings in Part 1](../ontology/LoginDefUserSettings.md)

Defines how users are stored, managed, and authenticated within the project. This includes super admin credentials, login identifiers, optional mobile and email verification settings, public registration policies, and whether user groups are active. This structure governs the behavior and structure of the user service's primary data model.

| `superAdminIdentifier` | `String` | no | `"admin@admin.com"` |  |  | The login identifier of the super admin user. This user has full permissions across the project and is not tenant-scoped. DEFAULTS TO THE PROJECT OWNER'S OWN IDENTITY: project creation stamps the creating user's email (or mobile, on a mobile-primary project) here, so the bootstrap account is addressable at an inbox a real person owns. Do NOT replace it with a cosmetic invention like 'superadmin@<project>.com' — a made-up address receives no password-reset mail and may collide with a real user of the project. When primaryLoginIdentifier is 'email' or 'emailOrMobile' this must be an email address; when 'mobile', a number in E.164 format (e.g. +905551234567). Changing this value only affects a project whose database does not yet hold the super-admin row: once seeded, the identifier is owned by the target database and is changed from the preview/deployer DB admin panels instead. |

Once the super-admin row exists in the target database this value no longer affects it — rotate through the application's own password flow. |

| `emailVerificationRequiredForLogin` | `Boolean` | no | `true` |  |  | Indicates whether users must verify their email address before they can log in. Related verification flows must be enabled in VerificationServices. Every login door honours it: the password login and the social login (OAuth callback) both refuse an unverified user with 403 errMsg_EmailNotVerified, and a social registration whose provider email is not verified (see the provider's emailVerification setting) creates an unverified account that verifies through the normal email verification flow before it can log in. An omitted key without an enabled verificationServices.emailVerification flow is warned about (VERIFICATION_FLOW_MISMATCH_BY_DEFAULT). A registration issues no session (no auto-login, emailVerificationNeeded: true) under exactly the condition the login refuses: the requirement on a project whose users have an email, required or optional. Only a user who HAS an email is gated: with an optional email the check is `user.email == null \|\| user.emailVerified === true` (a user registered without an email logs in; one with an unverified email is refused), with a required email it is `user.emailVerified === true`. Unlike email2FARequiredForLogin, this requirement is allowed on an optional email. relogin (refresh token or live session) re-reads the user row and applies the same check with the same 403, so an old refresh token cannot mint a session for a user whose email is no longer verified. |

| `allowUserLevel2FA` | `Boolean` | no | `false` |  |  | Opt-in per-user login second factor. Default false: the login second factor is project-global only (email2FARequiredForLogin / mobile2FARequiredForLogin). When true, the auth user object gains framework-owned enrolment flags, one per 2FA channel whose verification flow is active: `email2FAEnabled` (when verificationServices.email2Factor is active) and `mobile2FAEnabled` (when verificationServices.mobile2Factor is active and the user object has a mobile). Both default false. The password login, relogin (refresh token alone) and the social login stamp sessionNeedsEmail2FA for a user whose `email2FAEnabled` is true, and sessionNeedsMobile2FA for a user whose `mobile2FAEnabled` and `mobileVerified` are both true, IN ADDITION to the global flags: a global flag still challenges every user, enrolled or not. The 2FA-pending session completes through the same email/mobile 2FA start and complete routes and is gated by the same checkValidLogin second-factor gate. The flags are not writable through register, updateUser or updateProfile. The session owner changes them only through the enrolment routes `POST /api/auth/verify/email-2factor-enrolment/start\|complete` and `POST /api/auth/verify/mobile-2factor-enrolment/start\|complete`: start takes `enable` (true to enrol, false to disenrol) and sends a code to that channel, complete takes the `secretCode` and writes the flag, the enrolment code is valid for at most 10 minutes and five attempts, counted atomically, so turning a factor on or off needs a completed challenge of that channel; a session that still owes its login second factor is refused, so a pending session cannot disenrol itself. An administrator resets them through `PATCH /user2faenrolment/:userId` (the updateUserVerification gate). `/currentuser` returns both flags; they carry no secret. A true value with neither 2FA verification flow active is warned about (USER_LEVEL_2FA_WITHOUT_FLOW): no enrolment flag is emitted and no user can enrol. Implemented by the nodejs, java, dotnet and rust auth services: a build whose auth service is generated in another language refuses the flag (USER_LEVEL_2FA_LANGUAGE), because that login would not enforce the enrolled factor; where the language is known only advisorily it is warned as USER_LEVEL_2FA_LANGUAGE_UNSUPPORTED. |

| `registrationExcludedUserProperties` | `String`[] | no |  |  |  | Custom user properties (declared in `authentication.userProperties`) that the PUBLIC registration door must not accept. Listing the property here removes it from those four apis' requestParameters and dataClauseItems entirely; the column keeps its `basicSettings.defaultValue` at registration. The property stays fully writable on the ADMIN doors — `createUser`, `create<Tenant>OwnerOnSaas`, `create<Tenant>UserOnSaas` — and on any role-gated api the project declares for it, so this is a narrowing of the public surface only, never of the data model. Leave empty (the default) to keep every custom property on the register surface. |
| `loginBlockedProperty` | `String` | no |  |  |  | Names ONE custom user property (declared in `authentication.userProperties`) whose value decides whether the account may log in at all — the moderation / account-status gate. Leave it null (the default) and login is refused only for the framework's own reasons (soft-deleted row, unverified email, unverified mobile). Set it to a property such as `accountStatus` and list the refusing values in `loginBlockedValues`: every session-minting path (login, relogin, api-key exchange, trusted proxy login, auto-login after register) then refuses the account while the property holds one of those values, and lets it in again the moment the value leaves the set. This is deliberately NOT a soft delete: the row keeps `isActive: true`, so a suspended user still appears in admin and user-directory reads and can be un-suspended by writing the property back. The property must exist on the user object — naming one that is not declared in `authentication.userProperties` is a design-time error, since the gate would otherwise read `undefined` forever and silently never fire. Only custom properties are accepted: the built-in verification/soft-delete columns already have their own switches (`emailVerificationRequiredForLogin`, `mobileVerificationRequiredForLogin`, `isActive`). |
| `loginBlockedValues` | `String`[] | no |  |  |  | The values of `loginBlockedProperty` that REFUSE a login. Required when `loginBlockedProperty` is set — a named property with no blocked values is a gate that can never fire — and meaningless without it. Model the gate so the permitted state is the DEFAULT value of the property: a user created before the gate existed, or created by a path that does not set the property, must be able to log in. |

## Allowed values

### ErrorStatus

`400`, `401`, `403`, `404`, `409`, `422`, `429`, `500`, `503`

## Constraints

Property rules:

- `primaryLoginIdentifier`, `userNameType`, `secondaryIdentifierPresence`, `dualIdentifierRegistration`, `loginBlockedStatus`, `archivedIdentifierReuse`, `selfArchive` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- `archivedIdentifierHoldDays` must be at least 1. (`VALUE_OUT_OF_RANGE`)
- The items of `superAdminData` must have distinct names (`name`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)

Pattern rules:

| Code | Severity | Rule |
| --- | --- | --- |
| `ARCHIVED_IDENTIFIER_HOLD_DAYS_IGNORED` | warning | archivedIdentifierHoldDays is … but archivedIdentifierReuse is "never", so the days are ignored: an archived account's identifier stays reserved for as long as the account exists and only restoreUser brings it back. |
| `AUTH_REGISTRATION_EXCLUDED_PROPERTY_NOT_FOUND` | error | "…" is not a custom user property declared in authentication.userProperties, so excluding it removes nothing — the register apis keep exactly the surface they had. |
| `AUTH_REGISTRATION_EXCLUDED_PROPERTY_UNSATISFIABLE` | error | "…" is declared isRequired (a NOT NULL column) with no defaultValue or defaultFn, so the registering caller is its only value source. |
| `LOGIN_BLOCKED_ALL_VALUES` | warning | Every option of "…" is listed as blocking, so only a user whose "…" is null (or holds a value outside the enum) can log in. |
| `LOGIN_BLOCKED_PROPERTY_NOT_FOUND` | error | Property "…" is not declared in authentication.userProperties, so the login gate would read an undefined value and never refuse anyone. |
| `LOGIN_BLOCKED_PROPERTY_REQUIRED` | error | loginBlockedValues are declared but loginBlockedProperty is empty, so nothing decides whether a login is refused. |
| `LOGIN_BLOCKED_VALUE_NOT_IN_ENUM` | error | "…" is not one of the enum options of user property "…" (…), so it can never match and the gate would not refuse that state. |
| `LOGIN_BLOCKED_VALUES_REQUIRED` | error | loginBlockedProperty is "…" but no loginBlockedValues are declared, so the gate can never refuse a login. |

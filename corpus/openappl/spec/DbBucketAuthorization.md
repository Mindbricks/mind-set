# DbBucketAuthorization

**Level:** `section` · **Family:** [DbBucket](../ontology/families.md#dbbucket) (domain `Service`)

**Ontology:** [DbBucketAuthorization in Part 1](../ontology/DbBucketAuthorization.md)

Authorization settings for read and write access to the bucket. Controls who can upload and download files, with support for role-based access, access keys, and custom authorization scripts.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `readAccess` | `DbBucketAccessLevel` | no | `"private"` | `public`, `private`, `authenticated`, `roles` |  | Controls who can download files from this bucket. 'public' = anyone, no session required, 'private' = only the file owner and admins (the owner is the account that uploaded the file, compared against the session-stamped uploaderUserId on the file row), 'authenticated' = any authenticated user, including other users' files, 'roles' = only holders of a readCheckRoles role. Sessionless per-file key downloads are governed separately by enableKeyAccess. |
| `writeAccess` | `DbBucketWriteLevel` | no | `"authenticated"` | `authenticated`, `adminOnly`, `roles` |  | Controls who can UPLOAD files to this bucket, and nothing else. 'authenticated' = any authenticated user, 'adminOnly' = only admin roles, 'roles' = only holders of a writeCheckRoles role. Deleting is governed separately by deleteAccess — before that split this same field gated DELETE too, so its default handed every registered account a delete primitive over every other user's files. |
| `deleteAccess` | `DbBucketDeleteLevel` | no | `"owner"` | `owner`, `adminOnly`, `authenticated` |  | Controls who can DELETE files from this bucket — a separate decision from writeAccess, which governs upload only. 'owner' (the DEFAULT) = only the account that uploaded the file, plus admin roles. 'adminOnly' = only admin roles. 'authenticated' = ANY authenticated user may delete ANY file in the bucket, including other users' files; that is the earlier behaviour and is kept only as a deliberate opt-in. The delete gate NARROWS writeAccess and never widens it: a bucket with writeAccess 'adminOnly' stays admin-only for deletes whatever this field says. Ownership is read from the file row's uploaderUserId. RemoteBucket and NativeBucket deletes address a raw storage key: the nodejs router resolves the owner from the uploaderUserId of that key's {name}RemoteFile twin row, which its through-server /upload writes; a key with no twin row (a presigned /upload-url upload) or no recorded uploader, and the language targets that persist no twin, deny every non-admin (fail closed); widen those deliberately with 'authenticated', 'adminOnly' or writeAbsoluteRoles. |
| `enableKeyAccess` | `Boolean` | no | `false` |  |  | When true, any holder of a file's 12-character access key can download that file with NO session, on every bucket kind: DbBucket serves GET .../download/key/:accessKey directly, and RemoteBucket/NativeBucket honour ?accessKey= on the download route (the key is minted on the upload / upload-url response). When false or absent (the DEFAULT), key-based lookup stays behind the normal readAccess gate. Useful for shareable links; treat the key as a per-file capability credential. Unrelated to API keys, which represent a user's own rights and never grant extra authorization. |
| `readAbsoluteRoles` | `String`[] | no |  |  |  | Roles that bypass all read authorization checks. Users with any of these roles can always download files. Every name must be a defined role; an undefined one is UNDEFINED_BUCKET_GATE_ROLE as a warning. |
| `readCheckRoles` | `String`[] | no |  |  |  | Roles required for read access when readAccess is 'roles': the user must hold at least one of them to download. Consulted ONLY by that mode — under 'public', 'private' or 'authenticated' this list has no effect. An empty list under 'roles' behaves like 'authenticated'. Every name must be a defined role (a system role, a roleItems name or value, or a customRoleLookups name): an undefined one is UNDEFINED_BUCKET_GATE_ROLE as a warning, and a list whose every name is undefined while the access mode is 'roles' and readAbsoluteRoles names no defined role is that code as an error, because the bucket then admits no defined-role session. |
| `writeAbsoluteRoles` | `String`[] | no |  |  |  | Roles that bypass all write authorization checks. Users with any of these roles can always upload files. Every name must be a defined role; an undefined one is UNDEFINED_BUCKET_GATE_ROLE as a warning. |
| `writeCheckRoles` | `String`[] | no |  |  |  | Roles required for write access when writeAccess is 'roles': the user must hold at least one of them to upload. Consulted ONLY by that mode — under 'authenticated' or 'adminOnly' this list has no effect. An empty list under 'roles' behaves like 'authenticated'. Every name must be a defined role (a system role, a roleItems name or value, or a customRoleLookups name): an undefined one is UNDEFINED_BUCKET_GATE_ROLE as a warning, and a list whose every name is undefined while the access mode is 'roles' and writeAbsoluteRoles names no defined role is that code as an error, because the bucket then admits no defined-role session. |
| `readAuthScript` | [`MScript`](./MScript.md) | no |  |  | MScript kind `code` | Custom MScript expression for read authorization; must return true to allow the download. Evaluated after the coarse readAccess/role checks and can only NARROW them — absoluteRoles still bypass everything. The request context IS the script receiver, so every field is reachable both as this.<field> (the platform-wide MScript convention) and as a bare name: session, userId, role, params, query, body, data. On a READ gate data is the FILE ROW: the script runs after the coarse checks allowed and after the file row is looked up (the DbBucket file row, or the {name}RemoteFile twin found by storageKey on a Remote/Native bucket), so a per-file rule such as this.data?.uploaderUserId === this.session?.userId is expressible. A key that resolves to no row is answered as missing (404) without running the script, so a script never reveals which keys exist. A denied file answers the same 404 NOT_FOUND as a missing one (no existence oracle), and a script that throws denies the same way. Example: this.session?.userId === this.params.ownerId. |
| `writeAuthScript` | [`MScript`](./MScript.md) | no |  |  | MScript kind `code` | Custom MScript expression for write authorization; must return true to allow the upload. Evaluated after the coarse writeAccess/role checks and can only NARROW them — absoluteRoles still bypass everything. The request context IS the script receiver, so every field is reachable both as this.<field> (the platform-wide MScript convention) and as a bare name: session, userId, role, params, query, body, data. On a WRITE gate data is the request body, i.e. the upload metadata being stored. A script that throws denies. Example: this.session?.userId === this.data?.ownerId. |

## Constraints

Property rules:

- `readAccess`, `writeAccess`, `deleteAccess` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)

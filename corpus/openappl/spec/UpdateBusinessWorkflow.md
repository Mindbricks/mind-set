# UpdateBusinessWorkflow

**Level:** `section` · **Family:** [BusinessWorkflow](../ontology/families.md#businessworkflow) (domain `BusinessApi`)

**Ontology:** [UpdateBusinessWorkflow in Part 1](../ontology/UpdateBusinessWorkflow.md)

Defines the execution milestones for an `update`-type Business API, used to modify an existing record. Each field represents a fixed lifecycle milestone. Custom action names placed under a milestone will be executed in order after that point. These workflows enable full customization of business logic without overriding default update behavior, and they support visual modeling of logic steps.

**Failure semantics — NO ROLLBACK.** The milestones run sequentially with no transaction. Everything up to and including `afterBuildDataClause` (and before it `afterFetchInstance` / `afterCheckInstance`) runs BEFORE the row is updated, so an action that throws there leaves the database untouched. From `afterMainUpdateOperation` onward the parent row is already committed, and an action that throws (`onActionError: throwError`, the default) aborts the remaining pipeline WITHOUT reverting that update or any write an earlier action already made — the classic corruption is a status-advancing update whose `afterMainUpdateOperation` child create 409s, leaving the record advanced and the child missing. Put child writes that may legitimately fail in `afterCheckInstance` or `afterBuildDataClause`; use `onActionError: completeApi` for post-main work that must not fail the api, and an explicit compensating api when a post-main write really can fail. `completeApi` alone is INCOMPLETE for an `updateCrudAction`: a selector that matched no row resolves `[]` without raising anything, so nothing lands in `this.<actionName>Error`; add `onNoRows: throwError` to the action when the row it addresses must exist. See `BusinessWorkflow` for the full contract.

## Properties

| `afterStartBusinessApi` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | Executed first, just after the api is started by the controller and BEFORE the login check (pipeline step 0): the context has the raw request, and a session the caller sent is populated, but the api's login requirement has not been enforced yet, so an anonymous caller reaches this stage. Use it for login-independent work - fundamental request validations or preparing the context. On an api that requires a login (authOptions.loginRequired, default true) an InterserviceCallAction, AgentCallAction, IntegrationAction, InterProjectCallAction, SendMailAction, CheckMailboxAction, ReadMailAction, PublishEventAction, SendSmsAction, SendWhatsAppAction or SendPushNotificationAction may not be scheduled here, directly or inside a loop/parallel container: each acts with the service's or the project's own authority (a machine-identity forward, a mail, SMS, WhatsApp or push send or a mailbox read with the project's credentials, or a Kafka event its consumer treats as a machine caller), so an anonymous caller would borrow that authority. Design time refuses that shape (PRE_AUTH_MACHINE_AUTHORITY_ACTION); schedule those actions at afterReadParameters (the first milestone after the login check) or later. |
| `afterReadParameters` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | Triggered after all parameters are read from the request or Redis. Use this to perform early validation or context enrichment based on raw input. |

Like `afterSendResponse`, this milestone is SUCCESS-ONLY: an api that answered 4xx/5xx never reaches it. |

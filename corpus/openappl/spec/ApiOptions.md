# ApiOptions

**Level:** `section` · **Family:** [BusinessApiBasics](../ontology/families.md#businessapibasics) (domain `BusinessApi`)

**Ontology:** [ApiOptions in Part 1](../ontology/ApiOptions.md)

Main configuration section for a Business API. This object includes essential attributes such as naming, access control, event handling, input generation, and fallback strategies. In many cases, configuring this section alone is sufficient to define the primary behavior of an API entry point.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `dataObjectName` | [`LocalDataObjectName`](./LocalDataObjectName.md) | yes |  |  | names a [DataObject](./DataObject.md) | Specifies the primary data object that this Business API interacts with. This object is the core target of the API's operation, such as reading, updating, or deleting records. Required even when dataViewName is set — the DataView's mainObject must match this dataObject. |
| `dataViewName` | `String` | no |  |  |  | Optional. Specifies the name of a DataView defined in the BFF service whose mainObject matches this API's dataObject. The `get` and `list` read operations then answer the VIEW's row (its projection plus its aggregates/stats). How they read depends on the view: for a STORED view (`viewBasics.isStored: true`) they query the view's Elasticsearch index; for a DYNAMIC view they bind at READ TIME - the api reads its object from the DATABASE with its own where machinery exactly as authored (selectBy, fullWhereClause, additionalClauses, tenant and ownership terms; never compiled to an Elasticsearch query) and the view's joins are applied to each returned row per request, so the read is as fresh as any database read. All write operations (create, update, delete) - including the instance fetch performed by update/delete - execute against the database; they do not read from the DataView. The dataObjectName is always required and must match the DataView's mainObject. |
| `crudType` | `CrudTypes` | yes |  | `create`, `update`, `get`, `list`, `delete` |  | Defines the primary operation type for this API. Possible values are `get`, `list`, `create`, `update`, and `delete`. This classification drives the behavior and flow of the API lifecycle. |
| `name` | `String` | yes |  |  |  | A unique, human-readable name for the API, used for referencing in documentation and the UI. This is not a code-level identifier; instead, generated class and function names are derived from this value. Use camelCase formatting, avoid spaces or special characters, and ensure uniqueness within the same service. If you want the API to behave like a default RESTful endpoint, use a verb-noun combination like `createUser`, `getOrder`, or `deleteItem`, which will enforce expected parameters and URL patterns (e.g., `/users/:userId`). This name IS the API's identity: it keys the generated manager class and its file, the api-layer barrel export, the internal-call registry member you call as `API.<name>(params)`, the `targetApi` of an interservice call, and the swagger operationId. Two entries on the same data object that resolve to the same identifier — identical, differing only in case, or differing only by separators (`get_user` vs `getUser`) — are refused at design time (API_NAME_COLLISION). A trailing `ById` on a `get` / `update` / `delete` API affects only the derived ROUTE, which drops the suffix so `getOrderById` mounts at `/orders/:orderId`; the identity keeps the full name, so `unpublishPortfolio` and `unpublishPortfolioById` are two distinct, legal APIs (give at least one of them its own `restSettings.routePath`, or they will share a mount). The name `<serviceName>Service` (any letter case) is refused (SERVICE_MANAGER_NAME_COLLISION): the api's generated manager class would take the name of the service-level base manager `<ServiceName>ServiceManager`, the same clash a DataObject of that name draws. |
| `apiDescription` | `Text` | no |  |  |  | A brief explanation of the API's business purpose or logic. Helps clarify its intent for developers and documentation readers. |
| `frontendDocument` | `Text` | no |  |  |  | A text based information to inform the frontend developer or frontend AI agent about the api specific UX behaviour of the api logic based on user stories and use cases. The format may be either text or markdown(recommended). Write the document as an AI prompt and describe api specific UX behaviours. Note that this document will be given to the AI agent or human developer combined with all technical details that is generated from the business api design,so this document should only focus on data api-specific behavioral UX business logic. |
| `testingNotes` | `Text` | no |  |  |  | Free-text markdown block written by the designer at apply time, describing how this API's happy path should be tested. Read VERBATIM by the api-test-plan-scaffold blueprint as the AUTHORITATIVE happy-case source — overrides the planner's role/body-field inference rule when present. Write down only what the planner cannot statically infer from authOptions + the data-object schema + the route doc: custom validateAction rules (e.g. 'rejects 403 when seller.isActive=false'), sequencing prereqs ('must be called after checkout'), side effects worth asserting (kafka events, related-record writes), auto-populated session fields (sellerId, ownerId, tenantId — keep these out of the request body), conditional status codes (200 vs 201 vs 409). Format: short markdown following the template in the apply prompt — Happy path / Side effects / Custom rules / Skip cases. Empty is allowed (planner falls back to inference) but the validator will warn. |
| `raiseApiEvent` | `Boolean` | no | `false` |  |  | Indicates whether the Business API should emit an API-level event after successful execution. This is typically used for audit trails, analytics, or external integrations. Default `false` since patterns 1.93.0: a new api publishes nothing until you set it to `true`, and a stored api that omits the field publishes no route event and declares no route topic (before 1.93.0 an omitted field meant `true`; set it to `true` explicitly to keep such an api publishing). An explicit stored `true` publishes exactly as before. A project consumer of this API's derived route topic, written with or without the project codename prefix, requires `raiseApiEvent: true`; validation reports KAFKA_TOPIC_API_EVENT_DISABLED and names the service and API when it is off. Turn it on for writes another service or an external system listens to; a get or list event carries the whole result (a list event the whole page), so leave reads off unless a consumer needs them. The emitted payload is the unified event ENVELOPE: `{ id, type, source, time, requestId, actor: { userId, sessionId?, tenantId?, roleId? }, data: { _type, ...record }, old? }`. The API's result record rides under `data` (e.g. a `createUser` event carries `payload.data.email`, never `payload.email`), `type` is the domain fact (`user.created`), `source` is the publishing service codename, and update/delete events carry the previous state under `old`. Events NEVER carry a session object, tokens, or HTTP transport metadata — `actor` is the minimal identity, and credential-bearing keys are scrubbed at publish time. Every consumer mapping (agent kafka controllers, event subscriptions, notification triggers, external integrations) must read record fields through `data`. Use the `getKafkaEventPayloadStructure` tool to see the exact per-topic shape. |
| `raisedEventTopic` | `String` | no |  |  |  | Optional. The EXPLICIT wire-topic suffix for this API's raiseApiEvent event. By default the suffix is DERIVED from the API name by verb inversion (`followUser` -> `user-followed`, `subscribeToPlan` -> `toplan-subscribed`, `processRefundRequest` -> `refundrequest-processed`), which for a non-CRUD verb is rarely the name a spec guesses - and a consumer bound to the wrong spelling receives nothing, with no error anywhere. Set this to publish under a name you choose. An ordinary suffix becomes `<serviceCodename>-<raisedEventTopic>`; a complete topic already starting with `<serviceCodename>-` is used once. Overrides are trimmed and lowercased. Only the complete service prefix followed by a dash counts as already prefixed: a bare service codename, a partial prefix, or another service prefix remains an ordinary suffix. It must satisfy Kafka's topic character class (a-z A-Z 0-9 . _ -) and the composed name must stay within 249 characters. It moves the TOPIC only - the generated publisher class, topic constant and event class are still named from the derived event, so an override can neither rename nor collide generated symbols. Ignored when raiseApiEvent is false. When the derived name is UNGUESSABLE (any non-CRUD verb), validation reports it as the warning KAFKA_RAISED_EVENT_TOPIC_UNGUESSABLE, naming the wire topic and the derivation rule, so the contract is visible at authoring time without a separate getKafkaEventTopicsOfService call; setting this property silences that warning. A CRUD derivation (createOrder -> order-created) is not reported, because a warning on every event would train its reader to ignore the code, and neither is a framework-INJECTED api, whose name the designer did not choose and cannot override. |
| `blockMcp` | `Boolean` | no | `false` |  |  | When true, this Business API is left out of its service's public `GET /tools` registry, so mcpbff does not publish it as an MCP tool and the agent hub's discovered tool catalog does not list it. Every REST BusinessApi is in that registry by default; this flag is the only way to remove one (`mcpExposed` is retired). It hides the tool only: the REST route and the other controllers stay mounted with their normal auth, and an agent whose `toolSettings.apiTools` names the API still gets it. Use this for APIs that require frontend-specific flows (e.g., payment with credit card input, 3DS verification) and should not be called by AI agents directly. |
| `mcpExposed` | `Boolean` | no | `false` |  |  | RETIRED: no generator reads this flag to decide MCP exposure, so setting it neither adds nor removes a tool. Generated services run no MCP server and serve no `/mcp` or `/mcp-tools` route. Each service publishes a protocol-neutral `GET /tools` registry that mcpbff, the project's only MCP endpoint, reads and projects into MCP tools named `<service>__<api>`. Every BusinessApi with a REST controller is in that registry unless `blockMcp: true`: exposure is opt-out, and `blockMcp` is its only switch. Kept so stored blueprints that carry it stay valid; do not set it. A few design-time checks still read it: `true` reserves the parameter name `accessToken` (MCP_RESERVED_PARAMETER_NAME) and counts as an external exposure in the UNPAGED_LIST_EXPOSED and PUBLIC_MUTATION_AUTHZ_PIPELINE_OFF warnings. |
| `isDefaultApi` | `Boolean` | no | `false` |  |  | Marks this API as the canonical API for its crudType on the associated data object. This is a DOCUMENTATION marker, not a codegen switch — no emitter derives a route, a controller or a client from it. Its one realised effect is that the generated project documentation labels the endpoint '[Default <crudType> API]' so a frontend developer or an AI agent picks it over a custom variant. At most one API per crudType per data object should carry it — nothing enforces that today (follow-up). Leaving it unset is fine — readers then fall back to the most general API for the operation. |
| `useIdempotencyKey` | `Boolean` | no | `false` |  |  | When true, this API supports idempotent replay. The caller sends any string as `api-idempotency-key` (REST: header, query, or body — header wins; gRPC/MCP: in the request envelope). A repeated key returns the previously stored successful response with the response header `idempotency-key-cache: true` instead of re-running the API; error responses are never cached, so a failed call can be retried with the same key. Reusing a key with a different request payload is rejected with 409 `IDEMPOTENCY_KEY_INCONSISTENCY` — the client must keep a key's request identical across retries. The default is `false`: no replay behavior, every call executes normally. |
| `includeSoftDeleted` | `Boolean` | no | `false` |  |  | Opt this API OUT of the soft-delete row filter. On a data object with `basicSettings.useSoftDelete: true` every read and scoped write is narrowed with `isActive: true` by default, so archived rows stay invisible. That default makes a RESTORE endpoint inexpressible — an update whose whole purpose is to select an archived row and reactivate it can never match its target (the where clause, the fetch-instance read, and the db-layer update all AND `isActive: true`, so `checkInstance()` 404s). Set `includeSoftDeleted: true` to suppress the filter for THIS api only: no `isActive` term is injected into the where clause, and the generated fetch/get/list/update calls pass `includeArchived: true` down to the db layer. Use it for restore/undelete endpoints and admin or audit reads that must show archived rows — never for ordinary reads, which would leak archived rows. A `crudType: delete` API may not declare it (INCLUDE_SOFT_DELETED_ON_DELETE, error): its main delete selects live rows only, deleting an archived row would re-archive it rather than purge it, and there is no purge operation. The main-object filter is unchanged on an object with `useSoftDelete: false` (no `isActive` column) or a `crudType: create` API (no main where clause); validation warns in both cases. The flag also reaches the workflow child actions whose target object carries `isActive`: a child `UpdateCrudAction`, `DeleteCrudAction` or `FetchStatsAction` passes `includeArchived: true` to their db-layer helper even when the main object has no soft delete (on the stats helper the argument sits after `bucketBy`, so an opted-in api without a bucket emits `(query, stats, undefined, true)`); every other combination keeps the historic call arity byte for byte. Independent of the finer-grained escape hatch: an api whose own query already constrains `isActive` (a `whereClause.fullWhereClause` / `additionalClauses` term reading a declared `isActive` request parameter — `isActive` is framework-managed and cannot be declared as a data property or list filter) always keeps its explicit value; the default is only applied when the clause says nothing about `isActive`. |
| `loadShedTier` | `Integer` | no |  |  |  | Optional shed-priority tier (integer 0-5) this API declares for itself when the owning service runs a `loadShield` (0 = never shed — bypasses the shield queue entirely; 5 = first to shed under congestion). The per-API counterpart of the shield's central `loadShield.tiers.assignments[]` (the eventStream `loadSheddingPriority` idiom — a designer states an API's importance where the API is authored). PRECEDENCE (most specific wins): a central action-narrowed assignment > a central api-level assignment > this `loadShedTier` > the derived default by action nature (health 0, auth 1, writes 2, single reads 3, lists/reports 4) — the shield stays the architect's override view. INERT without a shield: on a service with no declared/enabled `loadShield` the property changes nothing (generated output stays byte-identical) and validation surfaces a warning (LOADSHIELD_TIER_WITHOUT_SHIELD). Values outside 0-5 fail validation (LOADSHIELD_TIER_INVALID). |
| `onNotFound` | `ApiOnNotFoundPolicy` | no | `"throw404"` | `throw404`, `complete` |  | Policy for a missing target row on get/update/delete APIs. `throw404` keeps the ordinary not-found response. `complete` routes a get/prefetch miss and, for update/delete, a zero-row mutation result through workflow.<crud>.afterMissingInstance; the normal after-main branch runs only for a present/successfully mutated row. Both outcomes then rejoin at afterBuildOutput and complete successfully. `complete` is invalid for create/list. TRANSPORT BOUNDARY: `complete` is defined only where the execution path has an explicit completed-miss outcome. Two transports carry one. (1) The ordinary non-streaming REST manager path, where a miss answers 2xx with the miss body instead of 404; an MCP-EXPOSED api counts, because it invokes that same REST route through the generated `/tools` registry — and it is the ONLY MCP exposure there is, since every generated service is MCP-agnostic (docs/ADR-mcp-service-tool-registry.md), so no api is ever refused for `MCP`. (2) A KAFKA controller, where a miss is an explicit CONSUMED NO-OP: `workflow.<crud>.afterMissingInstance` runs, no api event is raised (nothing was written), the handler logs `KafkaCompletedMissingInstance` at info level rather than `ErrorInKafkaMessage`, and it returns normally so the offset commits exactly as it does for an applied message — which is what makes a saga applier idempotent on redelivery. When the api declares a response topic, the miss is published with the envelope `type` `<dataObject>.<crudType>.missed` and the payload carries `_outcome: "completedMissingInstance"` beside whatever `afterMissingInstance` wrote to the response; an APPLIED outcome publishes exactly what it published before, so the ABSENCE of `_outcome` means the operation ran. SSE/streaming, gRPC and cron carry no completed-miss outcome, so declaring `complete` on an api that enables any of them — or that disables the REST controller without enabling a Kafka controller, leaving no supported transport at all — is refused at validation with `API_ONNOTFOUND_TRANSPORT_UNSUPPORTED`, and, if it ever reaches deploy time, by the generator's codegen guard (`[nodejs:onNotFound]`, `[dotnet:onNotFound]`, `[java:onNotFound]`, `[rust:onNotFound]`). EXECUTION-PATH BOUNDARY: two WHOLE-SERVICE shapes carry no completed-miss outcome either, whatever transports the api declares. (a) An api a JobStream targets — the job worker path has no caller to answer a miss to, and `targetApi.keepPublicRoute` does not change that, since it only decides whether the public route survives BESIDE the worker. (b) An api reached through the untyped `serviceLayerCall` adapter, which returns whatever the adapter returns and so cannot state an explicit operation outcome. Declaring `complete` on either is refused at validation with `API_ONNOTFOUND_EXECUTION_PATH_UNSUPPORTED` and, at deploy time, by the same codegen guards (`[nodejs:onNotFound]`, `[dotnet:onNotFound]`, `[java:onNotFound]`, `[rust:onNotFound]`). LANGUAGE PORTS: the Kafka completed-miss outcome is implemented by the nodejs, dotnet and java, rust and golang, and python generators. The dotnet guard composes its transport predicates from the same shared module design-time validation reads (src/patterns/custom/missing-instance-transports.ts); the java and rust guards mirror them. The golang generator emits the Kafka consumed-no-op but carries no codegen refusal of its own, so validation is its only boundary. The python generator emits the Kafka consumed-no-op, the `.missed` envelope and the `_outcome` marker for get, update and delete apis and, like golang, carries no codegen refusal of its own. |
| `exposeSecrets` | `String`[] | no |  |  |  | The `isSecret` columns THIS api is allowed to carry in its own response, named one by one. An `isSecret` column is scrubbed from every payload by default, which is right for a credential and wrong for a value whose owner must be able to read it back (a ticket code, a one-time claim link): the owner's own ownership-gated read returned the row with the field silently missing. Naming a column here carries it in this api's response ONLY. Every other surface is unchanged - other apis still scrub it (the allow-list is per-api, not per-column), and the Kafka envelopes, db-event payloads and request/response logs are scrubbed at their own choke points, which this field does not reach at all. Name a column that is not `isSecret`, or not on this api's `dataObjectName`, and validation refuses it: the field has to state facts. A `hashed` column is refused too - that value is a bcrypt digest, not the plaintext anyone wants back - and so is any name that ANY object in the project declares `hashed` (auth's `user.password` included): the scrub matches by name across the whole response, so such a name is never removed from the api's scrub list, whatever validation says. The opened value is this api's response and goes wherever that response goes: an api used as an agent tool hands it to the LLM provider and its conversation checkpoint, and an api with `useIdempotencyKey` stores it in the replay store. This supersedes re-injecting a scrubbed value with an AddToResponseAction, which works but records a deliberate secret exposure as an ordinary response action, invisible to review. |
| `visitSettings` | [`VisitSettings`](./VisitSettings.md) | no |  |  |  | Makes this BusinessApi a VISIT source (docs/ADR-object-visits-pattern.md): WHICH call counts as a visit of its data object, with which signal, and how it is confirmed. The storage (history table, counter, read state) belongs to the object's `objectSettings.visitTracking`, which must be enabled. The designer knows which api is a real visit: the shop-front product detail is one, the same row fetched by the admin panel, an MCP tool or an internal call is not. Recording runs after the response is sent and never adds latency to the read. This block replaces nothing: the retired GetOptions/ListOptions.setAsRead stay retired. Optional - omit (or null) when unused. |

## Constraints

Property rules:

- `dataObjectName`, `crudType`, `name` must be present. (`REQUIRED_FIELD_MISSING`)
- `crudType`, `onNotFound` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- `dataObjectName` must be a well-formed [`LocalDataObjectName`](./LocalDataObjectName.md) (a data object of the same service). (`INVALID_LOCAL_DATA_OBJECT_NAME_FORMAT`)

Pattern rules:

| Code | Severity | Rule |
| --- | --- | --- |
| `API_ONNOTFOUND_EXECUTION_PATH_UNSUPPORTED` | error | onNotFound=complete has no completed-miss outcome contract on this API's execution path: …. |
| `API_ONNOTFOUND_TRANSPORT_UNSUPPORTED` | error | onNotFound=complete has no completed-miss outcome contract on this API's enabled transports: …. |
| `BUSINESS_API_NOT_FOUND_POLICY_INVALID_CRUD` | error | onNotFound=complete is only valid for get/update/delete APIs, not …. |
| `KAFKA_RAISED_EVENT_TOPIC_UNGUESSABLE` | warning |  |
| `RAISED_EVENT_TOPIC_INVALID` | error | raisedEventTopic "…" cannot be used as the wire-topic suffix for API "…" (…). |

## Migration

> **Warning:** deprecated and relocated properties. They are listed so that older blueprints can be updated; new blueprints must not use them.

| Property | Status | Use instead | Note |
| --- | --- | --- | --- |
| `raiseDbLevelEvents` | deprecated | | RETIRED: this api-level flag never had a runtime effect and still has none. Db-level events are published by default; an object nobody consumes turns them off with the DataObject setting `objectSettings.basicSettings.publishDbEvents: false` (validation refuses it where a DataView, a subscription, a hub, a notification or another consumer reads them). This flag and is kept only so stored blueprints that carry it stay valid; do not set it. Db-level events carry the unified envelope: the row (stamped with `_type`) under `data`, the pre-change row under `old` (`updated` events only), and a `<object>.<verb>` event `type`; topics are `<serviceCodename>-dbevent-<object>-<verb>`. Use the `getKafkaEventPayloadStructure` tool for exact per-topic shapes. |

## Example

Use ApiOptions to declare the core identity of a Business API — its target data object, crudType, name, and behavioral flags (events, default-API marking, MCP opt-out with `blockMcp`). This example configures a list API over orders that is marked as the default list endpoint; like every REST API without `blockMcp`, it is also published as a tool in its service's `GET /tools` registry.

```json
{
  "dataObjectName": "order",
  "crudType": "list",
  "name": "listOrders",
  "apiDescription": "List orders visible to the current user within their tenant.",
  "raiseApiEvent": false,
  "isDefaultApi": true
}
```

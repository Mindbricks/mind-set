# ShoppingCartBasicSettings

**Level:** `section` · **Family:** [ShoppingCartConfig](../ontology/families.md#shoppingcartconfig) (domain `Service`)

**Ontology:** [ShoppingCartBasicSettings in Part 1](../ontology/ShoppingCartBasicSettings.md)

**Activation:** the pattern is switched on by `useShoppingCartFeature`.

Core shopping cart settings with activation flag. When useShoppingCartFeature is true, the Cart and CartItem DataObjects are auto-generated.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `useShoppingCartFeature` | `Boolean` | no | `false` |  |  | Enables shopping cart functionality for this service. When true, auto-generates Cart and CartItem DataObjects with all pricing, status, and calculation properties. In a multi-tenant project the two generated objects are tenant-level (objectDataIsInTenantLevel true, with the injected <tenantName>Id column): every cart and cart line row, and a local-mode order written into a tenant-level order object, carries the tenant of the request that created it, and a designer read api over them runs the tenant filter, so a tenant administrator reads its own tenant's carts only. This is decided when the code is generated, from the project's tenancy (nodejs today, the other languages follow their port); a single-tenant project is unchanged, and the Campaign store always stays platform-level. |
| `cartObjectName` | `String` | no | `"cart"` |  | format [codeName](./value-formats.md#codename) | Name for the auto-generated Cart DataObject (e.g., 'cart', 'shoppingCart'). Related objects are named based on this: {name}Item, {name}Campaign, etc. |
| `currency` | `String` | no | `"USD"` |  |  | The currency code for this cart (e.g., USD, EUR, TRY). All monetary calculations use this currency. |
| `supportGuestCart` | `Boolean` | no | `false` |  |  | Whether to support anonymous/guest carts before user login. Adds sessionId property for session binding. An anonymous shopper IS its session id (the X-Session-Id header), and the guest-to-login transition is ROTATION, NOT ADOPTION: the active-cart pointer is owner-sliced (user:{userId} wins over session:{sessionId} the moment the session carries a userId), so logging in moves the shopper to a different owner slot and they start from 'no cart'. The guest basket is neither merged nor adopted - it stays intact under its session slot until the cart TTL expires, and dropping back to the same session id finds it again. Cart adoption/merge on login is a possible FUTURE feature, not configurable behavior. |
| `supportNotes` | `Boolean` | no | `false` |  |  | Nodejs: true adds a nullable Text notes property to the autogenerated cart DataObject. Generated manager createCart(initialData) and cart events can supply it; the cart database mirror can persist and recover it when mirroring is active. Hand-authored cart definitions take precedence. This flag does not add a REST header-edit route. |
| `supportMetadata` | `Boolean` | no | `false` |  |  | Nodejs: true adds a nullable Object metadata property to the autogenerated cart DataObject. Generated manager createCart(initialData) and cart events can supply custom JSON data; the cart database mirror can persist and recover it when mirroring is active. Hand-authored cart definitions take precedence. |

# CheckoutConfig

**Level:** `subsection` · **Family:** [ObjectSettings](../ontology/families.md#objectsettings) (domain `DataObject`)

**Ontology:** [CheckoutConfig in Part 1](../ontology/CheckoutConfig.md)

Configuration for provider-neutral one-time payments. Provider-binding is explicit via `providerName` (lookup into projectSettings.paymentProvidersSettings.paymentProviders[]). Property bindings (amount / currency / status / owner) are PropRefer paths into the parent DataObject. Lifecycle hooks replace the legacy edgeFunctionOnStatusChange / edgeFunctionPaymentDone / afterPaymentCreations fields — designers can author multiple per-trigger MScript handlers in one place. HOSTED-CHECKOUT RETURN: when the bound provider settles through a hosted checkout form (iyzico Checkout Form), the vendor callback ALWAYS points at the service's own `/v1/payments/checkout-return/<provider>` route, derived from SERVICE_URL and never from a request body. That route settles the ticket and then redirects the buyer 303 to the ticket's `metadata.returnUrl`, which is stamped from the `return_url` supplied in the payment user params of the START call. With no `return_url` there is nothing to redirect to and the route answers a minimal JSON confirmation (`ok`, `orderId`, `paymentId`, `paymentStatus`, `statusLiteral`, `requestId`) - documented behaviour, but the buyer's browser stops there, so the buyer's return to the application depends entirely on `return_url` being present. The mounted payment route takes it as `body.paymentUserParams.return_url` on `PATCH /v1/start<object>payment/:orderId`; an api that drives the flow with a start-stage PaymentAction takes it from its OWN declared requestParameters (PAYMENT_START_NO_CALLER_PARAMS is the design-time finding when it declares none). A buyer who pays on the hosted form but never comes back (tab closed) is settled the same way, once, from iyzico's Checkout Form webhook (`CHECKOUT_FORM_AUTH`) on `/v1/payments/webhook/<provider>`, which the merchant points at the service in iyzico's panel. 3-D SECURE RETURN: a saved-card iyzico start (3dsecure/initialize) sends the service's own `/v1/payments/threeds-return/<provider>` as the vendor callback, likewise derived from SERVICE_URL. iyzico posts the bank-challenge outcome there; the route resolves the ticket by the posted paymentId plus the attempt's conversationId, calls 3dsecure/auth itself (forwarding conversationData) when the bank reports mdStatus=1, settles the ticket success / failed / amount_mismatch, runs the payment lifecycle hooks, and redirects 303 to `metadata.returnUrl` with `orderId` and `status` query parameters (the same JSON confirmation without one). The start answer for that shape is not a redirect: the frontend renders `next_action.threeDSHtmlContent`. No designer-authored complete stage is involved for either iyzico shape. 3-D SECURE BY PROVIDER: Stripe completes in the browser (Stripe.js) and the generated webhook route records it, with no return route; Adyen completes through the generated `PATCH /v1/complete<object>payment/:orderId` route with the `details` Adyen Web returns; iyzico through the two return routes above. A design never authors a complete, callback or webhook stage for these three providers.

| `amountProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | The property name that holds the order amount for payment. PLATFORM MONEY CONVENTION: every bound money property carries MAJOR currency units as a decimal (e.g. 250.00 TL, 10.00 USD) - never minor units (kurus/cents). Adapters convert to each provider's wire encoding themselves; a blueprint that stores minor units in a bound column will charge 100x. The bound column MUST be declared `type: "Decimal"`, so the framework rounds it to its `decimalScale` at every write boundary and before the amount reaches the provider. A bound column declared with another NUMERIC type (Integer/Short/Double/Float) is migrated by validation to Decimal (scale from the binding's static currency, default 2) and reported as an auto-fix; a non-numeric one is the ERROR `MONEY_BINDING_NOT_DECIMAL`. REQUIRED IN EFFECT: the generated REST start route (`PATCH /v1/start<object>payment/:orderId`) reads the amount off the persisted order row by LITERAL key, [amountProperty, `amount`] - there is no static amount and that route strips a body amount - so an activated checkout object that leaves amountProperty unset and declares no `amount` property is a design-time ERROR CHECKOUT_AMOUNT_UNBOUND (that route is refused 400 on every call, and a PaymentAction needs amountProperty anyway). A PaymentAction start resolves amountProperty more widely (request parameters, a dotted path into the persisted row such as `order.total`, then the manager scope), so a SET amountProperty that is not a declared property is only a WARNING CHECKOUT_AMOUNT_BINDING_NOT_A_COLUMN: the PaymentAction start works, the REST start route reads the literal key and NaNs (or charges the `amount` column when one exists). |

| `publishLifecycleEvents` | `Boolean` | no | `false` |  |  | Opt-in (default false; only a literal `true` on an ACTIVE checkout block counts) that makes the generated payment layer publish this object's normalized PAYMENT lifecycle events to Kafka (family `payment`), one topic per event: `<projectCodename>-<service>-service-lcevent-payment-<object lowercased>-<suffix>`, where the FIXED event list and its suffixes are `payment.captured` -> `captured`, `payment.failed` -> `failed`, `payment.canceled` -> `canceled`, `refund.succeeded` -> `refund-succeeded`. On a nodejs service the list also carries `payment.requires_action` -> `requires-action` and `payment.authorized` -> `authorized` (state events: published only while the ticket is still `started`) and `refund.created` -> `refund-created` and `refund.failed` -> `refund-failed` (facts keyed on the refund), and the same flag also publishes the object's DISPUTES (family `dispute`, topic `...-lcevent-dispute-<object>-<suffix>`: `dispute.opened` -> `opened` and `dispute.evidence_required` -> `evidence-required` as facts, `dispute.won` -> `won` and `dispute.lost` -> `lost` only when the dispute row ends in that state; `data.dispute` = an allowlisted sys_<Object>Dispute projection, no metadata) and, when the object also has an ACTIVE marketplace block, its PAYOUTS (family `payout`, topic `...-lcevent-payout-<object>-<suffix>`: `payout.in_transit` -> `in-transit`, `payout.paid` -> `paid`, `payout.failed` -> `failed` (with failureReason), `payout.returned` -> `returned`, each only when the payout row ends in that state; `data.payout` = an allowlisted sys_<Object>Payout projection without the claim / lease columns or metadata, `record` null). The java and dotnet payment layers publish the fixed list only. Published by the payment intent machine AFTER the sys_<Object>Payment status write and AFTER the designer lifecycle hooks, and only when the ticket ENDS in the state the event names (captured -> success, failed -> failed, canceled -> canceled, refund.succeeded -> refunded or partially_refunded): a late cancel of a captured payment, or a capture the amount gate refused, publishes nothing. A tokenized renewal ticket (`metadata.recharge === true`) is not published on this family - the subscription family announces the renewal. `data` = { eventType, family, object, providerName, providerEventId, occurredAt, orderId, previousStatus, status, dedupeKey, failureReason (payment.failed only), payment (an ALLOWLISTED projection of the sys_<Object>Payment ticket: id, orderId, providerName, paymentId, providerIntentId, paymentStatus, statusLiteral, failureReason, amount, currency, fee, ownerId, createdAt, updatedAt, the tenant column), refund (refund.succeeded: providerRefundId, providerIntentId, statusLiteral, amount, currency, reason), record (this object's own row read by `orderId`, in the shape and unit its db-change event publishes) }; never the raw provider payload, the client secret / next action, the refund evidence token or the ticket's metadata. Delivery is AT LEAST ONCE through the service's lifecycle outbox: each event is written to `sys_lifecycle_outbox` (one row per `data.dedupeKey`, the built envelope plus its retry state) before it is sent, the send is not awaited on the payment path, and a send the broker refuses (logged `PaymentLifecycleEventPublishFailed`) is re-sent by the outbox sweeper with the same envelope id and dedupeKey (every PAYMENT_LIFECYCLE_OUTBOX_SWEEP_INTERVAL_MS, default 30 s; backoff up to one hour; parked `dead` after 50 refusals). Envelope: `type` = the normalized event type; `actor.tenantId` = the row's tenant in a multi-tenant project. Off (the default) the generated code is byte-identical to a build without the field; the topics are listed by the kafka topic census and pre-created only while it is on. |
| `storePaymentMethod` | `Boolean` | no | `false` |  |  | An EXPLICIT opt-in (default false; only a literal `true` on an ACTIVE checkout block counts) to store the buyer's payment method while paying on this order object. It is the checkout twin of SubscriptionConfig.storePaymentMethod, for an order object that has no subscription block (a checkout-only order): either switch turns the behaviour on, and the framework reads them as ONE design-time rule (`storesPaymentMethodWhilePaying`), so the start routes, the PaymentAction enrolment, the webhook method mirror and the designer prompt cannot disagree. What it does: (1) a PaymentAction start / simple stage on the order object carries the stored-method enrolment (`storeMethod: true`) to the provider adapter (Adyen sends `storePaymentMethod: true`, Stripe `setup_future_usage: 'off_session'`), as under the subscription switch; (2) iyzico (save the card while paying on the hosted Checkout Form): the generated `PATCH /v1/start<order>payment/:orderId` and a PaymentAction start open the hosted form with the buyer's own card storage key (`sys_paymentCustomer.cardStorageKey`, read server-side from the buyer's payment-customer mapping, never from the request; none for a buyer who has no key yet), so iyzico lists the buyer's saved cards and offers to save the new one, and a card the buyer saves there is filed in the buyer's wallet (`sys_paymentMethod`) the moment the payment settles (the browser return or iyzico's Checkout Form webhook, once) through the identity owner's machine-only `attachPaymentMethodByCustomerIdForMachine`, which reads the buyer from the mapping; (3) it opens the RETENTION GATE of the webhook method mirror for the service: a provider-reported stored method (`method.attached` / `method.updated`) is filed for the user who owns the provider customer's mapping, through the same machine-only api. | `billingModel` | `BillingModel` | no |  | `reseller`, `intermediary` |  | OBJECT-level billing model of this checkout object (docs/ADR-billing-model-reseller-intermediary.md). `reseller` (al-sat): the PLATFORM is seller of record — it issues the full-amount invoice + fiscal document to the buyer and the FULL amount enters the platform's account as a plain charge, so a marketplace block on the SAME object is refused at design time (BILLING_MODEL_RESELLER_WITH_MARKETPLACE_SPLIT — a PSP split under a platform-issued full invoice is an invoice/cash mismatch); seller earnings settle platform-side via the earnings ledger + payment instructions. `intermediary` (aracilik): the SUB-MERCHANT is seller of record — the platform NEVER fiscalizes the sale, so fiscalization on the SAME object is refused (BILLING_MODEL_INTERMEDIARY_WITH_PLATFORM_FISCALIZATION); the platform's only invoice is the COMMISSION invoice to the seller, and the PSP marketplace split is the natural money path. The selector is PER OBJECT because hybrid platforms mix models across objects of one project (e.g. events=reseller on a plain account, experiences=intermediary on a marketplace account — two paymentProviders entries of the same brand with different names). Null/absent = legacy behavior: no model-pairing validation fires and emitted code is unchanged (a marketplace-bearing object without a declared model gets the BILLING_MODEL_NOT_DECLARED warning nudge). | `checkRoles` | `String`[] | no |  |  |  | Roles required on the INJECTED checkout payment routes of this object - PATCH /v1/start<x>payment/:orderId, PATCH /v1/refresh<x>payment/:orderId, PATCH /v1/checkoutrefresh<x>/:orderId, GET /v1/<x>paymentbyorderid/:orderId, GET /v1/<x>paymentbypaymentid/:paymentId and POST /v1/<x>refundpayment/:orderId (the checkout twin of SubscriptionConfig.checkRoles). Same meaning as BusinessApi authOptions.checkRoles: the list RESTRICTS (a caller holding none of these roles is refused 403 PAYMENT_ROLE_REQUIRED) and it is combined with OR. It is NOT absoluteRoles: the surface keeps its own separate BYPASS list (admin / superAdmin, PAYMENT_ABSOLUTE_ROLES), and a verified inter-service (M2M) caller that carries no user identity is admitted because the lifecycle routes are mounted allowM2M and a machine caller holds no role (an M2M caller that names a user - a forwarded user token - is that user and faces the list and the ownership gate). Login and the per-row ownership gate still run in front of and behind it. This is the way to gate the injected routes of an order object whose owner cannot be session-fed (written only by cron or internal-call apis), where the ownership gate cannot bind. A non-empty list applies unless routeAccess is `open`. The provider callback, the webhook and the mock 3-D Secure route are not gated by it. The refund route carries this gate only when refundRouteAccess is `inherit`: by default it carries the payment-operator gate instead, and `disabled` does not mount it. |
| `routeAccess` | `CheckoutRouteAccess` | no |  | `inherit`, `open` |  | What to do when checkRoles is empty. `inherit` (the default: an UNSET routeAccess means inherit) derives the injected routes' role gate from this object's authored apis (see CheckoutRouteAccess for the rule; it is the SubscriptionConfig derivation): when every human-facing authored api on the object declares checkRoles the six routes require their union, otherwise no role gate is emitted, and when the object's owner cannot be session-fed the design-time WARNING PAYMENT_CHECKOUT_ROUTES_UNGATED says so. `open` emits no role gate at all, even over a non-empty checkRoles, and states that the checkout routes are meant to stay ungated (it silences PAYMENT_CHECKOUT_ROUTES_UNGATED). Previously an unset value meant no role gate: a buyer-facing checkout that relied on that keeps it with `open`, and the design-time WARNING PAYMENT_CHECKOUT_ROUTES_GATE_INHERITED names every block whose routes the new default gates while routeAccess is still unset (writing either value silences it). |
| `refundRouteAccess` | `CheckoutRefundRouteAccess` | no | `"operator"` | `operator`, `inherit`, `disabled` |  | Who may call the injected refund route POST /v1/<x>refundpayment/:orderId (see CheckoutRefundRouteAccess). `operator` (the DEFAULT: an unset value means operator) requires a platform payment operator (superAdmin / admin / saasAdmin; in a multi-tenant project superAdmin / saasAdmin only, as it has no role named admin; or the refund-specific paymentRefundOperator PBAC grant - the shared paymentOperator grant of the payment consoles does not admit here; plus PAYMENT_ADMIN_TOKEN when set) or a verified inter-service (M2M) caller - owning the order is not enough, and checkRoles / routeAccess do not apply to this one route. `inherit` restores the earlier behaviour (the refund route shares the start / refresh gate, so the order owner can refund) and warns PAYMENT_REFUND_ROUTE_BUYER_REACHABLE when that gate is buyer-facing. `disabled` does not mount the route. Buyer-initiated refunds belong on an authored RefundAction api, where the designer's refund rules run. UPGRADE NOTE: previously the refund route was reachable by the order owner under the checkout gate; a project whose buyers or non-operator staff called it directly now gets 403 OPERATOR_REQUIRED and must move that flow to a RefundAction api, or set `inherit` explicitly (unsafe on a buyer-facing checkout). No migration rewrites existing blueprints. |

## Constraints

Property rules:

- `orderName`, `orderIdProperty` must be present. (`REQUIRED_FIELD_MISSING`)
- `onPaymentError`, `idempotencyStrategy`, `billingModel`, `routeAccess`, `refundRouteAccess` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- `providerName` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)
- `orderIdProperty`, `amountProperty`, `currencyProperty`, `orderStatusProperty`, `orderStatusUpdateDateProperty`, `orderOwnerIdProperty` must be a well-formed [`PropRefer`](./PropRefer.md) (a property of a data object). (`INVALID_PROP_REFER_FORMAT`)
- The items of `lifecycleHooks` must have distinct names (`name`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)

# LoginDefTenantSettingsConfig

**Level:** `subsection` · **Family:** [LoginDefinition](../ontology/families.md#logindefinition) (domain `ProjectAuthentication`)

**Ontology:** [LoginDefTenantSettingsConfig in Part 1](../ontology/LoginDefTenantSettingsConfig.md)

Configuration details for tenant-based access control, including tenant registration, naming, and avatar script.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `tenantRegisterIsPublic` | `Boolean` | no | `true` |  |  | If true, any user can create a tenant. If false, only SaaS admins can register tenants. When a user creates a tenant, they are automatically assigned as the tenant owner. |
| `uniqueTenantName` | `Boolean` | no | `false` |  |  | If true, two active tenants may not share the same `name`, and the owner-provisioning APIs refuse a replay instead of minting a second tenant. Default FALSE, because one person legitimately owning several tenants (and two unrelated tenants both called 'Acme') is a valid product shape and must keep working. Turn it on when the tenant name is a real identity in your product. It marks the tenant's `name` property unique, which emits a single unique database index on that column (partial on `isActive`, so a soft-deleted tenant releases its name), so the refusal is a constraint the database enforces and not a read-then-write probe two concurrent registrations can both pass; the loser gets a 409. The rule compares names EXACTLY: 'Acme', 'acme' and 'Acme Ltd' are three different tenant names to it, and so are two names differing only in interior whitespace. Note that `codename` being unique is NOT this rule: the codename is server-minted with a counter suffix ('acme' then 'acme1'), so it can never collide and therefore never refuses anything. If you also declare a `compositeIndexSettings` entry covering `name`, that composite wins and this knob ships nothing (the project validator warns). |
| `tenantName` | `String` | yes |  |  | format [lowerCamelCase](./value-formats.md#lowercamelcase) | Defines the name of the tenant object in the system (e.g., 'client', 'organization', 'workspace'). This name will be used to generate code, database models, and field references. It must start with a lowercase letter: the tenant foreign-key column every tenant-scoped object carries is synthesized as the lower-first name plus 'Id', so an upper-first value is normalized to camelCase automatically. REQUIRED whenever `useMultiTenantFeature` is on: a value that is absent, blank, whitespace-only or not a string is REFUSED at design time (`AUTH_TENANT_NAME_REQUIRED`), because a multi-tenant project with no name for its tenant model emits a tenant id column on the auth user that nothing seeds or stamps and no tenant column at all on your own objects. Turn `useMultiTenantFeature` off for a single-tenant project instead; there `tenantName` is ignored and may stay null. The tenant codename HEADER rule is a separate contract and is unchanged by that refusal, because it also serves single-tenant and not-yet-validated projects. A blank or whitespace-only value is treated as absent and the default name 'tenant' is used; surrounding whitespace is trimmed (a padded '  store  ' is 'store'), so the tenant codename header the services read is always `mbx-<tenantName>-codename` built from the trimmed name (or the `tenantNameHeaderName` override). |
| `tenantNameHeaderName` | `String` | no |  |  |  | Optional HTTP header name used to carry the tenant codename. A nonblank value overrides the default `mbx-<tenantName>-codename` header; blank or omitted values use that default. |
| `tenantAutoAvatarScript` | [`MScript`](./MScript.md) | no | `` "`https://gravatar.com/avatar/${LIB.common.md5(this.fullname… `` |  | MScript kind `code` | An MScript expression that generates a default avatar for the tenant. This is used when no avatar is provided in the request. |
| `compositeIndexSettings` | [`CompositeIndex`](./CompositeIndex.md)[] | no |  |  |  | Composite indexes for the tenant object, for a tenant identity that is a PAIR of columns rather than a single name (e.g. `name` + a declared region property). Each entry is the same { indexName, indexFields, onDuplicate } shape a DataObject's compositeIndexSettings takes, and `indexFields` may name a built-in tenant column (`name`, `codename`, `fullname`, `avatar`, `ownerId`), one of your own `tenantProperties`, or a framework column every object carries (`id`, `isActive`, `createdAt`, `updatedAt`, `_archivedAt`). A name that is none of those is REFUSED at design time, the same way a DataObject composite index refuses a column its object does not declare. MULTI-COLUMN ONLY: a composite index is named after its fields, so a single-field entry collides with the plain index that column already has and the unique constraint is never created in the database - the project validator warns about it. Express single-column uniqueness through that tenant property's `indexSettings.unique`, or through `uniqueTenantName` for the tenant name. |

## Constraints

Property rules:

- `tenantName` must be present. (`REQUIRED_FIELD_MISSING`)
- `tenantName` must be in the [`lowerCamelCase`](./value-formats.md#lowercamelcase) format. (`INVALID_CODE_NAME_FORMAT`)
- The items of `compositeIndexSettings` must have distinct names (`indexName`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)

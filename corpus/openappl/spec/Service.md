# Service

**Level:** `service` · **Family:** [Service](../ontology/families.md#service)

**Ontology:** [Service in Part 1](../ontology/Service.md)

**Name:** an instance is named by `serviceSettings.serviceBasics.name`.

Defines the overall structure and configuration for a microservice within the project. Each service acts as an independent domain that encapsulates its own data model, business logic, and interface behaviors. While services primarily manage and expose domain-specific data, this module extends beyond basic CRUD operations by offering customizable patterns, libraries, authentication, and specialized route handling. Use this module to tailor the internal and external behaviors of your service—whether it's securing endpoints, defining edge routes, managing complex data objects, or integrating advanced logic. The service configuration ensures the resulting microservice is robust, secure, and aligned with the specific application requirements.

| `computeJobs` | [`ComputeJob`](./ComputeJob.md)[] | no |  |  |  | Compute workloads hosted by this service (docs/ADR-calculation-layer.md §2/§3). Each `ComputeJob` is a long, business-shaped unit of work (batch-transform, ai-inference, media-processing, …) generated as an async, queued, observable, cancellable, retryable job: a submit Business API enqueues it and returns a jobId, a compute-worker controller drains the queue and runs it on the bounded compute pool, and it produces a result plus bucket-backed artifacts and a completion event. The recommended shape for any non-trivial computation. Only valid on rust/python host services (the calculation languages); a non-compute service (Node/Java/…) submits jobs to a compute service over M2M instead of hosting them (§7). |
| `eventStreams` | [`EventStream`](./EventStream.md)[] | no |  |  |  | High-throughput ingest→hot/cold/analytics pipelines hosted by this service. Each `EventStream` is the headline asset of the big-load pattern family: a single chapter that folds the ingestion write contract, the hot-store binding (write-optimized current-state + last-N + TTL), and the read surfaces as sections — composing the existing kafka/compute/realtime layers rather than forking them (the way `ComputeJob` folds its spec/input/result sections). Its hotStore / coldSink / analytics bindings reference a `projectSettings.bigLoadProvidersSettings` store BY NAME. The generated big-load-layer keeps the write path thin (a fast async batched insert — NEVER heavy per-row work) so the ingest layer absorbs far more than a synchronous CRUD endpoint. coldSink/analytics/retention/cleaningPipeline sections are defined in the schema but wired in later phases (P4+). |
| `jobStreams` | [`JobStream`](./JobStream.md)[] | no |  |  |  | Async job-orchestration streams hosted by this service (docs/ADR-async-job-orchestration-patterns.md). Each `JobStream` is a durable, reconnectable, observable async BUSINESS job that generalizes `ComputeJob`: the 'work' is a target `businessLogic[]` BusinessApi invocation (not a native compute kernel). From one declaration codegen emits an enqueue edge, a kafka WORKER controller on the job topic that drives the target API, a durable per-job event outbox, and a reconnectable SSE observation edge keyed by jobId — and it SUPPRESSES the target BusinessApi's public REST route (internal by default; `targetApi.keepPublicRoute` re-exposes it). deliveryMode is push; the lifecycle is queued→started→[relayed progress]→ended with a terminal result link. The sibling pull/admission-control pattern (`WaitingRoom`) is a separate asset in the same ADR. |
| `waitingRooms` | [`WaitingRoom`](./WaitingRoom.md)[] | no |  |  |  | Pull-mode admission-control queues hosted by this service (docs/ADR-async-job-orchestration-patterns.md, the WaitingRoom section). Each `WaitingRoom` is the Taylor-Swift-ticketing turnstile: it meters a thundering herd through N gated Redis rooms into a bound PUBLIC `businessLogic[]` BusinessApi so the target is never stampeded. From one declaration codegen emits a join edge (ZADD into the entry room), a metered cron-promoter advancing front-of-room → next room → final admission at each room's admissionRatePerSecond, the room's own realtime position channel, and a one-shot time-boxed `QueToken` minted on admission. CONTRAST jobStreams (push, which HIDES the target): a WaitingRoom does NOT proxy or suppress the target — the target keeps its public route and gains the `authOptions.queueTokenRequired` gate, and the client calls it DIRECTLY with the minted token. The sibling push/async-job pattern (`JobStream`) is a separate asset in the same ADR. |
| `loadShield` | [`LoadShield`](./LoadShield.md) | no |  |  |  | The service's single in-process priority load shedder (docs/ADR-loadshield-priority-load-shedding.md) — an optional SINGULAR chapter (at most one per service: the shield guards the whole dispatch plane over one shared DB pool, so two shields would fight over the same concurrency budget). Declares the per-API/action shed-priority tiers (integer 0-5, 0 = never shed, 5 = first to shed; unassigned routes get derived defaults by action nature), the CoDel-style `targetQueueLatencyMs` setpoint, an `enabled` flag, and exemptions. CONTRAST `waitingRooms[]`: a waiting room is an opt-in, client-visible PULL queue in front of ONE known-stampede API for a PLANNED spike; the loadShield is the always-on, invisible-until-triggered guard for the WHOLE service against UNPLANNED overload — they compose. `eventStream` ingest keeps its own declared shedding and is structurally exempt. Null/absent = the service dispatches unshielded, exactly as today. Declaring the chapter emits the nodejs runtime: a bounded priority queue + concurrency cap in front of route dispatch with immediate DB-free 429 LOAD_SHED rejection, plus the ADAPTIVE layer — a PID-driven rejection threshold on the tier×cohort scale and an AIMD auto-tuned concurrency cap, both fed by the shared DB-saturation signal and degrading to the static behavior when no relational signal exists. Controller gains are internal platform constants (never blueprint); `LOADSHIELD_DISABLED` / `LOADSHIELD_ADAPTIVE_DISABLED` are the runtime ops kill-switches, and `LOADSHIELD_COHORT_ROTATION_SECONDS` tunes the time-rotating cohort salt (default 3600, 0 = fixed pre-rotation mapping). |
| `seedData` | [`SeedData`](./SeedData.md)[] | no |  |  |  | Declarative seed-data records upserted into the service's DataObjects at startup (after migrations). Each `SeedData` entry is `{ seedBasics, values }` — `seedBasics` names the target `dataObject`, the `matchBy` idempotency key and the `insertOnly` names, and `values` is the map (property → MScript) for the row to insert-if-absent / refresh-if-present. The generator emits a `seed-data` BootstrapModule that runs once on boot via the db-layer. Replaces hand-written init routines (super-admin / root-tenant / admin-group bootstrap); reusable by any custom service that needs initial system records. A data object may carry MULTIPLE seed rows (e.g. three subscription plans): each entry upserts independently, keyed by its `matchBy` values — just make sure every row of the same object has a matchBy key whose seeded values differ (validation rejects rows that collapse onto the same matchBy identity with SEED_ROW_NOT_DISTINGUISHABLE). Item addressing: each row persists in its own storage slot keyed by its matchBy identity, and the item-addressed `seedData/{<dataObject>}` path resolves the object's FULL ROW SET — the row itself when one row is stored, an array of rows when several are; a row's own `id` addresses one exact row. |
| `oauthFlows` | [`OAuthFlow`](./OAuthFlow.md)[] | no |  |  |  | Declarative OAuth redirect flows hosted by this service. Each `OAuthFlow` exposes its own REST start (redirect to the provider) + callback (token exchange → normalized profile) route, backed by the config-driven common OAuth runtime. On the auth service the callback completes the login (find-or-register + mint session); every flow also publishes its `completeKafkaTopic` completion event so other services can react. Replaces the hand-written social-login router. |
| `graphLayer` | [`GraphServiceLayer`](./GraphServiceLayer.md) | no |  |  |  | The service's graph-database surface (docs/ADR-graph-database-layer.md §4c/§8/§9) — a single namespaced block so the graph collections don't clutter the Service top level. Holds the service's standalone `GraphEdge`s, declarative `GraphQuery`s, and composite `HierarchicalResourceGraph` resources. Null/absent when the service declares none. (DataObject node projections live on `objectSettings.graphProjection`; graph providers live on `projectSettings.graphProvidersSettings`.) |
| `serviceFiles` | [`ServiceFiles`](./ServiceFiles.md) | no |  |  |  | Design-time static files that ride in the generated service repo (an optional singular chapter, `ServiceFiles`). Each file is uploaded once with the `uploadServiceFile` tool, which stores the bytes in the platform bucket and writes one manifest entry `{path, visibility, contentType, size, sha256}` here; the build fetches and verifies the bytes and writes them to `service-files/public/<path>` or `service-files/private/<path>` in the repo. On a nodejs, dotnet, java, rust or python service a public file is served at `GET <serviceBaseUrl>/service-files/<path>`, and every file (public or private) is read from custom code and MScript with the synchronous `LIB.serviceFiles.text(path)` / `.json(path)` / `.bytes(path)` / `.info(path)` / `.has(path)` accessor, for example `AddToContextAction` with value `LIB.serviceFiles.text('legal/terms-v3.md')`. Other languages get the files in the repo; their route and accessor follow with each language port. A private file is NOT secret: anyone who can read the service repo, a preview or a runner image can read it, so never put credentials in one; use secrets or custom variables. Limits: 10 MB per file, 100 MB for all service files of the project. Null/absent when the service carries no files. |
| `cronJobs` | [`CronJob`](./CronJob.md)[] | no |  |  |  | Scheduled jobs of this service (`CronJob[]`). Each cron job (`{ jobBasics, scheduleSettings }`) calls one function of the service library (`jobBasics.libFunction`, a `library.functions` module) on a cron schedule, with no Business API in between. The generated runtime claims every tick in the service database (table `sys_cronJobRun`, unique on job name and tick), so exactly one replica runs each tick and no Redis is needed; it records every run (status, timings, a masked and capped error), enforces a timeout, and serves an admin surface (`GET /cron-jobs`, `GET /cron-jobs/:name/runs`, `POST /cron-jobs/:name/run`). `scheduleSettings.runMode` makes a job run on every tick (`always`), succeed only once ever (`onceEver`, the urgent data-migration tool), or succeed once per start era of the service (`oncePerStart`). Use a cron job for scheduled work that is plain code; use a Business API cron controller (`BusinessApi.cronSettings`) when the scheduled work should run through an API's parameters, actions, workflow and events. Emitted by the nodejs, rust and python runtimes: a service whose language is known to be another one is refused (CRON_JOBS_LANGUAGE_NOT_PORTED), and rust and python need a relational service: on a mongodb service of those languages a declared job is refused (CRON_JOBS_MONGODB_UNSUPPORTED). A service without cron jobs emits exactly what it emitted before this pattern existed. |

# SellerOnboardingConfig

**Level:** `subsection` · **Family:** [ObjectSettings](../ontology/families.md#objectsettings) (domain `DataObject`)

**Ontology:** [SellerOnboardingConfig in Part 1](../ontology/SellerOnboardingConfig.md)

Role-to-property map that lets the FRAMEWORK PROVISION a seller's connected sub-merchant account (level 2), instead of a designer hand-pasting a provider-side key into `sellerAccountProperty`. `sellerAccountProperty` says where the minted account id LIVES; this block says where the facts it is minted FROM come from. Every entry is a PropRefer naming a property OF THE OWNING DATA OBJECT - the same object `sellerAccountProperty` resolves against, exactly like FiscalPartyConfig's party bindings - so the SELLER-BEARING object is the object that carries the marketplace block; a separate seller/profile object carries its OWN marketplace block rather than being reached through a relation (PropRefer has no cross-object resolution, and inventing one here would make the money bindings and the identity bindings resolve against different rows), and the order objects that charge to it name it in their own marketplace block's sellerAccountObject instead of declaring this block. The blueprint speaks ROLES; the payment adapters speak provider WIRE FIELDS (iyzico subMerchantType / legalCompanyTitle / gsmNumber, Stripe business_type, ...) and translate at the edge - no provider-specific field name may ever appear in this block. WHEN THE DATA IS COLLECTED: the PRODUCT owns the form and the FRAMEWORK owns the requirements. A seller signup screen, an admin back-office edit or an import writes these properties through the object's ordinary CRUD, long before any provisioning call; provisioning reads them off the persisted row. WHEN NOT TO DECLARE THIS BLOCK AT ALL: a HOSTED-onboarding provider (kycOnboarding mode hosted-url / partner-referrals - Stripe Connect onboarding, PayPal partner referrals) collects the seller's legal identity on ITS OWN pages, so the platform never holds these facts and the block stays null; declare it for the API-onboarding brands (iyzico sub-merchant, Mangopay document-api) whose account is minted from a payload the platform assembles. Absent/null = no provisioning declaration: no finding is raised and emitted code is byte-identical to a blueprint without this block.

## Properties

| `legalNameProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property of the owning object holding the seller's LEGAL name - the registered company title for a company seller, the trading name for a sole proprietor. Adapters map it onto their own slots (iyzico: `name` plus `legalCompanyTitle`; Stripe: the company / individual naming fields). The API-onboarding brands require a name for every seller type. |
| `taxIdProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property of the owning object holding the seller's CORPORATE tax number (Turkey: VKN). This is the COMPANY-tier identifier; an individual or sole proprietor is identified by `identityNumberProperty` instead, so a platform whose allowedSellerTypes admits both tiers binds BOTH roles. |
| `taxOfficeProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property of the owning object holding the tax office (Turkey: vergi dairesi) the seller's tax number is registered with. A company-tier fact: brands that mint an account from a payload require it alongside the tax id. |
| `addressProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property of the owning object holding the seller's address as a single text value. iyzico requires it for EVERY sub-merchant type - proven by the MasaV6 sandbox probe, not inferred from the vendor docs. |
| `ibanProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property of the owning object holding the seller's settlement IBAN. This role gates SETTLEMENT, NOT REGISTRATION: an account is created without it, but a SETTLEABLE sub-merchant needs it - approving a settlement for an IBAN-less sub-merchant is refused by the vendor (iyzico error 5068) and surfaces as a typed 422 naming this field (proven live 2026-09-08). Bind it whenever the platform pays sellers out; leave it null only for a marketplace that never settles through the PSP. Because it is not a registration requirement, an unmapped iban is never reported by the allowedSellerTypes coverage check. |
| `identityNumberProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property of the owning object holding the seller's NATIONAL identity number (Turkey: TCKN). The INDIVIDUAL-tier identifier: required for a PERSONAL seller, and also for the sole-proprietorship tier (iyzico PRIVATE_COMPANY) whose owner is the taxable person. |
| `contactNameProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property of the owning object holding the contact person's given name. Required for the individual seller tier - the API-onboarding brands refuse a PERSONAL account without both contact name and surname. |
| `contactSurnameProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property of the owning object holding the contact person's family name. The twin of `contactNameProperty`; bind both or neither. |
| `sellerTypeProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property of the owning object holding the seller's LEGAL FORM, written in the bound brand's own sub-merchant vocabulary - the SAME vocabulary `allowedSellerTypes` uses (iyzico: PERSONAL / PRIVATE_COMPANY / LIMITED_OR_JOINT_STOCK_COMPANY, input alias LIMITED_COMPANY; stripe: individual / company). It is the row-level fact the per-type mandatory-role matrix is selected BY, so a platform whose `allowedSellerTypes` admits MORE THAN ONE form MUST bind it - otherwise no row can say which form a given seller is, and design time reports MARKETPLACE_SELLER_TYPE_BINDING_UNMAPPED. A single-form policy may leave it null: the one admitted form is implied. |
| `emailProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property of the owning object holding the seller's contact e-mail. The API-onboarding brands require it for every seller type, and it is the address the provider sends onboarding / KYC correspondence to. |
| `gsmProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property of the owning object holding the seller's mobile phone number in the vendor's expected format (iyzico wire field `gsmNumber`). Vendor-OPTIONAL at registration - bind it when the platform already collects it, not to satisfy a requirement. |

## Constraints

Property rules:

- `legalNameProperty`, `taxIdProperty`, `taxOfficeProperty`, `addressProperty`, `ibanProperty`, `identityNumberProperty`, `contactNameProperty`, `contactSurnameProperty`, `sellerTypeProperty`, `emailProperty`, `gsmProperty` must be a well-formed [`PropRefer`](./PropRefer.md) (a property of a data object). (`INVALID_PROP_REFER_FORMAT`)

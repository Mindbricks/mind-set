# LifecycleHook

**Level:** `subsection` · **Family:** [ObjectSettings](../ontology/families.md#objectsettings) (domain `DataObject`)

**Ontology:** [LifecycleHook in Part 1](../ontology/LifecycleHook.md)

**Name:** an instance is named by `name`.

A designer-authored MScript handler fired by the payment dispatcher when a normalized payment event advances the state machine. Hooks replace the legacy edge-function-driven post-payment plumbing — instead of writing a Kafka edge controller plus an edgeFunction, the designer writes the trigger + script inline. The dispatcher invokes hooks after the FSM transition completes and the state has been persisted; failures inside a hook DO NOT roll back the state transition and DO NOT fail the dispatch — they are logged loudly as PaymentLifecycleHookFailed (hook name, trigger, event id, error) and the event still settles processed, so the hook's effect is operator-reconcilable from the log. An internal API call made from a hook (await API.<name>(...)) that answers a non-2xx now raises a typed ApiError instead of resolving the error envelope as data, so a refused call lands in that same log instead of vanishing.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `name` | `String` | yes |  |  | format [codeName](./value-formats.md#codename) | Unique name of this hook within its parent config (CheckoutConfig / SubscriptionConfig / MarketplaceConfig). Used in logs and the events table. |
| `trigger` | `PaymentLifecycleTrigger` | yes |  | 24 values, see [PaymentLifecycleTrigger](#paymentlifecycletrigger) |  | Which lifecycle event fires this hook. The framework normalizes provider-specific events into the PaymentLifecycleTrigger enum before dispatching. The trigger also fixes which fields `resource` carries in the script/condition (single source: the Normalized* interfaces in the generated `src/common/payment-providers/types.ts`; a read the interface does not declare is rejected at design time — LIFECYCLE_HOOK_UNKNOWN_RESOURCE_FIELD). Each trigger delivers EXACTLY ONE of those interfaces and the generated hook branch casts `resource` to it, so a field belonging to a different trigger's arm does not compile — `orderId` is readable on afterPaymentCaptured and not on afterPaymentRefunded, `providerRefundId` the other way round, `paidAt` on afterInvoicePaid / afterInvoicePaymentFailed and not on the other subscription triggers. Per trigger family: afterPaymentCaptured / afterPaymentFailed / afterPaymentCanceled / afterPaymentStarted / afterPaymentAmountMismatch / afterPaymentCapturedAfterCancel → NormalizedIntent → providerIntentId, providerStatus, statusLiteral, amount, currency, providerSurcharge, customerId, paymentMethodId, description, orderId, metadata, failureReason, settlementItems, nextAction; afterPaymentRefunded / afterRefundFailed → NormalizedRefund → providerRefundId, providerIntentId, statusLiteral, amount, currency, reason, failureReason, metadata; afterDisputeOpened / afterPaymentDisputed / afterDisputeEvidenceRequired / afterDisputeWon / afterDisputeLost → NormalizedDispute → providerDisputeId, providerIntentId, amount, currency, reason, statusLiteral, evidenceDueBy, evidenceSubmittedAt, outcome; afterSubscriptionCreated / afterSubscriptionRenewed / afterSubscriptionPaymentFailed / afterSubscriptionPastDue / afterSubscriptionCanceled → NormalizedSubscription → providerSubscriptionId, customerId, planId, statusLiteral, failureReason, currentPeriodStart, currentPeriodEnd, cancelAtPeriodEnd, trialEnd, canceledAt, metadata, nextAction; afterInvoicePaid / afterInvoicePaymentFailed → NormalizedInvoice → providerInvoiceId, subscriptionId, amount, currency, statusLiteral, failureReason, billingReason, periodStart, periodEnd, paidAt, hostedInvoiceUrl, requiresAction; afterPayoutPaid / afterPayoutFailed / afterPayoutHeld → NormalizedPayout → providerPayoutId, destinationAccountId, amount, currency, statusLiteral, scheduledFor, arrivedAt, failureReason, transferGroup; afterKycUpdated → NormalizedConnectedAccount → providerAccountId, kycStatus, payoutEnabled, country, email, businessName, metadata. The normalized resource never has an `id` field: the provider-side id is the `provider…Id` member, and the stored row's own id is on the loaded row (`payment.id` / `subscription.id` / `payout.id`). The trigger must belong to the family of the hook list it sits in - CheckoutConfig: the payment, refund and dispute triggers; SubscriptionConfig: the subscription and invoice triggers; MarketplaceConfig: the payout triggers and afterKycUpdated - because no other lifecycle ever receives that event: a payout trigger in a checkout hook list would never fire and its `resource` would be typed for the payment machine, so it is rejected at design time (LIFECYCLE_HOOK_TRIGGER_WRONG_FAMILY). |
| `description` | `Text` | no |  |  |  | Human-readable explanation of what this hook does. |
| `condition` | [`MScript`](./MScript.md) | no |  |  | MScript kind `code` | Optional MScript boolean — when present and falsy, the hook is skipped for this event. Use this for fine-grained filtering (e.g. only fire on certain amounts or certain payment methods). It sees the same names as `script` (`event`, `resource`, and the row names of the owning config), bare. `this` is the generated `_hookCtx` context object, NOT the row: `this.amount` reads `undefined`, so the condition is falsy and the hook never runs - write `resource.amount > 0`. Validation warns on a `this.<name>` that is not a context key of the machine the trigger runs in and that no hook of the config assigns (LIFECYCLE_HOOK_THIS_NOT_IN_CONTEXT). |
| `script` | [`MScript`](./MScript.md) | yes |  |  | MScript kind `code` | MScript executed when the trigger fires. Like every MScript it is ONE expression, not a statement list: to run two calls in sequence, wrap them in an inline async IIFE - `(async () => { await API.reserveSeats({ bookingId: resource.orderId }); await API.issueReceipt({ bookingId: resource.orderId }); })()`. A bare `a; b` sequence is refused at validation (INVALID_MSCRIPT_SYNTAX): the generated handler wraps the script in parentheses, where it cannot compile. The script is placed inside the generated lifecycle handler, so the names below are plain bare identifiers: write `payment.id`, not `this.payment.id`. Every trigger gets the normalized event payload (`event`) and the normalized resource that event carries (`resource`) — provider ids and amounts live on the RESOURCE (`resource.providerIntentId`), not on the event. The row this service loaded is named for WHICH row it is, and that depends on the owning config: checkout triggers (payment, refund and dispute) get `payment`, the sys_<X>Payment ticket, with `order` kept as a deprecated alias of it; subscription triggers get `subscription`; marketplace triggers get `payout`. On a dispute trigger the sys_<X>Dispute row is reached as `this.dispute`, because the same checkout hook list is also emitted into the payment handler where that name does not exist. A row can be null (an `account.*` payout event, a dispute on an intent this service does not own), so guard it. `resource.metadata` values are `unknown`: a value is whatever the provider or the framework stored there, not necessarily a string. A read below `resource.metadata` compiles (`resource.metadata.lateCapture.orderId`, `resource.metadata?.amountMismatch?.expected`): the nodejs hook types `metadata` as `Record<string, any>`, and the java and dotnet hooks read members dynamically; a missing level reads null / undefined, so guard it. Nothing checks a value's type, so narrow a metadata value before passing it on, with `typeof x === 'string'` or `String(x)`: a truthiness guard does not make it a string. Write `typeof resource.metadata?.bookingId === 'string' && f(resource.metadata.bookingId)` or `f(String(resource.metadata?.bookingId ?? ''))`, not `resource.metadata?.bookingId && f(resource.metadata.bookingId)`. There is no request, session or user: a hook runs from a provider webhook, not from a call. Service library helpers are reached as `LIB.<module>(...)`, other rows through the generated dbLayer getters. Same-service Business APIs that declare `internalCallSettings.hasInternalCallController` are reached as `await API.<apiName>({ ...params })` — awaitable, runs the API's full manager pipeline asSystem, and resolves to the API's response resource. On nodejs, java and dotnet the optional second argument `API.<apiName>(params, { session: this.session })` carries a session explicitly when the hook has one and wants the caller's tenant (required for ledger APIs on a tenant-scoped owner object). Provider webhook hooks have no caller session and keep their explicit-param calls. Omitting the argument leaves the session null, with no inheritance through AsyncLocalStorage or the running manager; language targets without explicit-session support retain the sessionless signature; only internal-controller APIs are members of `API`, and the called API's own hooks may run but cannot make further `API.*` calls (depth is limited to one). Use hooks to fan out to other services (publish kafka events), invoke internal APIs, update related records, or run application-side bookkeeping.  The design-time checks over this script — unknown `resource` field, undefined `this.<X>`, unbound `API.<apiName>`, `LIB.<module>` existence, and the case-mismatch report — are STATIC and read the syntax you wrote. A field read on `event` or `resource` is seen as a direct member (`resource.x`, `resource?.x`, `this.resource.x`), a string-literal key (`resource['x']`), a key destructured off the root (`const { x } = resource`, also as an inline IIFE parameter pattern) and through ONE alias level (`const r = resource`, `((r) => r.x)(resource)`); each keeps the tier of the root it came from (bare = build break, ERROR; through `this.` = silent `undefined`, WARNING). A field another hook assigns onto the shared context excuses a read only when that hook runs in the SAME fire and comes EARLIER in the list: the same trigger, or the dispute alias pair `afterDisputeOpened` / `afterPaymentDisputed`, which both fire on `dispute.opened` over one context. Hooks of one fire run in list order; any other trigger fires on a different event and never shares the context. The checks are still blind to anything whose name is not literally in the source: a computed member (`this[key]`, `API[name]`, `LIB.mod[fn]`), a name reached through a spread or rest element (`{ ...payment }`), a key built at runtime, a `let` alias, an alias of an alias, a root renamed while destructuring `this` (`const { resource: r } = this`), a `this` rebound by a nested non-arrow `function`, and a root handed to any function other than an inline IIFE. Names are resolved by scope: a parameter or local that reuses the root's or an alias's name is that local, not the root. Lexical identity is respected in parameter defaults, switch discriminants, named classes and static blocks; this is not general dataflow analysis. Silence on such a read means NOT CHECKED, not checked-and-clean — and a TypeScript-annotated body skips the AST passes altogether. Spell member reads out literally if you want the checker to see them. |

## Allowed values

### PaymentLifecycleTrigger

`afterPaymentCaptured`, `afterPaymentFailed`, `afterPaymentCanceled`, `afterPaymentRefunded`, `afterRefundFailed`, `afterPaymentDisputed`, `afterPaymentStarted`, `afterPaymentAmountMismatch`, `afterPaymentCapturedAfterCancel`, `afterSubscriptionCreated`, `afterSubscriptionRenewed`, `afterSubscriptionPaymentFailed`, `afterSubscriptionCanceled`, `afterSubscriptionPastDue`, `afterInvoicePaid`, `afterInvoicePaymentFailed`, `afterDisputeOpened`, `afterDisputeEvidenceRequired`, `afterDisputeWon`, `afterDisputeLost`, `afterPayoutPaid`, `afterPayoutFailed`, `afterPayoutHeld`, `afterKycUpdated`

## Constraints

Property rules:

- `name`, `trigger`, `script` must be present. (`REQUIRED_FIELD_MISSING`)
- `trigger` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- `name` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)

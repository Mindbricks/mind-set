# MarketplaceConfig

**Level:** `subsection` · **Family:** [ObjectSettings](../ontology/families.md#objectsettings) (domain `DataObject`)

**Ontology:** [MarketplaceConfig in Part 1](../ontology/MarketplaceConfig.md)

Configuration for marketplace payouts on a DataObject. Provider-binding via `providerName`. Requires the bound provider to have capabilities.supportsMarketplace=true. In a multi-tenant project the seller-bearing object must be tenant-level (objectSettings.authorization.objectDataIsInTenantLevel: true); non-tenant sellers are refused at blueprint validation with MARKETPLACE_SELLER_NOT_TENANT_LEVEL before any PSP create call, whether onboarding is hosted or manual. Maps the object's seller-account / amount / fee properties onto the provider's marketplace primitives (Stripe Connect transfers, PayPal Hyperwallet, iyzico sub-merchant, Adyen MarketPay, Mangopay wallets).

| `settlementRelease` | [`SettlementReleaseConfig`](./SettlementReleaseConfig.md) | no |  |  |  | Optional settlement-RELEASE timing for a providerSplit marketplace object: WHEN the seller's split share of each captured sale is released to the seller. Today a split share is released only when a payout is created; with this block the framework books ONE payout row per captured sale at capture time (payment.captured), with the provider's settlement item ids of that sale persisted on it (iyzico: the split items' paymentTransactionIds, under the provider-neutral metadata.providerItemIds), and releases it on the declared condition: `onCapture` releases at once (the next scheduler tick sends it), `onDate` holds it until now >= the sale row's `releaseAtProperty` (e.g. the experience end date), `onStatus` holds it until the sale row's `statusProperty` reads one of `releaseOnStatus`, `manual` holds it until a payout is created for that sale (POST /v1/payments/payouts or a PayoutAction naming the sale by metadata.orderId / sourceOrderProperty). The SALE is re-checked before every release (per tick and under the scheduler claim), from the payment layer's own ticket and dispute records: a fully refunded or canceled sale or a lost dispute cancels the row (statusLiteral failed, metadata.settlementRelease.canceledReason sale_refunded / sale_canceled / dispute_lost, no provider call, afterPayoutFailed fires); an open dispute holds it (holdReason dispute_open) until the dispute is won; a partially refunded sale holds it (holdReason sale_partially_refunded) until an operator creates a payout for the sale. REQUIREMENTS (validation ERRORS): settlementMode providerSplit (platformSettled has no PSP payouts), a framework-driven payoutCadence on the bound provider (`on_demand` or `scheduled`; the stripe / iyzico / adyen default `provider_driven` books no payout - set paymentProviders[].payoutCadence.mode), `releaseAtProperty` for onDate and `statusProperty` + `releaseOnStatus` for onStatus, each naming a property of THIS object; and a Node.js, .NET, Java, Rust or Python service - the other backend languages do not emit the release yet and refuse the block (SETTLEMENT_RELEASE_LANGUAGE_UNSUPPORTED). PROVIDER PREREQUISITE (iyzico): the merchant account must NOT auto-approve split items - ask iyzico to switch the account's automatic item approval off; with auto-approval on, iyzico releases the seller share itself and no hold can apply. Replaces the authored-cron workaround (on_demand cadence + a cron that creates a payout per ended sale). Null / absent = today's behavior; emitted code is byte-identical to a blueprint without this block. |

| `settlementGate` | [`SettlementGateConfig`](./SettlementGateConfig.md) | no |  |  |  | Optional invoice gate on the APPROVE step of platformSettled settlement instructions (the reseller mutabakat step: the platform pays the seller only against the seller's incoming invoice). ## Constraints

Property rules:

- `settlementMode` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- `providerName` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)
- `sellerAccountProperty`, `amountProperty`, `applicationFeeProperty`, `currencyProperty`, `transferGroupProperty`, `settlementGroupProperty`, `settlementEligibleAfterProperty` must be a well-formed [`PropRefer`](./PropRefer.md) (a property of a data object). (`INVALID_PROP_REFER_FORMAT`)
- `sellerAccountObject` must be a well-formed [`LocalDataObjectName`](./LocalDataObjectName.md) (a data object of the same service). (`INVALID_LOCAL_DATA_OBJECT_NAME_FORMAT`)
- The items of `lifecycleHooks` must have distinct names (`name`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)

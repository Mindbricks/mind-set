# AgentKafkaController

**Level:** `section` · **Family:** [AIAgent](../ontology/families.md#aiagent) (domain `Service`)

**Ontology:** [AgentKafkaController in Part 1](../ontology/AgentKafkaController.md)

**Name:** an instance is named by `name`.

Defines a Kafka-triggered controller for the AI agent. When enabled, a KafkaListener is created that subscribes to the specified topic. Incoming messages are mapped to the agent's request format using the dataMapping expression, then the agent is executed under a minted SYSTEM session (roleId 'system', userId 'system:kafka:<agent>.<controller>', in the event's tenant). The event author (the envelope actor) is never the run's session and the run is not charged to the author's dailyTokenBudgetPerUser; the author is kept as onBehalfOf data (guardrails.inputValidation this.onBehalfOf, tool handlers' ctx.onBehalfOf, request.onBehalfOf). A controller can decline events that are not its own - an optional condition that evaluates falsy, or a declared dataMapping that returns null - and a declined event is skipped (no run, no retry, no dead-letter). Optionally, the agent's response can be published to a response topic. Multiple controllers can be defined per agent for different topics with different data mappings.

| `name` | `String` | yes |  |  | format [codeName](./value-formats.md#codename) | Unique identifier for this Kafka controller within the agent. Used in generated code and log correlation. Must be camelCase. For services resolved to Java, authored Kafka listener names and group IDs are limited to 249 Unicode code points; longer values are refused at design time before Spring listener startup. This Java-specific bound does not refuse other service languages or unresolved contexts. |
| `topic` | `String` | yes |  |  |  | Kafka topic to subscribe to, written as the full topic name. When a message arrives on this topic, the agent is executed with the mapped data. There is no alias syntax: a string such as 'order.created' is subscribed under exactly that name, and validation warns KAFKA_TOPIC_UNKNOWN_PRODUCER when nothing in the project publishes it. The only rewrite is the project scope: a topic a PublishEventAction of this project authors, or a framework topic of this project written without its `<projectCodename>-` prefix, is consumed under the prefixed wire name. `getKafkaEventTopicsOfService` lists the exact names. |
| `groupId` | `String` | no |  |  |  | Optional Kafka consumer group ID. If not specified, a default group ID is generated from the service codename and controller name. Use a custom group ID for shared consumption across service instances. For services resolved to Java, authored Kafka listener names and group IDs are limited to 249 Unicode code points; longer values are refused at design time before Spring listener startup. This Java-specific bound does not refuse other service languages or unresolved contexts. |
| `condition` | [`MScript`](./MScript.md) | no |  |  | MScript kind `code` | Optional MScript predicate that decides whether this controller handles an incoming event at all. It is evaluated for every message BEFORE the dataMapping and BEFORE any agent run, with the same four bindings as dataMapping: 'message' (the WHOLE raw wire message - the unified event envelope, so read the payload as message.data.field), 'session', 'topic' and 'headers'; the inline-function form '(message, session, topic, headers) => ...' is invoked with them positionally. A truthy result runs the controller exactly as if no condition were declared. A falsy result DECLINES the event: the dataMapping is not evaluated, no agent run starts (no sys_agentExecutions row), nothing is retried or published to the dead-letter topic, the event is marked processed for dedup, and an info-level AgentKafkaEventSkipped log with reason 'condition' is written. Use it on a shared topic where only some events belong to this agent (e.g. message.data.contentType === 'invoice'). Must be a single synchronous expression: an async function form is refused at validation (AGENT_KAFKA_CONDITION_ASYNC), and a condition that returns a Promise at runtime throws instead of being read as truthy. An authored literal source counts as declared - `null` or `false` declines every event, only an untouched (all-null) slot means no condition. A condition that THROWS is an error of the controller (logged by the Kafka listener, the event is not marked processed), not a decline. Null = every event is handled. A guardrails.inputValidation refusal is NOT a decline: it still fails the run (once, without retries) and dead-letters it. |
| `dataMapping` | [`MScript`](./MScript.md) | no |  |  | MScript kind `code` | MScript expression that transforms the incoming Kafka message into the agent's request body. Has access to 'message' (parsed JSON payload), 'session' (the minted SYSTEM session the run executes under: roleId 'system', userId 'system:kafka:<agent>.<controller>', the event's tenant; the event author is message.actor and reaches the agent as onBehalfOf, never as the session), 'topic' (topic name), and 'headers' (Kafka message headers). Should return an object matching the agent's expected input shape (e.g., { message: message.text, context: message.metadata }). A declared mapping (any authored source, the literal `null` included) whose RESULT is null or undefined DECLINES the event: the agent is not run, nothing is retried or dead-lettered, the event is marked processed and an info-level AgentKafkaEventSkipped log (reason 'dataMapping') is written - so 'return null' is the way a mapping says 'this event is not mine'. An object result with at least one field, EVERY field undefined (the shape an unconditional mapping produces when the envelope does not carry the fields it reads; JSON drops undefined keys, so it would reach the agent as an empty input), also declines on the Node.js service target, under its own reason 'dataMappingEmpty' with the undefined field names in the skip log's emptyFields - that is how a malformed or foreign envelope stays distinguishable from a deliberate filter (reason 'dataMapping'). A field set to null, a literal {} and an array are bodies and run. When the dataMapping PROPERTY itself is left null (not authored), NO mapping runs and the listener forwards the envelope's payload — `message.data ?? message` — as the request body, so an UNMAPPED controller's input fields are addressed BARE (read scope 'record'), exactly opposite to the mapped form described next. IMPORTANT — a declared dataMapping is read scope 'envelope': it is the one built-in Kafka consumer the framework does NOT unwrap for you, because the MScript is evaluated over the WHOLE raw wire message. And EVERY framework-raised event is a unified ENVELOPE — db-level, API-level AND explicit PublishEventAction messages alike, since ServicePublisher wraps its `data` argument unconditionally with no kind-dependent branch: `{ id, type, source, time, requestId, actor, data, old? }`, where `data` is `{ _type, ...record }` for a db/API event and the authored message object for a PublishEventAction topic. The payload ALWAYS rides under `data` — map fields as `message.data.field` (e.g. `message.data.status`), never from the envelope root (`message.type` is the domain fact like `user.created`, not your object's field); the pre-change row of an update is under `message.old`. Do NOT carry this `data.` prefix to other consumer surfaces: an EventNotification `targetPathInData` and a Kafka-triggered BusinessApi's `requestParameters[].dataPath` are read scope 'record' — the framework unwrapped `event.data` for them — and must use the bare key. Events carry no session and no HTTP status — `message.actor.userId` is the minimal identity. Use the `getKafkaEventPayloadStructure` tool to see the exact per-topic shape. IMPORTANT — the mapping must be a SINGLE EXPRESSION: statement sequences like 'if (…) { return {…}; } return null;' do not compile in the generated listener. For conditional logic use an inline function — '() => { if (…) { return {…}; } return null; }' or '(message, session, topic, headers) => ({ … })' — which the Node.js service target invokes with (message, session, topic, headers); unannotated function parameters are auto-annotated ': any' at codegen so both forms compile under the generated service's strict tsconfig (other language targets are being brought to inline-function parity). On the Node.js service target, a Promise or thenable mapping result is awaited before decline checks and before the request body reaches the agent. Async inline-function forms and bare API calls can return the body asynchronously. Top-level 'await' remains unsupported; place it inside an async function expression. A rejected mapping fails the Kafka handler like a synchronous mapping error. Root identifiers may use those four bindings, generated service bindings such as API, and JS/Node globals such as process, URL and crypto; unknown roots fail validation with MSCRIPT_UNKNOWN_ROOT_BINDING. |
| `enabled` | `Boolean` | no | `true` |  |  | Set to true to activate this Kafka controller. When false, the listener is not created during service startup. Default is true. |
| `concurrency` | `Integer` | no | `1` |  | min 1, max 64 | Maximum number of agent runs this controller executes AT ONCE on one service replica. Default 1: the controller handles one message at a time, and the next message is delivered only after the current run has finished and its offset is committed (a topic created by the framework has KAFKA_DEFAULT_PARTITIONS partitions, default 1, so one replica sees every message; more replicas in the same group only help when the topic has more partitions). Above 1, the Node.js listener consumes in batches and runs up to this many messages of a batch in parallel: the committed offset only moves past messages that have finished together with every earlier one, messages that carry the same Kafka key still run one after another, and after a crash the group resumes at the first unfinished message; a message that had already finished beyond it is redelivered and recognised as a duplicate by the run guard, so it is not run again. Every per-run guard (condition, dataMapping, maxTokenBudget, timeout) applies to each run, and the daily token budget and cost ceiling reserve each provider call's estimated cost before it is made, so runs in flight together cannot overspend them. The trade-off is cost and load: N runs in flight spend N times as fast and put N times the load on the model provider (also capped process-wide by AGENT_LLM_MAX_CONCURRENCY, default 4, so a value above it only queues more runs on the provider slots) and on the tools the agent calls. The alternatives without this setting are sharding the work over several topics, each with its own controller, or running more replicas on a topic with more partitions. Range 1 to 64. |

## Constraints

Property rules:

- `name`, `topic` must be present. (`REQUIRED_FIELD_MISSING`)
- `name` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)
- `concurrency` must be between 1 and 64. (`VALUE_OUT_OF_RANGE`)

Pattern rules:

| Code | Severity | Rule |
| --- | --- | --- |
| `AGENT_KAFKA_CONDITION_ASYNC` | error | AgentKafkaController.condition must be SYNCHRONOUS: it is evaluated before the run and a Promise is always truthy, so an async condition would accept every event. |

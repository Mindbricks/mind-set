# ApiKafkaSettings

**Level:** `section` · **Family:** [BusinessApiControllers](../ontology/families.md#businessapicontrollers) (domain `BusinessApi`)

**Ontology:** [ApiKafkaSettings in Part 1](../ontology/ApiKafkaSettings.md)

**Activation:** the pattern is switched on by `hasKafkaController`.

Configures Kafka as a trigger mechanism for the Business API. This supports both asynchronous processing and integration-based event handling (e.g., storage triggers, audit flows). Fields are flat — set `requestTopicName` and `responseTopicName` directly (the legacy `configuration: { ... }` wrapper is still accepted on input but lifted at validate time).

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `hasKafkaController` | `Boolean` | no | `false` |  |  | Enables the Kafka controller for this API. When true, the API can be triggered by Kafka messages. The generated controller unwraps the unified event envelope before the manager reads parameters — `body: _payload?.data ?? _payload` — so this API's `requestParameters[].dataPath` values are read scope 'record' and must be BARE keys, never `data.`-prefixed. The envelope's `actor` becomes the session and its `requestId` the correlation id.  PARAM_UNUSED semantics on kafka-consumer APIs: on an event-sourced API (hasKafkaController true, hasRestController false) a request parameter binds a key of the PRODUCER's payload, not a caller-supplied value. Binding a producer envelope key the manager never reads (e.g. `caseId`, `decidedAt`, `idempotencyKey`) is often DELIBERATE carriage — keeping `required: true` on the binding documents and enforces the producer contract even when the consumer's logic ignores the key. The validator therefore reports such bindings as informational (`PARAM_UNUSED` with `details.severity: 'info'` and consumer-specific text) instead of the REST-tier 'caller value silently dropped' warning; dropping the binding to silence it would silently loosen the contract check.  PERMISSION CHECK ON THIS ENTRY: a consumed message carries no session manager, so an api that declares `authOptions.permissionCheck` answers every message with 403 (logged as KafkaMessageRejected, dead-lettered when enabled) unless the event actor holds one of the api's `absoluteRoles` or the message is a verified machine call the api admits. Validation warns (PERMISSION_CHECK_ON_CALLERLESS_DOOR); gate a Kafka consumer with `checkRoles` / `absoluteRoles` instead. |
| `requestTopicName` | `String` | yes |  |  |  | Name of the main Kafka topic this API listens to. Can be custom or auto-generated from the API name. It stays required when the Kafka controller is enabled, also when `requestTopicNames` lists further topics: it is the FIRST topic of the api's effective topic list, and the default dead-letter topic (`<wireRequestTopicName>-deadletter`) is derived from it unless deadLetterPerTopic is true. |
| `responseTopicName` | `String` | no |  |  |  | Topic name to which the API response will be published. Optional. Only an APPLIED outcome (manager `httpStatus < 400`) is published here; a message the pipeline REJECTED never rides the response topic, it is logged as `KafkaMessageRejected` and, when `deadLetterEnabled` is true, published to the dead-letter topic instead. |
| `deadLetterEnabled` | `Boolean` | no | `false` |  |  | Opt-in dead-letter publishing for messages the manager pipeline REJECTS. The generated kafka controller treats any consumed message whose pipeline answers `httpStatus >= 400` (parameter vocabulary, required parameter, auth, ownership, a stale-version 409, a 5xx) as a REJECTED outcome: it logs an ERROR-level `KafkaMessageRejected` line (status, errorCode, detail, the api name and the redacted inbound message) instead of the INFO `KafkaMessageResponded` an applied mutation gets, and it commits the offset either way, so the message is not redelivered. With this flag true the controller ALSO publishes the original inbound message plus the problem body to the dead-letter topic (`deadLetterTopicName`, or, when unset, `<wireRequestTopicName>-deadletter` - the request topic AS THE CONSUMER SUBSCRIBES TO IT, which is project-scoped whenever a publishEventAction of this project authors it) through the service publisher, so a rejected message is preserved somewhere replayable. A dead-letter publish failure is logged as `KafkaDeadLetterPublishFailed` and never stalls the partition. Default false: an api that does not opt in emits no dead-letter code at all. |
| `deadLetterPerTopic` | `Boolean` | no | `false` |  |  | Opt-in per-incoming-topic default dead-letter names. Default false preserves the shared main-topic dead-letter stream (K5). With deadLetterEnabled true and no explicit deadLetterTopicName, true derives <scopeEventTopic(incomingTopic)>-deadletter for each effective request topic; the declared-topic census lists each stream for provisioning and ACLs. An explicit deadLetterTopicName always wins and remains shared. A single-topic controller is unchanged. This flag does not enable dead-letter publishing by itself. |
| `deadLetterTopicName` | `String` | no |  |  |  | Topic the rejected messages are published to when `deadLetterEnabled` is true. Optional: unset means `<wireRequestTopicName>-deadletter`, derived from the main request topic by default, or from each incoming topic when deadLetterPerTopic is true, as the consumer subscribes to it (project-scoped whenever a publishEventAction of this project authors that topic), so a scoped topic and its dead-letter stream stay in one namespace. Set explicitly, the name is baked exactly as authored - no suffix, no composition, never re-derived - and it still takes the publish door like any other topic: it is scoped to `<projectCodename>-<name>` when it is itself an authored PublishEventAction topic of this project, and stays verbatim otherwise. The census reports the string that reaches the wire in both arms. Must be a valid Kafka topic name. Ignored when `deadLetterEnabled` is false - and setting it without that flag raises the design-time warning `KAFKA_DEAD_LETTER_TOPIC_INERT`, because the generated controller then emits no dead-letter code at all and a rejected message's payload is preserved nowhere: set `deadLetterEnabled: true` to publish to this topic, or remove this field so the blueprint stops promising a dead-letter stream that does not exist. |
| `requestTopicNames` | `String`[] | no |  |  |  | Additional Kafka topics this API listens to, next to `requestTopicName`. The effective topic list is `requestTopicName` (or the generated default request topic when it is unset) followed by these names, exact-match de-duplicated in order, and the generated controller subscribes to EVERY topic of that list while routing all of them into the same handler and the same manager - one BusinessApi, one handling logic, several topics, instead of one near-identical api per topic. Each nodejs subscription gets its own consumer group (`<SERVICE_CODENAME>-<topic>-<apiName>`), where SERVICE_CODENAME is the lowercased `<projectCodename>-<serviceName>-service`. The response topic stays shared by all the topics. By default the dead-letter topic stays shared too: an explicit `deadLetterTopicName` is used for every topic, and the default dead-letter topic stays derived from the main topic. Opt into deadLetterPerTopic to derive the default from each incoming topic instead; an explicit name still wins. In the log lines and the dead-letter record the `topic` field names the topic the message actually came in on. Each entry must be a valid Kafka topic name (`KAFKA_TOPIC_NAME_INVALID` otherwise, a blank entry included) and a non-string entry is refused. Kafka topic names are case-sensitive: Orders and orders remain distinct subscriptions. Only exact duplicates within this list are removed, reported as an autofix. Leave empty (the default) for a single-topic api; an entry equal to `requestTopicName` changes nothing. |

## Constraints

Property rules:

- `requestTopicName` must be present. Enforced only while `hasKafkaController` is on. (`REQUIRED_FIELD_MISSING`)

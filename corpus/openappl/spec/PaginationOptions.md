# PaginationOptions

**Level:** `section` · **Family:** [BusinessApiQuery](../ontology/families.md#businessapiquery) (domain `BusinessApi`)

**Ontology:** [PaginationOptions in Part 1](../ontology/PaginationOptions.md)

Defines how pagination is handled in list-type Business APIs. Paginated lists take 1-based `page` and `pageSize` request parameters (legacy `pageNumber`/`pageRowCount` spellings are accepted as aliases) and respond with the list envelope `{ data: [...], paging: { page, pageSize, totalCount, totalPages } }`.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `paginationEnabled` | `Boolean` | no |  |  |  | RETIRED and IGNORED. No code generator reads this flag: a list api is always paginated unless it declares `unpaged: true`. The UI scaffolder writes `paginationEnabled: false` on every api, so a stored `false` cannot be told apart from the scaffold default, and reading it as "return the full set" would unpage every existing list. Leave the stored value as it is; to answer a list's whole result set, set `unpaged: true`. |
| `defaultPageRowCount` | `Integer` | no |  |  |  | Default page size (rows per page) applied when the caller does not send a `pageSize` (or legacy `pageRowCount`) request parameter. Must be a positive integer; null or 0 means the framework default of 25. The resolved window is still clamped to 1000 rows by the runtime. Honoured by the nodejs and golang api-layers; the other language lanes still emit their own default. |
| `cursorMode` | `Boolean` | no |  |  |  | Opt this list api into KEYSET (cursor) pagination instead of page/offset. A cursor list is ordered by the fixed keyset `createdAt ASC, id ASC` — `listOptions.listSortBy` and a runtime `?sortBy=` no longer apply — takes an opaque `cursor` request parameter instead of `page`, and answers with `{ data: [...], paging: { pageSize, nextCursor } }`. `nextCursor` is null when the walk is exhausted; feed it back as `?cursor=` for the next page. NO COUNT query runs, so `totalCount` and `totalPages` are ABSENT from the envelope — that skipped table scan is the point of the mode. Use it for deep walks, exports and any list where rows are inserted while the caller is paging: offset paging skips and duplicates rows under concurrent inserts, keyset does not. `listOptions.topPick` is meaningless here (there is no ranked window to cap) and is ignored. Honoured by the nodejs, dotnet, java and golang lanes (PostgreSQL and MongoDB); the other language lanes still ignore it and serve page/offset. A validation ERROR together with `unpaged: true`. |
| `unpaged` | `Boolean` | no |  |  |  | Opt this list api OUT of pagination. This is the ONLY switch that does; the retired `paginationEnabled` is ignored. An unpaged list answers its WHOLE filtered result set in one response, `{ data: [...], paging: { page: 1, pageSize: N, totalCount: N, totalPages: 1 } }` (an empty set reports `totalPages: 0`), and ignores `page`/`pageSize` request parameters. The runtime walks the store in keyset chunks of 1000 rows, so rows come back in the fixed order `createdAt ASC, id ASC` and `listOptions.listSortBy` does not apply (the validator warns when both are declared). A set larger than the runtime ceiling is REFUSED with 422 `UNPAGED_LIST_TOO_LARGE`, never truncated; the ceiling is the `UNPAGED_LIST_MAX_ROWS` environment variable (a positive integer, default 10000). `listOptions.topPick` still caps the set. A validation ERROR together with `cursorMode` (a caller-driven keyset walk is the opposite contract) and with `apiOptions.dataViewName` (an Elasticsearch read cannot walk past its result window). The ceiling applies to the one-response answer: an SSE stream (`responseMode: 'stream'`) of an unpaged list sends the whole set chunk by chunk and is NOT capped. A store that returns a cursor it already returned ends the walk with 500 `UNPAGED_LIST_WALK_STALLED` instead of hanging. Meant for internal, kafka, cron and library callers: the validator warns when external callers can reach an unpaged list (`UNPAGED_LIST_REST_EXPOSED` with a REST controller, `UNPAGED_LIST_EXPOSED` with only SSE, gRPC or `apiOptions.mcpExposed`), because every caller that passes the api's gates receives the whole table; for such a list, page it and size the page with `defaultPageRowCount`. Honoured by the nodejs and golang lanes; the other language lanes still serve one page at the default size. |

# PaymentAction

**Level:** `section` · **Family:** [BusinessApiActionStore](../ontology/families.md#businessapiactionstore) (domain `BusinessApi`)

**Ontology:** [PaymentAction in Part 1](../ontology/PaymentAction.md)

**Extends:** [BusinessApiAction](./BusinessApiAction.md); the properties it declares apply here too.

Calls the proper native payment provider functions according to the current stage of payment lifecycle. The bound provider is selected by `providerName` (lookup into projectSettings.paymentProvidersSettings.paymentProviders[]). The legacy `gateway` field is preserved for back-compat with pre-PaymentProvider-refactor configs — when only `gateway` is set, it resolves to a `legacyStripe` provider via the runtime compat shim. WHERE THE CALLER'S PAYMENT CONTROLS COME FROM: a `start` stage builds the provider intent from the OWNING API'S BOUND REQUEST PARAMETERS - the emitted action spreads that request-parameter blob into the intent input and PaymentManager reads `return_url`, `paymentMethodId` and `providerOptions` off it. The money facts (amount / currency / orderId / customer) come from the parent DataObject's checkout block bindings against the PERSISTED order row, never from the caller, so those three keys are the only values a caller ever contributes. An api that declares no requestParameter at a caller-supplied `httpLocation` (`body`, or `query` on a bodyless method) can receive none of them - design-time finding PAYMENT_START_NO_CALLER_PARAMS. The consequence that bites hardest is `return_url`: with a hosted-checkout provider (iyzico Checkout Form) the buyer's browser leaves for the provider and returns to the service's own `/v1/payments/checkout-return/<provider>` route, which redirects 303 to the ticket's `metadata.returnUrl` - stamped from `return_url` at start - and, when the ticket carries none, answers a minimal JSON confirmation instead. That JSON is documented behaviour, not an error: the payment succeeds and the buyer's browser simply stops on it. An iyzico saved card's 3-D Secure ends the same way on the generated `/v1/payments/threeds-return/<provider>` route, which calls 3dsecure/auth itself, so an iyzico design authors no `complete` stage. Neither does a Stripe design (Stripe.js finishes the intent and the generated webhook route records it) nor an Adyen design (its details step is the generated `PATCH /v1/complete<object>payment/:orderId` route); of the native providers only PayPal's capture after the buyer approved needs an authored `complete` stage.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `providerName` | `String` | no |  |  | format [codeName](./value-formats.md#codename) | Lookup key into projectSettings.paymentProvidersSettings.paymentProviders[].name. Selects which native adapter handles this action. When null/omitted, falls back to the legacy `gateway` field for back-compat (resolves to `legacyStripe` if only `gateway` is set). |
| `stage` | `PaymentStage` | no | `"start"` | 10 values, see [PaymentStage](#paymentstage) |  | The type of the stage call that the action will make. It can start, complete or refresh a payment, or read back a provider callback. New stages (refund, subscribe, payout, dispute) are handled by their dedicated Action types; PaymentAction itself only owns the original one-time-payment stages (simple, start, complete, refresh, callback). Any other PaymentStage value on a PaymentAction (refund, dispute, subscribe, cancelSubscription, payout) is a design-time ERROR PAYMENT_STAGE_OFF_CONTRACT: the generated action has no arm for it and would fall back to starting a payment, i.e. CHARGE the buyer; use a RefundAction, SubscriptionAction or PayoutAction (disputes arrive on the provider webhook). Every stage reads the caller's payment USER PARAMS from ONE blob: this api's bound request parameters at a caller-supplied httpLocation (`body`, or `query` on a bodyless method), one flat key per declared parameter plus the keys of a declared Object parameter named `paymentUserParams`. `start` passes that blob through as the one `return_url`, `paymentMethodId` and `providerOptions` are read off (see the class description), so declare those keys whenever the flow needs them - without a caller-supplied parameter the api can receive none of them and validation reports PAYMENT_START_NO_CALLER_PARAMS. `complete` and `refresh` address an intent that already exists and read its id off the SAME blob (`providerIntentId`, or `paymentId`; `complete` also reads `return_url` and `paymentMethodId`), so declare that id as a caller-supplied requestParameter too: without it the nodejs emission of the stage throws on every call, and validation reports PAYMENT_STAGE_NO_INTENT_ID_PARAM (a warning, not an error: the other language runtimes read the id off the raw request). `callback` reads the provider's own request. On a checkout order object `complete`, `refresh` and `callback` are GATED before the provider is called, exactly as the generated payment routes are: the `sys_<X>Payment` ticket recorded for the addressed id must exist (400 PAYMENT_NOT_STARTED), its order row must exist (404 NOT_FOUND), and the caller must own that order (another user is 403 NOT_OWNER, a request with no session is 401 LOGIN_REQUIRED; only a trusted system caller or a kafka consumer declared `loginRequired: false` skips the owner check, never the ticket check). A ticket that is still a start claim (a start of the order is in flight) is 409 PAYMENT_START_IN_FLIGHT, as on the generated complete / refresh routes. An anonymous hosted-checkout browser return or a provider webhook therefore cannot drive these stages: those arrive on the generated `/v1/payments/checkout-return/<provider>` and webhook routes, and an iyzico saved card's 3-D Secure callback on the generated `/v1/payments/threeds-return/<provider>` route, which completes the payment (3dsecure/auth) without any stage. Stripe needs no `complete` stage either (the browser finishes the intent through Stripe.js and the webhook route records it), and Adyen's details step is the generated `PATCH /v1/complete<object>payment/:orderId` route. Of the native providers only PayPal's capture after the buyer approved needs an authored `complete` stage, in a session api the return page calls. `start` and `simple` on a checkout order object authorize the persisted order BEFORE anything reaches the provider, with the generated start route's ownership rule: the order's owner (the order row first, then the payment ticket), a payment admin (`admin` / `superAdmin`; `superAdmin` / `saasAdmin` in a multi-tenant project) or a verified inter-service caller the api admits may start it; another user is 403 NOT_OWNER and a request with no caller 401, before any intent, ticket or charge (a trusted system caller is not asked). On an order object with no `sessionSettings.isOwnerField` a buyer cannot start it at all, and validation reports PAYMENT_START_ORDER_OWNERSHIP_UNBOUND (a warning) for a start api a non-admin can reach. The check covers the payment action only, not what an earlier action of the same workflow read. |
| `buyerAbsent` | `Boolean` | no | `false` |  |  | Declares that this action charges while the BUYER IS NOT IN SESSION: a scheduled or merchant-triggered charge made on the buyer's behalf (a renewal or card-on-file charge a cron job or an event consumer runs, an agreed top-up, a later charge the buyer agreed to in advance, such as one an AI assistant confirmed for them earlier), never a checkout the buyer is clicking through. The off-session charge still needs a proven stored card: a scheduled or system run (a cron or internal transport, or a Kafka consumer declared loginRequired false, recognised from the transport and never from the request) proves it from the order owner through the identity owner's machine-only reads (needs an owner column on the order object), an HTTP call proves it with the caller's forwarded token, and an anonymous HTTP call proves none and stays on-session; the framework does not check which user calls the API over HTTP, so never put such an action on an API the buyer calls while paying. Default false. It is a design fact, read at generation time; no request value can set it. It matters on a Stripe entry with savedCardOffSession 'verified' (beside savedCardThreeDSMode 'verifyOnce'): only a start / simple charge of an action declared buyerAbsent, on a checkout order object, on a proven stored card (the order owner's on a system run, the caller's on an HTTP call) whose row is 3-D Secure verified, is sent off_session (a merchant-initiated transaction, no buyer step, no 3-D Secure liability shift). Every other action stays on-session on that entry and Stripe may still ask the buyer to authenticate. Card-network rules allow a merchant-initiated charge only while the buyer is absent, under the stored-credential agreement accepted when the card was saved, so a buyer-present checkout (a one-click purchase included) must NOT declare it. Declared on another provider, on a Stripe entry without savedCardOffSession 'verified', on a complete / refresh / callback stage, on a marketplace order object, on an order object bound to a provider entry of another brand, or with no checkout order object behind it, it does nothing and draws the warning PAYMENT_ACTION_BUYER_ABSENT_INERT. nodejs, dotnet and java services only for now. |

## Allowed values

### PaymentStage

`simple`, `start`, `complete`, `refresh`, `callback`, `refund`, `dispute`, `subscribe`, `cancelSubscription`, `payout`

## Constraints

Property rules:

- `stage` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- `providerName` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)

Pattern rules:

| Code | Severity | Rule |
| --- | --- | --- |
| `PAYMENT_AMOUNT_PROPERTY_MISSING` | error | amountProperty is required in the payment configuration for DataObject "…" but is not defined. |

## Example

Use to drive the one-time payment lifecycle (start/complete/refresh/callback/simple) against a named PaymentProvider — e.g. create a payment intent at checkout that the frontend then confirms.

```json
{
  "name": "startOrderPayment",
  "description": "Create a payment intent for the order so the client can confirm it.",
  "providerName": "stripeMain",
  "stage": "start",
  "contextPropertyName": "paymentIntent",
  "writeToResponse": true
}
```

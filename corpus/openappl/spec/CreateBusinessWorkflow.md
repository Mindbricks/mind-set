# CreateBusinessWorkflow

**Level:** `section` · **Family:** [BusinessWorkflow](../ontology/families.md#businessworkflow) (domain `BusinessApi`)

**Ontology:** [CreateBusinessWorkflow in Part 1](../ontology/CreateBusinessWorkflow.md)

Defines the standard execution milestones for a `create`-type Business API. Each field represents a milestone (a fixed lifecycle stage), and its value is an ordered list of action names executed by the API manager. These steps include all default, hardcoded logic (e.g., session handling, parameter extraction, DB insert) while leaving space for user-defined actions after each milestone. You can modify this workflow programmatically or visually.

**Failure semantics — NO ROLLBACK.** The milestones run sequentially with no transaction. Everything up to and including `afterBuildDataClause` runs BEFORE the row is inserted, so an action that throws there leaves the database untouched. From `afterMainCreateOperation` onward the new row is already committed, and an action that throws (`onActionError: throwError`, the default) aborts the remaining pipeline WITHOUT undoing that insert or any write an earlier action already made. Put child writes that may legitimately fail — a unique-index child create, an `interserviceCallAction` create on another service, an external api call — in `afterBuildDataClause`; use `onActionError: completeApi` for post-main work that must not fail the api. See `BusinessWorkflow` for the full contract.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `afterStartBusinessApi` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | Executed first, just after the api is started by the controller and BEFORE the login check (pipeline step 0): the context has the raw request, and a session the caller sent is populated, but the api's login requirement has not been enforced yet, so an anonymous caller reaches this stage. Use it for login-independent work - fundamental request validations or preparing the context. On an api that requires a login (authOptions.loginRequired, default true) an InterserviceCallAction, AgentCallAction, IntegrationAction, InterProjectCallAction, SendMailAction, CheckMailboxAction, ReadMailAction, PublishEventAction, SendSmsAction, SendWhatsAppAction or SendPushNotificationAction may not be scheduled here, directly or inside a loop/parallel container: each acts with the service's or the project's own authority (a machine-identity forward, a mail, SMS, WhatsApp or push send or a mailbox read with the project's credentials, or a Kafka event its consumer treats as a machine caller), so an anonymous caller would borrow that authority. Design time refuses that shape (PRE_AUTH_MACHINE_AUTHORITY_ACTION); schedule those actions at afterReadParameters (the first milestone after the login check) or later. |
| `afterReadParameters` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | Triggered after all parameters are read from the request or Redis. Use this to perform early validation or context enrichment based on raw input. |
| `afterTransposeParameters` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | Executed after parameters are normalized or transformed. Use this for logic that depends on preprocessed values (e.g., derived inputs or structure remapping). |
| `afterCheckParameters` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | Runs after parameter validations complete. Use this for business logic checks or to raise field-specific errors (e.g., pricing thresholds, invalid combinations). |
| `afterCheckBasicAuth` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | Fires after role and permission validations. Typically used to enforce fine-grained access checks or audit preparation logic. |
| `afterBuildDataClause` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | Executed after the data clause object is constructed and before the actual create operation. Use this to inject additional fields or adjust payload structure. |
| `afterMainCreateOperation` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | Runs immediately after the database insert operation completes. Ideal for events, side-effects, or chained actions based on the created record.  This stage also runs when NO ROW WAS INSERTED. If the object declares a unique index with `onDuplicate: 'stopOperation'` (the sanctioned way to make a create retry-safe), a replay returns the EXISTING row and the pipeline continues normally — `this.result` and `this.<objectName>` are that prior row. Read `this.createOutcome` to tell the cases apart: `'created'` (a row was inserted), `'duplicateStopped'` (the index matched and nothing was written) or `'duplicateUpdated'` (`onDuplicate: 'doUpdate'` matched and the row was updated in place). Gate every action here whose effect must not repeat — child creates, counter allocations, published events — with `condition: "this.createOutcome === 'created'"`. The value is bound by `executeMainOperation()` at this stage, so it is `undefined` in any earlier stage and must not be read there. |
| `afterBuildOutput` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | Allows final shaping of the response payload before it is sent. You can inject, modify, or strip fields at this stage. |
| `afterSendResponse` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | Triggered after the response is sent to the client. Use for post-response operations like analytics, logging, or delayed workflows. This milestone is SUCCESS-ONLY: an api that aborted and answered 4xx/5xx skips it entirely, along with the api event and `afterApiEvent`, so nothing authored here runs and no event is published. |
| `afterApiEvent` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | Triggered after the Business API emits an API-level event (if configured). This is the final milestone in the API execution flow and is typically used for cleanup, async queues, or chained notifications that depend on event dispatch success. Like `afterSendResponse`, this milestone is SUCCESS-ONLY: an api that answered 4xx/5xx never reaches it. |

## Constraints

Property rules:

- `afterStartBusinessApi`, `afterReadParameters`, `afterTransposeParameters`, `afterCheckParameters`, `afterCheckBasicAuth`, `afterBuildDataClause`, `afterMainCreateOperation`, `afterBuildOutput`, `afterSendResponse`, `afterApiEvent` must be in the [`codeName`](./value-formats.md#codename) format.

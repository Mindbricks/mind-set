# InvoicingConfig

**Level:** `subsection` · **Family:** [ObjectSettings](../ontology/families.md#objectsettings) (domain `DataObject`)

**Ontology:** [InvoicingConfig in Part 1](../ontology/InvoicingConfig.md)

Configuration for provider-neutral accounts-receivable invoicing on a DataObject. Provider-binding is explicit via `providerName` (lookup into projectSettings.invoiceProvidersSettings.invoiceProviders[]); a null providerName binds the framework-internal provider. Property bindings (customer / amount / currency / due date / status) are PropRefer paths into the parent DataObject, same style as CheckoutConfig. The invoice flow is: draft (this object, freely editable) → finalize (line snapshot + number + FSM `open`) → payment allocation (sys_<X>InvoicePayment) → status mirrored back onto this object. Triggers are DECLARATIVE (`issuePolicy` / `issueCondition`) — the designer never writes imperative glue; `issuePolicy: manual` plus invoice actions is the imperative escape hatch.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `providerName` | `String` | no |  |  | format [codeName](./value-formats.md#codename) | Name of the configured InvoiceProvider that is the SYSTEM OF RECORD for this object's invoices. Must match an entry in projectSettings.invoiceProvidersSettings.invoiceProviders[].name. When null, the framework-internal provider is used — storage and invoice lifecycle fully inside the generated application. |
| `sourceObjectName` | [`LocalDataObjectName`](./LocalDataObjectName.md) | no |  |  | names a [DataObject](./DataObject.md) | Optional: the same-service DataObject this invoice is issued FROM (e.g. the order). When set, issuePolicy triggers read amount / lines / customer from the source object; when null, this object itself is both the domain surface and the source. Must be a local data object of the same service — a cross-service source is deliberately out of scope: there is no automatic cross-service invoice bridge. Unless `publishLifecycleEvents` is set, the invoice layer publishes no Kafka events of its own (every injected api has raiseApiEvent: false); the payment layer publishes only its payment-status events (`<object>-payment-updated` on every ticket status change, `<object>-payment-paymentdone` on a change into success). A separate billing service that must hear about an invoice fact either listens to this object's opt-in invoice lifecycle topics (`publishLifecycleEvents: true` - normalized events delivered at least once through the service's lifecycle outbox, see that field) or needs a designer-authored lifecycle hook that publishes it (a LIB function with a declared topic, or an internal-call api with a PublishEventAction); either way it listens with a standard EventSubscription. OWNERSHIP: every issued invoice row is stamped `ownerId` from the SOURCE object's owner column (the property flagged `sessionSettings.isOwnerField`). A source with no owner column stamps `ownerId: null` on every invoice, so no customer can read one (the document route answers 403 OWNER_UNRESOLVED_LEGACY, the owner-filtered list returns nothing) and only operator callers (absolute roles, M2M) see them; design-time WARNING INVOICE_OWNER_UNBINDABLE. The framework does not guess an owner column. |
| `issuePolicy` | `InvoiceIssuePolicy` | no | `"manual"` | `manual`, `onPaymentCaptured`, `onSourceCreate`, `onSubscriptionInvoicePaid` |  | Declarative creation/finalization trigger — codegen wires the dispatcher accordingly, the designer never writes imperative glue. `manual` (default): invoices are created and finalized only through explicit calls. `onPaymentCaptured`: when the bound payment lifecycle reports a captured payment for the source object, the invoice is issued and finalized from the source snapshot (the B2C e-commerce flow). `onSourceCreate`: an open invoice with a due date is issued as soon as the source object is created — the B2B invoice-first-collect-later flow (pair with issueCondition to split B2B from B2C). onSourceCreate is wired through the in-process after-create seam: the db-layer create of the source object hands the committed row to the invoice manager automatically. `onSubscriptionInvoicePaid`: one invoice per provider subscription cycle, using the effective source subscription journal, including a cross-sourced object in this service; replay-safe and merchant-of-record aware. |
| `issueCondition` | [`MScript`](./MScript.md) | no |  |  | MScript kind `code` | Optional MScript guard evaluated before an automatic issuePolicy trigger fires (e.g. only issue a legal invoice for B2B buyers). When present and falsy, the automatic trigger is skipped for that event; manual issuance stays available. BINDINGS: the guard runs with `this` bound to a context object, NOT the row - its only keys are `order` and `source` (both the source row the invoice is issued from: sourceObjectName, or this object itself) and `payment` (the sys_<X>Payment ticket on onPaymentCaptured, the sys_<X>Subscription row on a subscription capture, null on onSourceCreate); on onPaymentCaptured the lexical `event` / `resource` are in scope too. Write `order.buyerType === 'B2B'` (or `this.order.buyerType`), never `this.buyerType`: a `this.<field>` that is not one of those keys reads `undefined`, the guard is falsy on every event and no invoice is ever issued, so validation refuses it (CONDITION_THIS_NOT_IN_CONTEXT, ERROR). |
| `customerProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property on this object referencing the buyer — an auth user id or a customer/party record reference. The invoice is attached to this customer for balance and collection purposes. It does NOT decide who may READ the invoice: read access is the invoice row's `ownerId`, stamped from the source object's owner column (see sourceObjectName). |
| `amountProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Optional property holding the invoice total, for objects whose total is not derived from lines. When invoiceLineRelation is active, line totals are authoritative and this binding serves as a mirror/cross-check. PLATFORM MONEY CONVENTION: MAJOR currency units as a decimal (the invoice family's native unit) - never bind a minor-unit (kurus/cents) column; line-relation bindings (unitPrice/lineTotal/vatAmount/...) follow the same convention. The bound column MUST be declared `type: "Decimal"`, so the framework rounds it to its `decimalScale` at every write boundary and before the amount reaches the provider. A bound column declared with another NUMERIC type (Integer/Short/Double/Float) is migrated by validation to Decimal (scale from the binding's static currency, default 2) and reported as an auto-fix; a non-numeric one is the ERROR `MONEY_BINDING_NOT_DECIMAL`. |
| `vatRateStaticValue` | `Double` | no |  |  |  | Optional static VAT rate (percent, e.g. 20) for RELATION-LESS invoice objects — the single implicit line built from amountProperty. Semantics: amountProperty is the VAT-INCLUSIVE gross; at snapshot time the implicit line is priced as a gross line (pricesIncludeVat) with the cart-parity gross-first formula (net = round(gross / (1 + rate/100)), vatAmount = gross - net, kurus rounding, so net + vatAmount equals the gross exactly), so invoice totals and fiscal document lines carry the real breakdown and the UBL emits a non-zero 0015 bucket with no exemption pair. Mutually exclusive with vatRateProperty (both set is a design-time ERROR) and meaningless next to invoiceLineRelation — the relation owns the per-line breakdown, so combining is a design-time ERROR. Rate 0 or key absent behaves exactly as before: zero bucket + the zero-VAT exemption fallback. |
| `vatRateProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Optional property ON THIS OBJECT holding the VAT rate (percent) for the relation-less single implicit line — the dynamic twin of vatRateStaticValue (both set is a design-time ERROR; combining with invoiceLineRelation is a design-time ERROR). Same VAT-inclusive-gross semantics; an unset/unreadable row value falls back to rate 0. |
| `vatExemptionCodeProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Optional property ON THIS OBJECT holding the GIB KDV exemption reason CODE of the relation-less single implicit line - the twin of invoiceLineRelation.vatExemptionCodeProperty for an object without a line relation, next to vatRateProperty. Read only when the line's VAT rate is 0: the code lands on the line's zero-VAT 0015 bucket of the Turkish fiscal document (cbc:TaxExemptionReasonCode), e.g. 335 for printed books (KDV 13/n), 301 for goods export, 351 for a 0% line that is NOT exempt. An unset or empty row value falls back to the invoice-wide / fiscal provider entry vatExemptionReasonCode, then to 350. The emitted codes decide the InvoiceTypeCode: any 2xx/3xx exemption code makes the document ISTISNA, 351 keeps SATIS. A code on a row whose rate is not 0 is refused when the document is prepared (typed 400). Combining it with a bound invoiceLineRelation is a design-time ERROR (the relation's own vatExemptionCodeProperty applies there). |
| `vatExemptionReasonProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Optional property ON THIS OBJECT holding the exemption reason TEXT that pairs vatExemptionCodeProperty on the relation-less single implicit line. Unset or empty: the platform writes the OFFICIAL GIB text of the code (UBL-TR Kod Listeleri, e.g. 335 -> 'KDV 13/n Basılı Kitap ve Süreli Yayınların Teslimleri'), so this binding is only needed for a code the GIB list does not carry yet. Meaningless without vatExemptionCodeProperty (WARNING). |
| `currencyProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Property on this object that holds the invoice currency. |
| `currencyStaticValue` | `String` | no |  |  |  | Static currency fallback — applies only when currencyProperty is unset or resolves to nothing on the row. |
| `dueDateProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Optional property holding the payment due date stamped onto open invoices. When unbound, collection.daysUntilDue derives the due date at issue time. |
| `statusProperty` | [`PropRefer`](./PropRefer.md) | no |  |  | names a [DataProperty](./DataProperty.md) from `>basicSettings.name` | Optional property on this object that MIRRORS the invoice status (draft \| open \| paid \| partially_paid \| voided \| uncollectible). The framework updates this property as the invoice state machine advances. It is a read model for UX/queries — the ledger's own statusLiteral on sys_<X>Invoice stays authoritative and is never writable through this object's update APIs. |
| `invoiceLineRelation` | [`InvoiceLineRelation`](./InvoiceLineRelation.md) | no |  |  |  | How this object relates to its LINE ITEM object — the editable SOURCE of invoice lines. Snapshot semantics: at finalize time the lines and their tax breakdown are copied into the immutable sys_<X>InvoiceLine ledger, so later edits to the source rows never change an issued invoice. The relation's per-line bindings align one-to-one with the line fields the shopping-cart pricing settings produce (unitPrice, quantity, lineTotal, discountAmount, vatRate, vatAmount, finalTotal), so a cart's tax breakdown flows into the invoice losslessly. |
| `numbering` | [`InvoiceNumberingConfig`](./InvoiceNumberingConfig.md) | no |  |  |  | Invoice numbering configuration (series / prefix / reset period). Authoritative for the internal provider (the framework's atomic sys_invoiceSequence assigns numbers) and for any provider with capabilities.supportsNumbering=false; when the bound provider owns the legal sequence (e.g. stripe), this block is ignored for number assignment. |
| `collection` | [`InvoiceCollectionConfig`](./InvoiceCollectionConfig.md) | no |  |  |  | How finalized invoices are collected: sent to the customer to be paid later (`sendInvoice`, with daysUntilDue deriving the due date), or charged automatically against a stored payment method (`chargeAutomatically` — requires the bound provider to have capabilities.supportsCollection=true). |
| `lifecycleHooks` | [`InvoiceLifecycleHook`](./InvoiceLifecycleHook.md)[] | no |  |  |  | Designer-authored MScript handlers fired as the invoice state machine advances (afterInvoiceFinalized, afterInvoicePaid, afterInvoiceVoided, afterCreditNoteIssued, afterPaymentApplied, ...). Invoice hooks carry their OWN trigger vocabulary (InvoiceLifecycleTrigger) — the payment LifecycleHook trigger enum is reconciled 1:1 with the payment lifecycle machines and deliberately stays untouched. A hook receives the normalized document (`invoice`: NormalizedInvoiceDetail; `allocation` / `creditNote` on their triggers), not the sys_<X>Invoice row - the source row id is `invoice.metadata.sourceObjectId`. |
| `publishLifecycleEvents` | `Boolean` | no | `false` |  |  | Opt-in (default false; only a literal `true` on an ACTIVE invoicing block counts) that makes the generated invoice layer publish this object's normalized INVOICE lifecycle events to Kafka (family `invoice`), one topic per event, 1:1 with the invoice lifecycle triggers: `<projectCodename>-<service>-service-lcevent-invoice-<object lowercased>-<suffix>`, where the FIXED event list and its suffixes are `invoice.finalized` -> `finalized` (afterInvoiceFinalized), `invoice.paid` -> `paid` (afterInvoicePaid), `invoice.partially_paid` -> `partially-paid` (afterInvoicePartiallyPaid), `invoice.voided` -> `voided` (afterInvoiceVoided), `invoice.uncollectible` -> `uncollectible` (afterInvoiceUncollectible), `invoice.payment_applied` -> `payment-applied` (afterPaymentApplied), `creditnote.issued` -> `creditnote-issued` (afterCreditNoteIssued). Published from the invoice lifecycle AFTER the designer lifecycle hooks of the same trigger, every time the trigger fires. `data` = { eventType, family, object, providerName, providerEventId (null: the triggers are not provider events), occurredAt, orderId (the source row id), status, dedupeKey, invoice (an ALLOWLISTED projection of the normalized invoice: providerInvoiceId, invoiceNumber, series, statusLiteral, currency, subtotal, vatTotal, total, amountPaid, amountRemaining, dueDate, issuedAt, lineCount, sourceObject, sourceObjectId, surfaceRowId), allocation (payment triggers: providerAllocationId, providerInvoiceId, amount, currency, appliedAt, paymentRef, invoiceStatus, amountPaid, amountRemaining), creditNote (creditnote.issued: providerCreditNoteId, providerInvoiceId, amount, currency, reason, issuedAt) }; never the buyer / seller party, the lines or the metadata wholesale. Delivery is AT LEAST ONCE through the service's lifecycle outbox: each event is written to `sys_lifecycle_outbox` (one row per `data.dedupeKey`, the built envelope plus its retry state) before it is sent, the send is never awaited by the transition that fired it, and a send the broker refuses (logged `PaymentLifecycleEventPublishFailed`) is re-sent by the outbox sweeper with the same envelope id and dedupeKey (every PAYMENT_LIFECYCLE_OUTBOX_SWEEP_INTERVAL_MS, default 30 s; backoff up to one hour; parked `dead` after 50 refusals). The same fact processed twice (a redelivered invoice webhook) is sent once while its outbox row is kept; a redelivery can still repeat an event: dedupe on `data.dedupeKey`, and reconcile money from the invoice rows, not from the stream. Envelope: `type` = the normalized event type; `actor.tenantId` = the row's tenant in a multi-tenant project. Off (the default) the generated code is byte-identical to a build without the field; the topics are listed by the kafka topic census and pre-created only while it is on. |

## Constraints

Property rules:

- `issuePolicy` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- `providerName` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)
- `sourceObjectName` must be a well-formed [`LocalDataObjectName`](./LocalDataObjectName.md) (a data object of the same service). (`INVALID_LOCAL_DATA_OBJECT_NAME_FORMAT`)
- `customerProperty`, `amountProperty`, `vatRateProperty`, `vatExemptionCodeProperty`, `vatExemptionReasonProperty`, `currencyProperty`, `dueDateProperty`, `statusProperty` must be a well-formed [`PropRefer`](./PropRefer.md) (a property of a data object). (`INVALID_PROP_REFER_FORMAT`)
- The items of `lifecycleHooks` must have distinct names (`name`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)

Pattern rules:

| Code | Severity | Rule |
| --- | --- | --- |
| `INVOICE_ISSUE_POLICY_NO_PAYMENT_PATH` | error | issuePolicy "…" requires … block on source object "…". |
| `INVOICE_LINE_OBJECT_NOT_FOUND` | error | Line item object "…" is not a data object of this service. |
| `INVOICE_LINE_VAT_CONVENTION_MISMATCH` | warning | This service's shopping cart prices VAT-INCLUSIVE (pricingSettings.catalogPricesIncludeVat), but invoiceLineRelation reads "…" unit prices as NET. |
| `INVOICE_LINE_VAT_INCLUSIVE_WITHOUT_RATE` | error | pricesIncludeVat declares the bound unit prices VAT-INCLUSIVE, but no vatRateProperty is bound, so there is no rate to extract the VAT with and every line would be invoiced at 0% VAT. |
| `INVOICE_SOURCE_OBJECT_NOT_FOUND` | error | Source object "…" is not a data object of this service. |
| `INVOICE_VAT_BINDING_CONFLICT` | error | vatRateStaticValue and vatRateProperty are mutually exclusive — the relation-less implicit line has ONE VAT rate. |
| `INVOICE_VAT_BINDING_WITH_LINE_RELATION` | error | Single-line VAT bindings (vatRateStaticValue / vatRateProperty) apply only to RELATION-LESS invoice objects — invoiceLineRelation already owns the per-line tax breakdown (bind its vatRateProperty/vatAmountProperty … |
| `INVOICE_VAT_EXEMPTION_BINDING_WITH_LINE_RELATION` | error | vatExemptionCodeProperty / vatExemptionReasonProperty on the invoicing configuration apply only to RELATION-LESS invoice objects (the single implicit line). |
| `INVOICE_VAT_EXEMPTION_REASON_WITHOUT_CODE` | warning | vatExemptionReasonProperty is bound without vatExemptionCodeProperty. |
| `INVOICE_VAT_RATE_OUT_OF_RANGE` | error | vatRateStaticValue must be a percentage between 0 and 100 — received …. |

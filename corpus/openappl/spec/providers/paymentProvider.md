## Live and test key detection

Per-brand LIVE/TEST credential-mode detectability - can the framework tell, from the entry's own resolved configuration, whether this credential moves REAL money? `key-prefix` = the mode is encoded in the credential string itself (stripe sk_test_/sk_live_); `keyPrefixes` maps each detectable config key to its live/test prefix classes, and ONLY those catalogued prefix strings may ever be echoed into a log or an error - never any further part of the key. `base-url` = the mode is encoded in the endpoint host (`urlKey` names the config key; `sandboxMarkers` are matched case-insensitively BEFORE `liveMarkers`, because iyzico's sandbox host contains its live host as a substring; a base-url row that also names `environmentKey`/`liveValues`/`testValues` falls back to that environment field when the URL matches no marker). `environment-field` = an explicit environment enum config key decides (`environmentKey`/`liveValues`/`testValues`; `environmentDefault` is the value the adapter factory falls back to when the key is unset, so detection answers what the adapter will actually do). `none` = nothing detectable; the mode reports `unknown`. This fact feeds the live-key runtime guard: a detected `live` mode refuses to construct the real adapter on a non-prod deployment unless the entry sets `allowLiveInPreview`, and /v1/payments/mock-status reports the mode per provider. Detection rules are mirrored (and parity-tested) in _common/nodejs/src/common/payment-providers/key-mode.ts, which ships inside generated services where this catalog does not exist.

## Webhook provisioning

Per-brand WEBHOOK PROVISIONING origin - can a program register this brand's webhook endpoint and receive its signing material back, or must a human do it in the vendor's panel? `api-returns-secret` = the create call answers with the signing secret, so the framework can reach verified-webhook state with no human touching a dashboard (POST /v1/payments/admin/webhooks/provision). `api-no-secret` = an endpoint can be created over the API but no signing secret comes back, because the brand verifies with something else. `panel-only` = the endpoint is registered in the vendor's panel. `shipped` says whether THIS framework implements the capture yet, which is a different fact from whether the vendor offers it. Measured from each adapter's own verifyWebhook and its endpoint-creation calls in _common/nodejs/src/common/payment-providers/.

| Entry | provisioning | shipped | verifiesWith | note |
|---|---|---|---|---|
| `stripe` | api-returns-secret | true | webhookSecret | POST /v1/webhook_endpoints returns the signing secret (whsec_*) ONLY in the creation response - never readable again, only rotatable. createWebhookEndpoint captures it there; rotation is create-then-delete, because a secret only ever comes out of a creation. Because the sweep captures it, `webhookSecret` is PROVISIONING STATE, not an authored configuration key: this brand catalogues no such key (removed in the webhook-provisioning catalog alignment), and the captured value lives under PAYMENT_PROVIDER_<NAME>_WEBHOOK_SECRET. |
| `adyen` | api-returns-secret | false | hmacKey | Adyen's Management API creates a standard webhook and generates its HMAC key, so this brand CAN self-provision - but the adapter implements no creation call, so the sweep reports it unsupported. It is the only other brand that can be live-but-unverifiable (requiredFor webhook + webhookVerificationUnavailable), which makes it the first follow-up. |
| `paypal` | api-no-secret | false | webhookId | POST /v1/notifications/webhooks creates the webhook and returns its id, but PayPal issues NO signing secret at all: verifyWebhookAsync posts the event back to /v1/notifications/verify-webhook-signature with that id. Provisioning would capture an id, not a secret - a different shape from the stripe path. |
| `paddle` | api-returns-secret | false | webhookSecretKey | The adapter verifies the Paddle-Signature h1 HMAC with the notification destination's secret key. Paddle's notification-settings API creates a destination and returns that key as endpoint_secret_key, so this brand CAN self-provision - but the adapter implements no creation call, so the sweep reports it unsupported and the key is set by hand (PAYMENT_PROVIDER_<NAME>_WEBHOOK_SECRET_KEY). |
| `lemonsqueezy` | panel-only | false | signingSecret | The author CHOOSES the signing secret when creating the webhook in the Lemon Squeezy dashboard, and the adapter requires it to construct - so there is no secret for a create call to hand back and no live-but-unverifiable state to fix. |
| `iyzico` | panel-only | false | secretKey | iyzico webhook verification uses the configured API secretKey; there is no separate signing key to capture. Verification accepts only V3 signatures and requires the privately configured merchantId for subscription notifications, refusing them when it is absent. The merchantId is never taken from the webhook body. The webhook URL is registered in the merchant panel. |
| `mangopay` | api-no-secret | false |  | Mangopay hooks are unsigned GET requests (EventType, RessourceId, Date) and no signing secret exists. The receiver re-fetches the named resource with the adapter's own clientId + apiKey and trusts only that answer, so there is nothing to capture. Hooks are registered per EventType in the Mangopay dashboard or with POST /hooks; the adapter implements no creation call. |

## Subscription plan id origin

Per-brand ORIGIN of `sys_<X>SubscriptionPlan.providerPlanId`. This is the fact that decides whether a PRE-SEEDED providerPlanId is legitimate for a brand at all. `provider-generated` = the provider mints the reference and the adapter READS IT BACK from the create response, so any value a designer seeds by hand is wrong by construction and can only be obtained by calling createPlan (POST /v1/payments/admin/plans/provision). `caller-chosen` = the adapter derives the reference from values the caller already owns, so a seeded value is legitimate and the provisioning sweep stores the same string. Measured from each adapter's own createPlanImpl in _common/nodejs/src/common/payment-providers/. `adoption` = the brand's VENDOR-SIDE idempotency story when the local providerPlanId is null but a vendor object may already exist: `list-and-adopt` = the adapter implements listPlans and the sweep adopts an identity-matched existing object instead of minting a duplicate; `create-only` = no listPlans, a cleared providerPlanId re-mints at the vendor and the orphan is cleaned in the vendor's panel.

| Entry | origin | shape | note | adoption | adoptionNote |
|---|---|---|---|---|---|
| `stripe` | provider-generated | price_* | createPlanImpl creates a Product then a recurring Price and returns `price.id`. Stripe mints the id. | list-and-adopt | listPlans walks GET /v1/prices (recurring, active, product expanded); the product metadata carries the identity stamp - and the `code` key createPlanImpl has always stamped, which is what matches pre-stamp objects. |
| `paypal` | provider-generated | P-* | createPlanImpl creates a catalog Product then POST /v1/billing/plans and returns the plan `id` PayPal assigned. | create-only | No listPlans implemented; GET /v1/billing/plans exists but the adapter does not walk it yet, so a cleared providerPlanId re-mints and the orphan is cleaned in the PayPal panel. |
| `iyzico` | provider-generated | opaque reference code | createPlanImpl creates the product then the pricing plan and reads `pricingPlanReferenceCode` BACK from iyzico; the create call sends no reference of its own. createSubscriptionImpl then sends that value as `pricingPlanReferenceCode`, so a seeded plan code can never match. This is the brand the pre-seeded providerPlanId problem was found on. | create-only | No listPlans implemented and the pricing-plan objects carry no caller metadata to stamp, so an orphaned plan is recognised by name in the iyzico panel only. |
| `adyen` | caller-chosen | the plan code | Adyen has no plan object at all; createPlanImpl echoes `input.code` and the synthetic subscription id is `shopperReference:planCode`. Seeding the plan code is correct for this brand. | create-only | Nothing to adopt: there IS no vendor-side plan object, so a re-run mints nothing and duplicates are impossible for this brand by construction. |
| `paddle` | provider-generated | pri_* | createPlanImpl creates a Product then a Price and returns `price.id`. It falls back to the plan code only when Paddle returned no id, which is an error path rather than a contract. | create-only | No listPlans implemented; Paddle products carry custom_data the stamp could live in, which makes this brand the first list-and-adopt follow-up. |
| `lemonsqueezy` | caller-chosen | variant id, else the plan code | Variants are dashboard-managed; createPlanImpl returns `metadata.variantId` when the designer supplied one and otherwise echoes `input.code`. Seeding the variant id is the intended path. | create-only | Variants are dashboard-managed and createPlanImpl mints no vendor object, so there is nothing for a sweep to duplicate or adopt. |
| `mangopay` | unsupported |  | No createPlanImpl - the adapter inherits the base, which throws CapabilityLimitedError. There is no provider-side plan object to reference. |  |  |
| `custom` | unknown |  | Bring-your-own adapter: the project registers it, so the framework cannot state the origin. Whatever the registered createPlan returns is what the provisioning sweep stores. If it implements listPlans, the sweep list-and-adopts through it. |  |  |

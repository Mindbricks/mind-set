# RemoteBucketBasics

**Level:** `section` · **Family:** [RemoteBucket](../ontology/families.md#remotebucket) (domain `Service`)

**Ontology:** [RemoteBucketBasics in Part 1](../ontology/RemoteBucketBasics.md)

Core settings for the remote bucket including its name, description, size limits, allowed file types, and antivirus scanning.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `name` | `String` | yes |  |  | format [codeName](./value-formats.md#codename) | Unique bucket identifier within the service. Used in route paths (/bucket/{name}/ — not /remotebucket/{name}/), table names ({name}RemoteFile), and API names. Must be a valid codeName. |
| `description` | `Text` | yes |  |  |  | Human-readable description of what this bucket stores (e.g., 'Product images', 'User documents', 'Video uploads'). |
| `maxFileSizeMb` | `Integer` | no | `100` |  |  | Maximum allowed file size in megabytes. Files exceeding this limit are rejected at upload time. Default: 100 MB (remote buckets can handle larger files than DbBuckets). |
| `allowedMimeTypes` | `String` | no |  |  |  | Comma-separated list of allowed MIME types (e.g., 'image/png,image/jpeg,application/pdf'). If null, all MIME types are accepted. Each entry is either an exact 'type/subtype', a family wildcard 'type/*' (so 'image/*' accepts image/png, image/jpeg and every other image subtype) or '*/*' (any type); matching is case-insensitive and ignores ';' parameters, and any other shape (no slash, '*/png', ...) fails generation naming the bucket and the entry. NOTE: the runtime additionally sniffs the file's magic bytes via the file-type package — declared signature-bearing types must match the known sniff, regardless of the bucket allow-list; unknown signatures are refused. The only compatible exceptions are APNG declared PNG and Illustrator PDF declared PDF with a %PDF- container; these keep their declared type. ACTIVE CONTENT (HTML, XHTML, SVG, every JavaScript type, XML and any +xml type) is kept as its type only when that exact type is listed here; a wildcard ('image/*', '*/*') or no list does not admit it. An upload whose bytes, declared type or file name say active content and that is not listed by its exact name is still accepted but stored as application/octet-stream, its original name kept and its active extension left out of the storage key. Active objects default to attachment; serveActiveInline permits an exact declared type only on an isolated storage origin: DbBucket downloads always send X-Content-Type-Options: nosniff and Content-Disposition: attachment (plus Content-Security-Policy: default-src 'none'; sandbox for an active type), and a presigned download of an active object is signed with an attachment disposition and application/octet-stream. Generated by the nodejs, java, dotnet and python lanes. |
| `virusScan` | `Boolean` | no | `false` |  |  | When true, every uploaded file is scanned by ClamAV (configured under projectSettings.clamAvSettings, defaults to the platform ClamAV REST service, the field's default value) BEFORE it is written to the storage provider. Auto-promoted to true at generation time when bucketAuthorization.readAccess is 'public'. Adds scanStatus / scanResult / scannedAt columns to the generated {name}RemoteFile data object. WHERE THE GUARANTEE APPLIES: the bytes of a RemoteBucket live in the storage provider and never in the row, so unlike a DbBucket this scan cannot move down to row creation - there is nothing in a {name}RemoteFile row to scan. It covers exactly the through-server upload route (POST /bucket/{name}/upload). Two paths are therefore NOT scanned and the designer must choose them knowingly: a presigned PUT from /upload-url goes straight to the provider without passing through this service, and a business api that writes a {name}RemoteFile row itself records a storageKey for bytes nothing here ever saw. An intake that must accept files from anonymous or untrusted callers should use a DbBucket, whose scan is attached to the row. Scanned buckets emit /upload-url only with allowPresignedUpload: true; validation warns whenever scanning and that opt-in are both enabled. |
| `virusScanMode` | `BucketVirusScanMode` | no |  | `block`, `quarantine` |  | How the upload route responds when ClamAV reports an infection - for a RemoteBucket this is a property of that route, because the bytes never enter a row (see virusScan above). 'block' rejects the upload with HTTP 422 and nothing is written to the remote provider. 'quarantine' uploads to a quarantine key prefix and persists the row with scanStatus='infected', refusing both presigned URLs and proxy downloads of infected records. If null, falls back to projectSettings.clamAvSettings.configuration.defaultMode (default: 'block'). That resolution happens at DESIGN time and is baked into the generated service as a literal. A deployment can still override it at runtime by setting the CLAMAV_DEFAULT_MODE env var to 'block' or 'quarantine' (an operational escape hatch that works in both directions); leaving it unset, empty or unrecognised means no override and this per-bucket value wins. Lane status: honoured in nodejs, dotnet, python, php and golang (golang bakes the per-bucket literal and lets CLAMAV_DEFAULT_MODE override it in both directions), and rust honours it but cannot be overridden back down to 'block'. |
| `imageVariants` | [`ImageVariant`](./ImageVariant.md)[] | no |  |  |  | Resized copies (thumbnails, previews) the bucket creates for every image it stores. Each entry names one variant (`thumb`, `preview`, ...) and how to produce it; the declaration compiles into the generated upload route, which creates every variant SYNCHRONOUSLY with the `sharp` image library right after the original is written, before it answers. The ORIGINAL is stored unchanged; a variant is a separate object in the SAME bucket at the deterministic key `<original key without extension>__<variant name>.<format>` (for example `catalog/abc.jpg` gives `catalog/abc__thumb.webp`), auto-oriented from EXIF and stripped of metadata. The result is recorded on the `{name}RemoteFile` twin row in its `variants` column as `{ <name>: { key, url, width, height, format, size } }` and returned by the upload response; because the twin row is what the bucket's create and update events carry, a service that copies the file into a snapshot reads `variants.<name>.url` from the event. The `url` is the bucket's own download route with `?variant=<name>` (`{SERVICE_URL}/bucket/{name}/download/<original key>?variant=<name>`), which redirects to a presigned URL of the variant and falls back to the original (header `X-Bucket-Variant: original`) when the variant is not recorded. Only images the bucket itself stores are processed, recognised by their BYTES (a jpeg, png, webp, gif, avif/heif or tiff signature; an svg or any other document gets none, whatever type it declares), uploaded through POST /bucket/{name}/upload (and the in-process writeBucketObject helper). Inputs above 50 megapixels are a recorded failure, and at most IMAGE_VARIANT_MAX_CONCURRENCY (default 2) variants render at once per process. A variant object is served only through ?variant= on its original; its own key answers 404 on the download and delete routes. Other content types, quarantined uploads and presigned /upload-url uploads (whose bytes never pass through the service) get no variants and never fail because of them; external URLs are never fetched. A variant that cannot be produced does NOT fail the upload: the original is kept, the upload answers ok, and the variant is recorded as `{ error }` so the admin backfill route POST /bucket/{name}/variants/backfill (admin roles) can create it later; that route also creates the variants of objects stored before the declaration, page by page, and skips variants that already exist. Deleting the original through DELETE /bucket/{name}/object/:key also deletes its variants. Declaring variants adds the `sharp` npm dependency to the generated service. Implemented for RemoteBucket in the nodejs target; on a NativeBucket the declaration is accepted with a warning and has no effect yet. |
| `allowPresignedUpload` | `Boolean` | no | `false` |  |  | Explicit opt-in to emit /upload-url when effective virusScan is enabled. Default false. Without it scanned buckets accept bytes only through /upload. Unscanned buckets keep /upload-url. A scanned opt-in bucket reports VIRUS_SCAN_BYPASSED_BY_PRESIGNED_INTAKE because direct provider PUTs are not scanned. Clients must echo every returned upload header; S3 and GCS bind Content-Type and the storage key in the signature. Azure relies on inert download serving. |
| `serveActiveInline` | `Boolean` | no | `false` |  |  | Explicit opt-in for inline active content, default false. Only exact active allowedMimeTypes entries and recorded types qualify. The actual signed storage origin must be HTTPS on a host whose registrable domain matches SERVICE_URL, FRONTEND_URL, ALLOWED_ORIGINS or COOKIE_DOMAINS; provider/shared hosting domains are always refused; both SERVICE_URL and FRONTEND_URL must be configured. Unrelated or provider storage hosts and unknown metadata stay inert. DbBucket refuses this field and proxy responses keep sandbox CSP. Public delivery continues to refuse active types. Supported in nodejs, dotnet and java; other runtimes require ports. |

## Constraints

Property rules:

- `name`, `description` must be present. (`REQUIRED_FIELD_MISSING`)
- `virusScanMode` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- `name` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)
- The items of `imageVariants` must have distinct names (`name`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)

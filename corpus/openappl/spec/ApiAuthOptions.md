# ApiAuthOptions

**Level:** `section` · **Family:** [BusinessApiBasics](../ontology/families.md#businessapibasics) (domain `BusinessApi`)

**Ontology:** [ApiAuthOptions in Part 1](../ontology/ApiAuthOptions.md)

Defines core authentication and authorization settings for a Business API. These settings cover session validation, role and ownership checks, and access scope (e.g., tenant vs. SaaS-level). While these options are sufficient for most use cases, more fine-grained access control—such as conditional permissions or contextual ownership—should be implemented using explicit access control actions (e.g., `PermissionCheckAction`, `MembershipCheckAction`, `ObjectPermissionCheckAction`).

| `apiInSaasLevel` | `Boolean` | no | `false` |  |  | If true, this API is a SaaS-LEVEL (cross-tenant) surface, and the CONSEQUENCE is the point: it removes tenant isolation from this api's reads. In a multi-tenant project every read and every scoped write (get/list/update/delete) on a tenant-level DataObject is otherwise AND-ed with `{ <tenantName>Id: this._tenantId }` (the MANAGER slot - there is no generic `session.tenantId`) (and the tenant ROOT object is pinned to the caller's own row by `id`); `apiInSaasLevel: true` drops that term entirely, so this api reads - and, on a scoped write, mutates - rows belonging to EVERY tenant. That is exactly how a deliberate cross-tenant surface is built (a public catalogue or job board, a SaaS-admin console, cross-tenant analytics), and it is also indistinguishable in the blueprint from the same flag left behind by accident - copying a board api as the template for a tenant-scoped list is the shape that bites. So when the api reads tenant-level data, NAME what you are exposing in `crossTenantScopeOf`: an undeclared pairing is reported as SAAS_LEVEL_TENANT_READ_UNDECLARED, and a declaration naming a source the api does not read is refused as CROSS_TENANT_READ_DECLARATION_MISMATCH. Gate the api itself with `checkRoles`/`absoluteRoles` naming SaaS-level roles unless the surface is genuinely public. |
| `crossTenantScopeOf` | `String` | no |  |  |  | DECLARES that this api's cross-tenant reads are deliberate, by NAMING the read source whose tenant isolation `apiInSaasLevel` waives. Write the api's own `apiOptions.dataViewName` when the api reads a DataView, otherwise its `apiOptions.dataObjectName`; matching is case-insensitive and a `service:` prefix on an object name is ignored. WHY A NAME AND NOT A YES/NO FLAG: the accident this guards against is copying a deliberate cross-tenant api as the template for a tenant-scoped one, and a boolean would be copied along with it unchanged, still reading `true`. A name is not - retarget the copy at another view or object and the declaration no longer matches what the api reads, which is refused as CROSS_TENANT_READ_DECLARATION_MISMATCH. Leave null when this api is not a cross-tenant surface: declaring it without `apiInSaasLevel: true` waives nothing and is reported as CROSS_TENANT_READ_WITHOUT_SAAS_LEVEL. NAMED FOR THE COMMON CASE, NOT A LIMIT: `apiInSaasLevel` lifts the tenant term from an api's scoped WRITES too (a SaaS-level update/delete addresses any tenant's row), and one declaration covers whichever the api does - the source named is the `dataViewName`/`dataObjectName` the api is pointed at, not the verb. |
| `M2MAllowed` | `Boolean` | no | `false` |  |  | If true, this API ACCEPTS machine callers: a caller presenting a VERIFIED `x-m2m-token` and no user identity passes checkValidLogin / checkBasicAuth instead of being refused. It WIDENS the login gate; it is not a gate of its own, and it is a statement about what the API ALLOWS, never about who called (the CALLER-side answer is `this.isM2M`, and a guard reading `M2MAllowed` instead is true for every caller of an M2M-allowed api). `loginRequired: true` + `M2MAllowed: true` IS NOT A MACHINE-ONLY FORM. This doc called it one until the consequence was measured: six apis authored in exactly that pair, with no `checkRoles` beside it, let a plain tenantOwner read ANOTHER tenant's plan, seat and quota state. The login gate opens for a user session exactly as it does for a machine token, so anonymous is the only caller the pair excludes. To REFUSE human callers, declare `requiredCallerKind` beside it — that is the flag that narrows, this one only widens.  THE FOUR CALLERS. "Machine vs human" is two rows; the runtime has four, and the fourth is the one a designer cannot predict and the one their traffic actually carries — `InterService.call` attaches `x-m2m-token` unconditionally and forwards the caller's bearer when `forwardCallerToken` is set, so an ordinary end user proxied through a service-to-service hop arrives carrying BOTH signals:  \| caller \| isM2M \| session owner \| loginRequired:true + M2MAllowed:true \| ... + requiredCallerKind: machine \| ... + requiredCallerKind: machineWithoutUserIdentity \| \|---\|---\|---\|---\|---\|---\| \| anonymous \| false \| null \| 401 \| 401 \| 401 \| \| an INTERACTIVE user session \| false \| set \| PASSES (the hole) \| 403 \| 403 \| \| a session-less machine token \| true \| null \| passes \| passes \| passes \| \| a user FORWARDED on an InterService hop \| true \| set \| passes \| PASSES \| 403 \|  `loginRequired: false` does the OPPOSITE of what it looks like here — it switches the whole authorization pipeline off (ApiManager short-circuits every role, permission and ownership check on that flag, checkValidLogin included, and no checkBasicAuth override is emitted), so the endpoint answers ANONYMOUS callers and M2MAllowed beside it demands nothing. There is no M2M-ONLY gate for a Business API; `loginRequired: false` means PUBLIC. Declaring the pair explicitly is reported as PUBLIC_API_WITH_M2M_ONLY_INTENT. (EdgeControllers are a different pattern with a different runtime and do carry an m2m auth mode — see EdgeControllerOptions.) |
| `requiredCallerKind` | `ApiRequiredCallerKind` | no | `"any"` | `any`, `machine`, `machineWithoutUserIdentity` |  | WHO may call this api, as a demand on the CALLER — the narrowing counterpart to `M2MAllowed`, which only widens. `M2MAllowed` is what the API DECLARES it tolerates; `requiredCallerKind` is what the caller must TURN OUT TO BE, measured at runtime from the verified `isM2M` identity or the Kafka dispatch transport. Default `any` — no caller-kind demand, exactly the behaviour every api had before this field existed, so a project on the old spelling is unaffected.  `machine` is the machine-only gate the platform used to have no way to express. It refuses an INTERACTIVE user session with 403 `M2M_CALLER_REQUIRED` and admits a machine caller — INCLUDING an end-user identity forwarded on an ordinary InterService hop, which carries `x-m2m-token` and is therefore `isM2M`. That is the DEFAULT reading of "machine callers only" on purpose: measured live on the reporting project, the narrow line would have cut invitation-accept and job publishing, which reach these apis through exactly such a hop.  `machineWithoutUserIdentity` is the labelled EXCEPTION: machine caller AND no user identity resolved at all, so it ALSO REFUSES the forwarded hop (403 `M2M_CALLER_WITHOUT_USER_IDENTITY_REQUIRED`). Declare it only for an api that must never run on behalf of a person — a key-rotation or tenant-provisioning surface — and expect it to refuse any internal caller that forwards its bearer. If you are unsure which you want, you want `machine`.  BOTH refuse before any role, permission or ownership gate and are NOT bypassed by `absoluteRoles`: an absolute role is a statement about a PERSON, and the point of this field is that no person may call. Cron and in-process `internal` triggers are exempt — they have no HTTP caller and already run as a trusted system job, the same exemption `checkValidLogin` makes. A KAFKA dispatch (the api's `kafkaSettings` consumer) satisfies the machine half of this gate too: no human stands behind a consumed event, and framework-published events (dbEvents, route events) carry no `x-m2m-token`, so `machine` admits every message the kafka controller dispatches instead of answering 403 `M2M_CALLER_REQUIRED` and dropping it. That is the ONLY gate kafka satisfies — it is not a trusted system job: `loginRequired`, the role, permission and ownership gates still run against the session the event carries (its `actor`), and `machineWithoutUserIdentity` still refuses an event whose `actor` names a user, which a framework dbEvent usually does (it carries the originating user). Current design-time validation requires `M2MAllowed: true` beside a machine kind on a `loginRequired: true` api (MACHINE_CALLER_KIND_WITHOUT_M2M_ALLOWED). This admits session-less token callers through the login gate; Kafka events carrying a user actor still undergo ordinary user login checks. A `checkRoles` list beside a machine kind currently produces MACHINE_CALLER_KIND_WITH_ROLE_GATE. That warning does not disable roles: a Kafka actor or a user forwarded on an InterService hop can carry a role, and the runtime still enforces the declared role gate for that identity. See `M2MAllowed` for the four-caller table. The auth role-write door needs `machineWithoutUserIdentity`: an authored auth api may write the user's `roleId` only when no session-bearing caller, forwarded identity included, can reach it; `machine` does not open it. Lane status: this gate is enforced in nodejs, python, dotnet, java, rust and golang. Its carry onto the JobStream enqueue edge (JobStreamAccess.enqueueAccess) is enforced in all of them except golang, whose enqueue gate does not carry the caller-kind field yet. |
| `loginRequired` | `Boolean` | no | `true` |  |  | Specifies whether the user must be authenticated to access the API. By default, this inherits the login requirement from the associated data object, but it can be overridden here. `false` means PUBLIC, and it is not one relaxed flag beside the others: it turns the WHOLE authorization pipeline off. No checkBasicAuth override is generated, the role lists never reach the manager, and ApiManager short-circuits checkValidLogin, every role, permission, ownership and parent-ownership check on this single flag — including the M2M demand, so `M2MAllowed: true` beside it gates nothing. Pairing it with a role/permission/ownership gate is refused as PUBLIC_API_WITH_ROLE_GATE, and pairing it with an explicit `M2MAllowed: true` is reported as PUBLIC_API_WITH_M2M_ONLY_INTENT. |
| `queueTokenRequired` | `String` | no |  |  |  | The name of a `WaitingRoom` (services.waitingRooms[].roomBasics.name or its codeName in THIS service; the stamp is the room key, codeName when set, else name) whose admission `QueToken` this API requires. An ADDITIONAL gate beyond login/M2M (M2M-parity in shape): when set, the API stays publicly routed but the caller must present a valid, unexpired, queue-scoped QueToken minted by that WaitingRoom; the codegen pass emits a Redis one-shot check (token exists + not consumed + matches this room) that consumes the token on success (per the room's QueTokenSettings.singleUse). Empty/absent = no admission gate. This is the only BusinessApi change a WaitingRoom binding implies (the WaitingRoom binding sets this automatically when it fronts the API; it can also be declared by hand). Combine with loginRequired/checkRoles as usual. |
| `ownershipCheck` | `Boolean` | no | `false` |  |  | Defines whether ownership should be enforced on the main data object. This check restricts access to the object’s owner and will be applied via the query in list operations and after the instance is fetched in others. On golang a DataView read (apiOptions.dataViewName on a list or get api) and a serviceLayerCall api carry no ownership gate, so declaring it there is the non-bypassable validation error API_AUTH_GATE_NOT_GENERATED (the same for permissionCheck and foreignPermissionCheck). |
| `parentOwnershipChecks` | [`ApiParentOwnershipCheck`](./ApiParentOwnershipCheck.md)[] | no |  |  |  | A list of PARENT-ownership gates. Where `ownershipCheck` gates on the caller owning THIS object, each entry here gates on the caller owning a PARENT record the request is created under or acts on. At runtime the generated manager fetches the parent row named by `parentObject` using the id carried in the request field `parentIdField`, and DENIES (403) unless the parent row's `ownerField` equals the session userId (a missing parent row is also a 403). This expresses the create-under-parent / modify-child-if-you-own-the-parent case that `ownershipCheck` cannot (no target row exists yet on a create) and that `permissionCheck` cannot (RBAC/membership, not ownership). Runs right after `checkBasicAuth`, before the main operation. Empty = no parent-ownership gate. |
| `absoluteRoles` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | A list of role names that grant unconditional access to this API in terms of authentication and authorization. Users with any of these roles will bypass all auth checks—including role, permission, ownership, and membership and custom 401-403 validations. However, business-level validations (e.g., required fields, value constraints) will still apply to ensure domain correctness. NOT THE WHOLE LIST THE GENERATED CODE GETS: every login-required api is EMITTED with `superAdmin` in its absolute-role list whether or not it appears here, and `tenantOwner` is added automatically wherever the tenant filter is in force on the api (a tenant-scoped object, and not a SaaS-level api). Exactly those two roles are automatic - not `tenantAdmin`. Those operator roles live one layer BELOW the blueprint on purpose - a blueprint default invites exceptions and drifts, and a designer or an agent that forgets them is exactly how a legitimate operator, or a tenant owner on their own tenant, ends up refused - so do not add them here and do not expect to read them back here. Whatever you DO declare survives: the emitted list is the UNION of your entries with the automatic ones, de-duplicated case-insensitively (the same case-folded role identity the runtime compares with), never a substitution. The `tenantOwner` arm RIDES THE TENANT FILTER for a reason: an absolute role bypasses every authorization check but NEVER the tenant scope, so on a tenant-scoped api the owner reaches its own tenant and nothing else. Where no tenant filter stands behind the gate - a SaaS-level api (`apiInSaasLevel: true`), an api over a non-tenant-scoped object such as a shared catalog, or a CREATE api (a create emits no where clause at all, so no tenant term ever rides it - only the create-time session stamp, which an authored tenant-column `dataClauseItems` entry overrides by design) - `tenantOwner` is NOT automatic, because that is exactly the surface where making it automatic once produced a live privilege escalation (anyone who registered their own tenant listing all tenants, editing the shared plan catalog, writing billing rows, or minting a row straight into another tenant through a provisioning create); there, only `superAdmin` is automatic and you declare any tenant role you need yourself. The automatic roles are added only where the gate can run: `loginRequired: false` switches the whole authorization pipeline off, so a public api still emits exactly what it authored. None of this reaches tenant isolation - the tenant filter is assembled separately and is never bypassed by an absolute role, and `apiInSaasLevel` remains the only declared cross-tenant surface. The bypass includes the FOREIGN permission gate (`foreignPermissionCheck`): a session holding an absolute role - authored here or one of the automatic `superAdmin` / `tenantOwner` pair - skips the project's `foreignPermissionProvider` exactly as it skips the native role, permission and ownership gates; the provider is never called for it (no round-trip, so an unreachable provider does not refuse it either), and there is no per-api opt-out. absoluteRoles ALONE IS NOT A GATE: with no checkRoles, enforceable ownershipCheck, permission check, liveCheck membership check, 401/403 validation, session-scoped whereClause, membershipFilters entry (list apis) or well-formed parentOwnershipChecks entry (only where the generated manager carries that gate: not on the retired php lane) beside it, every other logged-in user falls through and can call the api. The validator reports that shape as ABSOLUTE_ROLES_WITHOUT_GATE - an ERROR everywhere: validateProject / validateService fail, every build and regeneration fails, and a normal save of the project, service, api or its auth block is refused - for an api saved long ago exactly as for a new one. Add checkRoles (usually the same roles, e.g. absoluteRoles: ["admin"] with checkRoles: ["admin"]) to make it operator-only, set an enforceable ownershipCheck if the row's owner may call it, declare a parentOwnershipChecks entry (parentObject, parentIdField, ownerField) if the owner of the PARENT row may call it, or remove absoluteRoles (keep loginRequired: true) if it is meant to be open to every logged-in user. A save that must land before the fix (two errors blocking each other's fix) may pass skipValidation: true, which skips every save-time check; validate and build still report it. CART READS: on a get / list api over the shopping cart object this list holds operator roles only - superAdmin, admin, saasAdmin in a single-tenant project; superAdmin, saasAdmin in a multi-tenant one, plus tenantOwner / tenantAdmin only where the api's tenant filter is in force (a tenant-level cart object and no apiInSaasLevel; the auto-generated cart is tenant-level in a multi-tenant project generated in nodejs, and platform-level elsewhere), because a tenant administrator bypasses the owner gate but not the tenant scope and would otherwise read every tenant's carts. Anything else is CART_READ_API_SHOPPER_ABSOLUTE_ROLE (ERROR, non-bypassable). CART LINES AND CART READ ACTIONS: the same rule holds on a get / list api over the cart item object and on an api holding a read action onto the cart or its lines - tenantOwner / tenantAdmin count as operators only where that read's tenant filter is in force (the item api's own filter, or the action's tenant pin on its target; the auto-generated cart item is tenant-level in a multi-tenant nodejs service), and the tenantOwner the generated gate adds on its own counts too; anything else is CART_READ_SURFACE_NOT_SCOPED (ERROR, non-bypassable). Undefined designer gate roles receive the UNDEFINED_GATE_ROLE warning, including entries in absoluteRoles. |
| `checkRoles` | `String`[] | no |  |  | format [codeName](./value-formats.md#codename) | A list of roles that are required to pass basic role checks for this API. These are not absolute—users with these roles still undergo other validations and access control checks unless also included in `absoluteRoles`. Multiple roles are combined using OR logic. CART LINES AND CART READ ACTIONS: on a get / list api over the cart item object, or an api holding a read action onto the cart or its lines, this list holds operator roles only - superAdmin / admin / saasAdmin single-tenant; superAdmin / saasAdmin multi-tenant, plus tenantOwner / tenantAdmin only where that read's tenant filter is in force (the auto-generated cart item is tenant-level in a multi-tenant nodejs service); anything else is CART_READ_SURFACE_NOT_SCOPED (ERROR, non-bypassable). Designer API gates naming a role absent from the project receive UNDEFINED_GATE_ROLE as a warning; on a login-required api a list whose EVERY name is undefined is UNDEFINED_GATE_ROLE as an error (the api admits no defined-role session), unless `absoluteRoles` names a defined role, which keeps the warning. A business membership accessLevel is not a session role. Framework-injected APIs and project-free validation are exempt. |
| `foreignPermissionCheck` | [`ApiForeignPermissionCheck`](./ApiForeignPermissionCheck.md) | no |  |  |  | Opt this API into the project's FOREIGN permission server (declared once on `authentication.foreignPermissionProvider`). When both this and the project provider are present, the runtime gate sends a request shaped from `foreignPermissionCheck.params` (a free MScript map evaluated against the api context `this`) plus the provider's `sessionBindings` to the foreign policy engine and denies (403 by default) when the server's response trips the provider's `denyWhen`. The params are whatever the permission server expects — the framework does not interpret the keys. Leave null for no foreign check. Not asked for an absolute-role session: `absoluteRoles`, including the automatic `superAdmin` / `tenantOwner` pair, bypasses this gate like every other authorization check, with no per-api opt-out; the tenant filter still applies. |
| `permissionCheck` | [`ApiPermissionCheck`](./ApiPermissionCheck.md) | no |  |  |  | Opt this API into the project's NATIVE permission resolver (ADR-native-permission-system §10). When set, the runtime gate calls `decide(permission, objectId, on, ctx)` on the project's permission manager and DENIES (403) when the layered resolution (object/user override → membership → global role → ownership) returns `{ effect: 'DENY' }`. `permission` is a declared `PermissionGroup` permission name; the optional `on` is a PropRefer to a request field carrying the parent/scope object id (for membership-role checks against a parent). Runs at a TYPE level right after `checkBasicAuth` (covers create/list — no objectId) AND at an OBJECT level after the instance fetch (get/update/delete — objectId available). Null = no native check (legacy `checkRoles`/`ownershipCheck` resolve byte-identically to today).  REQUIRES PERMISSION MANAGEMENT — `authentication.accessControl.permissionBasics.pbacIsActive` must be on. With it off the permission resolver IS NEVER GENERATED, so the gate is emitted against nothing and answers DENY (deny-by-default) before ANY layer runs: not the store-backed layers, not the CONFIG-ONLY membership layer, not even the absolute-role bypass. Every caller is refused — the record's own owner and superAdmin included — with a message that reads like a policy decision rather than a missing resolver, and a guarded `list` narrows to zero rows through the same deny-closed filter. This is a design-time ERROR (`PERMISSION_CHECK_WITHOUT_PBAC`). Enabling PBAC is a project-wide decision to adopt permission management, not the local fix for one api: without it, gate on `checkRoles`/`absoluteRoles`, `ownershipCheck`, or a MembershipCheckAction's `requiredRoles`.  REACHED FROM AN AI AGENT TOOL: an agent tool bound to this api on the same service (an `apiTools` entry, or a `crudScopes` CRUD tool whose operation this api serves) runs this gate with the CALLER's session manager, so the verdict is the one the same caller gets over REST. A run with no HTTP caller (a Kafka- or cron-triggered agent, a run resumed after an approval pause or a restart) carries no session manager, and the gate then REFUSES the tool call (403) instead of passing it. Gate an api that an event-driven agent must call with `checkRoles` / `ownershipCheck` instead. REACHED FROM A KAFKA CONTROLLER OR A JOBSTREAM WORKER: neither door carries a session manager (the identity is the event envelope's actor, or the session the enqueue gate forwarded), so the permission cannot be decided there and the call is REFUSED (403) - a JobStream job is marked failed - after the api's absoluteRoles and a verified machine caller it admits, which still pass; cron and internal calls keep their bypass. Validation warns about such an api (PERMISSION_CHECK_ON_CALLERLESS_DOOR). Gate an event-driven api with `checkRoles` / `absoluteRoles`, or `ownershipCheck` where it applies. REACHED FROM A GRPC CONTROLLER: the session manager is attached to a gRPC call only when its credential resolves a session, and such a call is decided exactly as over REST; a call that resolved no session is REFUSED (403, PERMISSION_DENIED) after the same absoluteRoles and machine-caller arms. It reaches the gate only when `loginRequired` is false, and validation warns about that combination with a gRPC controller (PERMISSION_CHECK_ON_CALLERLESS_DOOR, door grpc); set `loginRequired: true` to have every gRPC caller decided. |
| `machineSessionRetirement` | `Boolean` | no | `false` |  |  | Grants this api ONE machine capability: retiring every session of the user the api itself resolved. Only on an authored auth api (`authentication.businessLogic`) whose main data object is `user`, with crudType `get` or `update`, `M2MAllowed: true` and `loginRequired` left on; the validator refuses it anywhere else (MACHINE_SESSION_RETIREMENT_OUTSIDE_AUTH, MACHINE_SESSION_RETIREMENT_SHAPE) and on an auth service generated in a language that does not emit it yet (MACHINE_SESSION_RETIREMENT_LANGUAGE; nodejs, java, dotnet and rust emit it). The framework then binds a retire action right after the main operation (`afterMainGetOperation` / `afterMainUpdateOperation`, which run only when the operation resolved a row), so EVERY successful call retires the addressed user's sessions: access sessions, refresh families and owner-index entries, plus the user's invalidation epoch, which also ends cached api-key sessions and any session the owner index never held; the userSession rows of the retired sessions are marked loggedOut. WHO may retire: a VERIFIED, ADMITTED `x-m2m-token` caller that names no user (a token naming a user is that user, not a machine), and only within the target's own tenant: in a multi-tenant project the user's tenant must be the tenant the request resolved, and a token that signs a `callerTenantId` must name that same tenant; a superAdmin account is refused (403 MACHINE_SESSION_RETIREMENT_REFUSED). A person calling the same api keeps the self / admin gate of the session store, unchanged. The target is never a request value: it is the row the api's own (tenant-pinned) main operation read. Typical use: a machine-only `blockAccount` update api that writes the blocked state and, with this flag, ends the account's sessions in the same call. |
| `requireApproval` | [`ApiApprovalRequirement`](./ApiApprovalRequirement.md) | no | `null` |  |  | Step-up APPROVAL for a critical operation: the api answers its first call with 403 APPROVAL_REQUIRED and sends a one-time code to the caller's own verified email or mobile. The caller repeats the SAME request with `api-approval-id` and `api-approval-code` (REST: headers, or the same two fields in the JSON body; gRPC / MCP: the request envelope; never the query string) and the api runs. The 403 is the EXPECTED first answer of such an api, not a failure: a frontend shows a code input and retries, a test treats it as a step. The challenge rides the problem body's `errors` member: `{ approvalId, channel, codeIndex, expireTime, expiresAt, actionName, actionDescription }`.  WHERE THE GATE SITS: a fixed milestone of the api pipeline, never a designer stage. It runs AFTER every authorization check (login, checkRoles / absoluteRoles, permissionCheck, ownershipCheck, parentOwnershipChecks, the parameter checks and every hook up to afterCheckBasicAuth) and BEFORE the first stage that may write: for create / list / a get that fetches no instance, right before buildWhereClause / buildDataClause; for update / delete and an ownership-checked get, right after afterCheckInstance and the object-level permission check, before buildDataClause and the main operation. So a caller who is not allowed to run the api can never make it send a code, and nothing from buildDataClause on runs before the approval. An action that writes the database in a stage BEFORE the milestone runs on the challenged first call too, which is reported as APPROVAL_GATE_AFTER_WRITE.  BOUND TO THE INPUT (`bindInput`, default true): the code approves exactly this user, this api of this service and the canonical digest of the api's declared request parameters (the `useIdempotencyKey` hash rule). A retry with a changed parameter, another api, another user, a wrong, expired or already used code is refused with ONE failure shape, 403 APPROVAL_INVALID. A wrong code or a changed input counts an attempt; the fifth destroys the approval, and a new call without `api-approval-id` starts a new one. A second first call inside 60 seconds with the same input answers the same challenge again without a second message; with another input it answers 429 APPROVAL_RESEND_WINDOW.  TEST MODE: on the preview and dev deployments the challenge also carries the code (`errors.secretCode`), so a harness or a designer completes it without a mailbox; on stage and production it never does. DOORS: cron and in-process internal calls pass; a kafka-consumed or job-stream call, a machine caller with no user and an agent run with no caller are refused 403 APPROVAL_NOT_AVAILABLE (nobody there can receive a code); an idempotent replay (`useIdempotencyKey`) answers the response the approved execution stored. Over SSE the stream's error frame carries APPROVAL_REQUIRED but not the approvalId, so a streaming client takes the challenge from the REST route first (APPROVAL_ON_SSE_CONTROLLER). Requires `loginRequired: true` (APPROVAL_REQUIRES_LOGIN), no machine-only `requiredCallerKind` (APPROVAL_ON_MACHINE_API), a channel whose identity is REQUIRED on the project's users (APPROVAL_ON_OPTIONAL_IDENTITY) and, until the remaining language lanes port it, a nodejs, dotnet, java or rust service (APPROVAL_NOT_PORTED: another lane would run the api unapproved). It is the ONLY approval surface: the standalone action-approve verification flows are retired, and approving from another device by a link is not supported yet. Leave null for an ordinary api. |

## Constraints

Property rules:

- `requiredCallerKind` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- `absoluteRoles`, `checkRoles` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)

Pattern rules:

| Code | Severity | Rule |
| --- | --- | --- |
| `FOREIGN_PERMISSION_CHECK_EMPTY_PARAMS` | warning | foreignPermissionCheck is declared but foreignPermissionCheck.params is empty. |
| `MACHINE_CALLER_KIND_WITH_ROLE_GATE` | warning | authOptions.checkRoles is declared beside requiredCallerKind:'…', and it can admit nobody. |
| `MACHINE_CALLER_KIND_WITHOUT_M2M_ALLOWED` | error | authOptions.requiredCallerKind:'…' is declared on a loginRequired:true api that does not declare M2MAllowed:true, and that pair refuses EVERY caller. |
| `MACHINE_SESSION_RETIREMENT_OUTSIDE_AUTH` | error | authOptions.machineSessionRetirement is declared on an api outside the auth service. |
| `PERMISSION_CHECK_AND_CHECKROLES` | warning | Both permissionCheck (native permission resolver) and checkRoles (legacy role-in-list) are set on this api. |
| `PERMISSION_CHECK_SCOPE_FIELDS_SHAPE` | error | permissionCheck.scopeFields …. |
| `PERMISSION_CHECK_UNKNOWN_PERMISSION` | error | permissionCheck.permission "…" is not declared in any project PermissionGroup. |
| `QUEUE_TOKEN_WAITINGROOM_UNKNOWN` | error | queueTokenRequired "…" does not match any waitingRooms[].roomBasics.name or codeName in this service. |

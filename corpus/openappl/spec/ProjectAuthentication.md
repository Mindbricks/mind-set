# ProjectAuthentication

**Level:** `module` · **Family:** [ProjectAuthentication](../ontology/families.md#projectauthentication)

**Ontology:** [ProjectAuthentication in Part 1](../ontology/ProjectAuthentication.md)

Defines the authentication and authorization configuration for the entire project. This module serves as the foundation for user identity, login behavior, access control, and verification flows. All services in the project, especially user services, rely on these centralized settings.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `authenticationEssentials` | [`AuthBasics`](./AuthBasics.md) | yes |  |  |  | Basic authentication settings for the project. Defines the core authentication method (e.g., email/password, token-based) and global authentication behaviors. |
| `loginDefinition` | [`LoginDefinition`](./LoginDefinition.md) | yes |  |  |  | Specifies how users, user groups, and tenants are defined in the project's data model. These definitions allow the generated service to dynamically extract identity and authorization data from project-specific data objects. |
| `verificationServices` | [`VerificationServices`](./VerificationServices.md) | yes |  |  |  | Defines optional verification flows such as password reset, email confirmation, mobile verification, and 2FA. An OpenAPPL compiler automatically generates the required backend logic for these features under the user service. |
| `accessControl` | [`AccessControl`](./AccessControl.md) | yes |  |  |  | Specifies permission-based access control settings. These govern what users or roles can access, based on project-wide authorization rules. |
| `socialLogins` | [`SocialLoginSettings`](./SocialLoginSettings.md) | no |  |  |  | Configuration for allowing users to sign in or register using external identity providers. Supported providers include Google, Apple, Facebook, Microsoft, LinkedIn, GitHub, and GitLab. |
| `sessionGeoSensitivity` | [`SessionGeoSensitivity`](./SessionGeoSensitivity.md) | no |  |  |  | Location-sensitivity rules for sessions. The generated service resolves the client's geo-location (country/region/city) from the internal geoip-service at login and stamps it onto the session and userSession record. When active, you can require a step-up (email/SMS verification) or force re-login when a login arrives from a location the user has not used before, and/or invalidate a live session when its request location drifts. Leave inactive to keep location enrichment without enforcement. |
| `foreignPermissionProvider` | [`ForeignPermissionProvider`](./ForeignPermissionProvider.md) | no |  |  |  | Optional delegation of per-BusinessApi authorization to a FOREIGN permission server (a centralized policy engine), declared once here and generated into EVERY service. When set, any BusinessApi that opts in via `basics.authOptions.foreignPermissionCheck` sends a request (shaped from the api's MScript params + the caller's session bindings) to this server over gRPC or REST and is denied (403 by default) when the server's response trips `denyWhen`. The provider is a project constant (one server, one transport); the per-api QUESTION is independent of the data pattern. Leave null to keep the generated service's built-in authorization only. |
| `profileSettings` | [`ProfileSettings`](./ProfileSettings.md) | no |  |  |  | Declares whether OTHER people may read a user's profile, and which of the user's own custom properties they see. The auth service generates `GET /userprofiles/:userId` by default: it serves the display identity (the user object's own name shape — `fullname`, or `name` + `surname` — plus `avatar`) and every property listed in `publicFields`, so an app can always render WHO a record belongs to. Switch it off with `hasPublicProfile: false` for projects where users must stay invisible to each other; then no profile route is generated at all and `GET /users/:userId` remains owner/admin-only, which is the auth service's confidentiality posture for the full user record. The AUDIENCE is an independent decision: `loginRequired` (default true) shares the profile with logged-in users only; `loginRequired: false` is the deliberate widening to anonymous callers. For a richer profile (cover images, social links, follower counts) model a separate profile DataObject in a business service, linked by `userId`; this block stays the identity surface. |
| `userProperties` | [`DataProperty`](./DataProperty.md)[] | no |  |  |  | Defines additional properties to include in the user data object. These are added to the default fields [ email, password, fullname, name, surname, mobile, emailVerified, mobileVerified, roleId] and shape the structure of the User model in the generated user service. Note: Standard fields (`id`, `isActive`, `createdAt`, `updatedAt`) are automatically created. Every one of those thirteen names is RESERVED: a declaration here colliding with one is REFUSED at design time (`AUTH_USER_PROPERTY_NAME_RESERVED`), and so is a name declared twice in this list. Both comparisons IGNORE CASE - `Email` is the built-in `email`, and `displayName` beside `displayname` is one property declared twice - because a differently-cased spelling is not a different column: the DB index name is the column name snake_cased and LOWER-cased, so two such properties would emit one index name and only the first index would ever be created. For the same reason two names that merely PROJECT onto one index name (`ownerId` and `owner_id`) are refused too (`AUTH_USER_PROPERTY_INDEX_NAME_COLLISION`). |
| `tenantProperties` | [`DataProperty`](./DataProperty.md)[] | no |  |  |  | Defines additional properties to include in the tenant data object, alongside the built-ins the auth service always emits: `name`, `codename` (unique, server-minted from the name), `fullname`, `avatar` and `ownerId`. Every one of those five names is RESERVED, and so are the standard fields `id`, `isActive`, `createdAt` and `updatedAt`, which are created automatically: a declaration here colliding with any of the nine is REFUSED at design time (`AUTH_TENANT_PROPERTY_NAME_RESERVED`) - declare a differently-named property instead. The comparison IGNORES CASE, and so does the duplicate check within this list: `Name` is the built-in `name`, and `displayName` beside `displayname` is one property declared twice. A differently-cased spelling is not a different column - the DB index name is the column name snake_cased and LOWER-cased, so two such properties would emit one index name and only the first index would ever be created. For the same reason two names that merely PROJECT onto one index name (`ownerId` and `owner_id`) are refused too (`AUTH_TENANT_PROPERTY_INDEX_NAME_COLLISION`). So this list does not redeclare the tenant `name`. To make the tenant name unique, set `uniqueTenantName: true` on the tenant configuration, which stamps `indexSettings.unique` on the built-in `name` for you; for a tenant identity that is a PAIR of columns, declare the pair in `compositeIndexSettings`. |
| `businessLogic` | [`BusinessApi`](./BusinessApi.md)[] | no |  |  |  | Custom Business APIs to be included in the generated auth service. These APIs follow the same patterns as regular service Business APIs—supporting REST, WebSocket, Kafka, and cron triggers with full workflow capabilities. Standard auth API names (login, register, verify, resetPassword, etc.) are reserved and cannot be overridden. Use this to extend the auth service with project-specific operations on User, Tenant, or other auth-related data objects. Role writes: roles are not badges, so an api or crud action here that writes the auth user's `roleId` is refused (AUTH_USER_ROLE_WRITE_UNGUARDED, non-bypassable) - use updateUserRole / createUser, and model an earned label as a badge data object. The one exception is a real role change after an operation, run by a service: a create / update api on `user` declaring `authOptions.requiredCallerKind: "machineWithoutUserIdentity"` (with M2MAllowed true and loginRequired left on) that writes `roleId` in its own dataClauseItems. The generated api then refuses a caller whose session carries a user identity (400 M2M_CALLER_WITHOUT_USER_IDENTITY_REQUIRED) and stores only a declared role, in its canonical spelling: never an administrator role (superAdmin, saasAdmin, admin, tenantOwner, tenantAdmin: 400 ADMINISTRATOR_ROLE_NOT_ASSIGNABLE), never a SaaS-level role (saasAdmin, saasUser - a machine caller is no SaaS operator: 400 SAAS_ROLE_GRANT_FORBIDDEN), never an empty role list when users have multiple roles (400 ROLE_LIST_EMPTY); an undeclared role: 400 ROLE_NOT_DEFINED. Both role refusals are case- and separator-insensitive. A crud action or bulk create onto `user` is never that door. |
| `dataObjects` | [`DataObject`](./DataObject.md)[] | no |  |  |  | Custom DataObject definitions to host IN the generated auth service (the process that owns the givenPermission table). This lets a project attach project-specific CRUD objects—e.g. a permissionCheck-guarded object—to the auth service so the native-permission resolver can decide over real givenPermission rows. Objects whose name collides with a system auth object (user/userGroup/givenPermission/...) are skipped. |

## Constraints

Property rules:

- `authenticationEssentials`, `loginDefinition`, `verificationServices`, `accessControl` must be present. (`REQUIRED_FIELD_MISSING`)
- The items of `userProperties` must have distinct names (`basicSettings.name`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)
- The items of `tenantProperties` must have distinct names (`basicSettings.name`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)
- The items of `businessLogic` must have distinct names (`basics.apiOptions.name`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)
- The items of `dataObjects` must have distinct names (`objectSettings.basicSettings.name`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)

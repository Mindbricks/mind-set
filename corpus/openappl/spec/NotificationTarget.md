# NotificationTarget

**Level:** `section` · **Family:** [EventNotification](../ontology/families.md#eventnotification) (domain `NotificationService`)

**Ontology:** [NotificationTarget in Part 1](../ontology/NotificationTarget.md)

**Name:** an instance is named by `targetName`.

Defines a recipient or list of recipients for an event notification. Targets are derived from the notification data and can be conditional. By default `targetKind: 'userId'` resolves to an authenticated user and the system looks up the user's email/phone/devices via auth-service. Set `targetKind` to one of `email` / `phoneNumber` / `whatsappPhone` / `telegramHandle` / `deviceToken` when the resolved value at `targetPathInData` is already the direct contact handle — typically when notifying non-users (leads, opted-in subscribers, etc.) whose contact details live in the application database, not the auth user table. The AUDIENCE kinds `role` / `userGroup` address a set of users instead of a payload-sourced value: `targetValue` names a declared role value or user group, the notification service asks the auth service (M2M) for the matching users at delivery time, and each resolved user then follows the normal `userId` delivery path (dedup across targets included).

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `targetName` | `String` | yes |  |  | format [codeName](./value-formats.md#codename) | A unique, human-readable name for the target. Use camelCase (e.g., 'customer', 'internalApprovers'). A blank value (empty or whitespace-only) is the UNSET state: the notification layer trims before reading it, so a name of `' '` behaves exactly like no name at all rather than as a genuinely-set target name. The same blank-is-unset rule applies to `targetPathInData`, `targetValue`, `targetUserIdInArrayTargetItem` and `targetItemNameInArray`. Normalizing the name never affects the target itself: its `condition` gate is bound to the target by POSITION, not by name, so a blank-named (or duplicate-named) target still evaluates its OWN condition and is still skipped when that condition is false. |
| `targetKind` | `NotificationTargetKind` | no | `"userId"` | `userId`, `email`, `phoneNumber`, `whatsappPhone`, `telegramHandle`, `deviceToken`, `role`, `userGroup` |  | What kind of recipient this target declares. Default 'userId' — the value at `targetPathInData` is an application user id and email/phone/devices are looked up via auth-service. The direct-handle kinds skip the user lookup and treat the resolved value as the contact handle. The audience kinds 'role' / 'userGroup' ignore `targetPathInData` entirely: `targetValue` names a declared role value or user group name, and the delivery-time fan-out resolves it to user ids via the auth service (M2M). Must be compatible with the parent EventNotification's `jobType`: jobType 'email' accepts userId\|email; 'sms' accepts userId\|phoneNumber; 'push' accepts userId\|deviceToken; 'telegram' accepts userId\|telegramHandle; 'whatsapp' accepts userId\|whatsappPhone; 'role' and 'userGroup' resolve to user ids and are accepted by every jobType (like userId). |
| `targetPathInData` | `String` | no |  |  | format [dotPath](./value-formats.md#dotpath) | The path to the contact handle(s) inside the notification's data. **The root is the event RECORD, not the wire envelope**: the generated listener unwraps the unified event envelope — `record = event.data` — before reading this path, so NEVER prefix it with `data.`. A `data.` prefix reads through a second, non-existent envelope, resolves to `undefined`, and the notification silently targets nobody. What the record holds depends on the producer: for a topic published by a `PublishEventAction` it is the authored message object (address its keys directly), for a db-event topic it is the row, for an API-event topic it is the API's result record. This is the opposite binding from an AIAgent `kafkaController.dataMapping`, which is handed the RAW wire message and therefore does read `message.data.<key>`. When the notification declares `eventDataSettings.dataViewName`, the root is the fetched DataView document instead. In the shared vocabulary this surface is read scope 'record', the same scope as a BusinessApi Kafka controller's `requestParameters[].dataPath` and as an AIAgent `kafkaController` with NO `dataMapping`; only an AIAgent `kafkaController` that DOES declare a `dataMapping` is read scope 'envelope'. See the Kafka-topics reference page for the full wire-vs-reader table, or ask the `getKafkaEventPayloadStructure` tool, whose every answer returns it as `consumerBindings`. When `targetKind: 'userId'`, the value is a user id (single or array). Otherwise the value is the direct contact handle (email address / E.164 phone / @telegramHandle / device token). For nested objects use `prop1.prop2.prop3` notation. Required for every payload-sourced kind; leave it null for the audience kinds `role`/`userGroup`, which take their audience from `targetValue` instead and ignore this path. VALUE SHAPES the resolver accepts, at every read site (the scalar value, an array item that is its own value, a per-item path inside an object item, and the direct-handle mapper): a non-empty STRING is taken as-is, and a WHOLE NUMBER within +/-2^53 is stringified, so a numeric primary key resolves. Booleans, objects, arrays, NaN/Infinity and non-integers are REJECTED and the target resolves nobody. An id BEYOND 2^53 is rejected too, and must be published as a STRING: JSON parsing rounds such a number before any handler sees it, so the digits that arrive are not the digits that were sent. On a rejection the target contributes no recipient and the notification is recorded as a delivery FAILURE; the offending shape is named in the service LOG line, not in the stored row. Point this path at the scalar id or handle field, never at the object that contains it. PORTING STATUS: only the nodejs listener implements this contract today. Six of the eight service trees have a notification target resolver at all; rust and mcpbff have no notification layer. The java, python, golang and php listeners are string-only, so a numeric id resolves nobody there and the target fails visibly, exactly as an unresolvable path does. The dotnet listener is NOT a second implementation of this contract, and it is the one tree where a numeric id is actively unsafe rather than merely unsupported: its handler unwraps the whole wire payload through the shared JS-shaped request-bag unwrap before any target is read, and that unwrap boxes EVERY JSON number as a double on purpose, so the listener never sees the raw token. A whole number within 2^53 does resolve there, matching nodejs. An id BEYOND 2^53 has already been rounded by that unwrap, and dotnet then ACCEPTS the rounded value instead of rejecting it, so the notification is delivered to a NEIGHBOURING id (a real, different user in a sequential-integer schema) rather than recorded as a failure. A non-integer is accepted there too, and rendered under the process culture. Publish ids as STRINGS: that is the only shape all six listeners agree on. |
| `targetValue` | `String` | no |  |  |  | The STATIC audience name for the audience target kinds — ignored (and normally null) for every other kind. For `targetKind: 'role'` this is a declared role VALUE (the literal a session carries in `roleId`): a built-in system role — superAdmin/admin/user in single-tenant projects, superAdmin/saasAdmin/tenantOwner/tenantAdmin/tenantUser/saasUser in multi-tenant projects — or the `value` of a custom RoleItem declared under accessControl.roleSettings. For `targetKind: 'userGroup'` this is a user group's `groupName` (groups are runtime data of the auth service's userGroup object; the name is resolved at delivery time, so `userGroupsActive` must be enabled). Validators reject an unknown role value at design time; an unknown group name surfaces at delivery time as a failed delivery record, never a silent drop. |
| `scope` | `NotificationTargetScope` | no | `"tenant"` | `tenant`, `global` |  | Tenant scope of an audience (`role`/`userGroup`) target in a MULTI-TENANT project — ignored elsewhere. Default 'tenant': the fan-out resolves users within the EVENT's tenant (tenant id taken from the event envelope's actor, falling back to the record's tenant id field); when no tenant id is resolvable at delivery time the target FAILS VISIBLY (error log + failed delivery record) rather than silently notifying across tenants. Set 'global' to deliberately fan out across all tenants (e.g. a saasAdmin broadcast). |
| `isArray` | `Boolean` | yes |  |  |  | Indicates whether the target path contains a list of contact handles. If true, the notification will be sent to each entry in the array. |
| `targetUserIdInArrayTargetItem` | `String` | no |  |  | format [dotPath](./value-formats.md#dotpath) | When `targetKind: 'userId'` and `isArray: true`, this is the property name inside each item that holds the user id. Ignored when targetKind is not 'userId'. |
| `targetItemNameInArray` | `String` | no |  |  | format [dotPath](./value-formats.md#dotpath) | If the target is an array, the path to the ARRAY CONTAINER - the array itself - inside the notification data. Despite the name this is NOT a per-item property name: declaring it makes targetPathInData the path read INSIDE each item, so targetItemNameInArray: 'members' with targetPathInData: 'memberUserId' reads members[].memberUserId. Leave it empty when targetPathInData already points at the array; the items are then the user ids / contact handles themselves, unless targetUserIdInArrayTargetItem names the id property inside each item. |
| `condition` | [`MScript`](./MScript.md) | no |  |  | MScript kind `code` | An MScript expression evaluated ONCE PER TARGET, never per array item. For isArray targets, target is the whole array; use itemCondition to filter individual recipients. It determines whether the notification should be sent to this target, based on the target data. Access the target data using `target` (without `this`) and data source using `this.dataSource`. The `this` receiver is the same five null-normalized members the event-level eventDataSettings.condition gets, with the same null-safe-to-any-depth fold for chains rooted at one of them, so read that slot's description before relying on a missing-data read: the fold makes the condition ANSWER FALSE and skip this target silently, it does not record a delivery failure. Reading a member the receiver does not have is a misdeclaration, and design-time validation REFUSES it: NOTIF_TARGET_CONDITION_RECEIVER_UNKNOWN is an ERROR on this slot, not a warning, so a condition rooted at anything outside the five members does not build. The tier was raised on a measured census over every committed blueprint - 187 targets, 174 per-target condition slots, and zero rooted outside the five members - and it exists because what the read DOES at runtime is not portable and cannot be made portable without forking the shared MScript accessor per language. What every listener agrees on is only that the target is NEVER SENT while the read stands; HOW that happens is a property of the listener. A plain comparison against such a member (`this.target`, `this.data`) reads `undefined` and folds to false, so the target is skipped silently. A deeper read through one (`this.target.isPublic`, `this.data.owner.id`) fails condition evaluation on the nodejs and python listeners, which record a failed per-target delivery; on java the same read does not COMPILE at all, because `this.<member>` lowers to a field the listener's condition context does not declare; and on the null-safe listeners (dotnet, rust, golang) it folds to false and the target is skipped instead, and dotnet additionally logs a one-shot runtime warning naming the member so the skip leaves a trace to find, while rust and golang leave none. The same read through a DECLARED member (`this.dataSource.owner.tier`) is null-safe at every link past the root and simply answers false. The event-level eventDataSettings.condition slot carries the identical rule - same receiver, same code, same ERROR tier - so neither slot accepts a root the other refuses. See the LANGUAGE NOTE on eventDataSettings.condition: which reads fail rather than fold is a per-listener property, not a portable guarantee. |
| `itemCondition` | [`MScript`](./MScript.md) | no |  |  | MScript kind `code` | Optional per-item MScript filter for an isArray target on nodejs. The existing condition runs ONCE PER TARGET with target bound to the whole array; use itemCondition to skip individual recipients. In itemCondition, bare target is the current item, data is the DataView-first event record, and this carries payload, dataSource, old, actor and metadata. A targetItemNameInArray container path with a valid, non-conflicting JavaScript identifier root also binds the current item (reserved roots such as data, target and runMScript keep their existing meanings; use bare target for those paths): for members use members.active; for group.members use group.members.active. The container path keeps its existing meaning for recipient resolution. Example: targetItemNameInArray: 'members', targetPathInData: 'userId', itemCondition: { js: 'members.active && target.userId !== this.actor.userId' }. False skips that item; an evaluation error warns and skips only that item, continuing its siblings. Filtering every item is an intentional empty audience, not a delivery failure. Other language listeners require the corresponding port before using this slot. |

## Constraints

Property rules:

- `targetName`, `isArray` must be present. (`REQUIRED_FIELD_MISSING`)
- `targetKind`, `scope` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- `targetName` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)
- `targetPathInData`, `targetUserIdInArrayTargetItem`, `targetItemNameInArray` must be in the [`dotPath`](./value-formats.md#dotpath) format. (`INVALID_DOT_PATH`)

Pattern rules:

| Code | Severity | Rule |
| --- | --- | --- |
| `NOTIF_ARRAY_CONDITION_ITEM_READ` | warning | condition runs once per target with the whole array. |
| `NOTIF_ITEM_CONDITION_NOT_ARRAY` | warning | itemCondition only filters isArray targets. |

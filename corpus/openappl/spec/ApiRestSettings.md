# ApiRestSettings

**Level:** `section` · **Family:** [BusinessApiControllers](../ontology/families.md#businessapicontrollers) (domain `BusinessApi`)

**Ontology:** [ApiRestSettings in Part 1](../ontology/ApiRestSettings.md)

**Activation:** the pattern is switched on by `hasRestController`.

Defines the REST controller configuration for a Business API. REST is the default HTTP interface in OpenAPPL. These settings allow enabling/disabling REST access and customizing the endpoint path. Fields are flat — set `routePath` and `forcePOSTMethod` directly on this block (the legacy `configuration: { ... }` wrapper is still accepted on input but lifted at validate time).

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `hasRestController` | `Boolean` | no | `true` |  |  | Controls whether the Business API is exposed as a REST endpoint. Set to false to disable HTTP access. |
| `routePath` | `String` | no | `"$default"` |  |  | Custom REST path override. Leave as `$default` to auto-generate.  ## Default-route calculation  Given the API's crudType, name, dataObjectName, and whereClause.selectBy, the calculator produces:    create / list                   →  /<resourcePath>   get / update / delete           →  /<resourcePath>/:<param>          (unless the where clause, not the URL, addresses the row - see below)  The `<param>` segment is chosen in this order:   1. If `whereClause.selectBy` has exactly one entry and that entry is NOT `id`,      the param uses that field name, even when a `fullWhereClause` is also set. Example: selectBy=['slug'] → /<resource>/:slug.   2. Otherwise, if `whereClause.fullWhereClause` is set, there is NO param: the route is the bare `/<resourcePath>` (see the next section).   3. If `whereClause.selectBy` has several entries and none is `id`, there is NO param either.   4. Otherwise the param is the data-object's natural id, formatted as `<dataObjectName>Id`.      Example: dataObject=`User` → /<resource>/:userId.  `<resourcePath>` is derived from the API name + dataObjectName, ALWAYS lowercased:   - Default-shape APIs (e.g. getUser/listUsers/createUser/updateUser/deleteUser on the User     object) collapse to the plural object name: `/users`.   - Non-default APIs (custom verbs like `archiveUser`, `closeOrder`) concatenate verb + singular     object name (no plural): `/archiveuser`, `/closeorder`.  The path parameter follows the standard OpenAPPL naming convention — `dataObject.objectName` is lowercase camelCase (e.g. `user`, `orderItem`), and the param appends `Id`: `:userId`, `:orderItemId`. (The resource segment is additionally lowercased; the param name passes the input case through.)  ## fullWhereClause removes the path parameter: author routePath  A get/update/delete API that sets `whereClause.fullWhereClause` (and no single non-`id` selectBy entry, which still names the segment) gets NO path parameter from the default calculator: the where clause, not the URL, addresses the row, so there is no segment to derive, and a `:<dataObjectName>Id` nothing reads would only make every caller send a dummy id. The calculated route is therefore the bare `/<resourcePath>`, which for a `get` is the same `GET /<resource>` the list API mounts. Validation reports that shape once, as the ERROR `SINGLE_ACCESS_ROUTE_MISSING_ID`, whose message names the route to author (the list-endpoint `ROUTE_COLLISION` warning stands down for it). So an API with a fullWhereClause sets `routePath` explicitly: with a `:segment` named after the request value the where clause reads (`/orders/:invoiceNbr`), or as a static path distinct from the collection (`/orders/current`, `/getactivebasket`) when the record is resolved from the session or other context. The same applies to a multi-entry selectBy without `id`.  ## Custom routePath rules    - Always start with `/`.   - If your custom path includes a parameter (`:something`) AND `selectBy` is unset, the parameter name is inferred as the selectBy field. Example: `routePath: '/orders/:invoiceNbr'` with no selectBy → effective selectBy is `invoiceNbr`.   - If your custom path's parameter name conflicts with the configured `selectBy`, an ambiguity warning is raised at validation.   - A custom routePath without any `:`-style parameter IS allowed for single-record get/update/delete APIs — useful for verb-style endpoints (e.g. `/getActiveBasket`, `/closeMyOrder`) where the record is resolved from auth context or `fullWhereClause` rather than the URL. Just be aware the route cannot vary per record, so it must not collide with the list/create path on the same resource.  ## Version prefixes  The generated service mounts every Business API route twice: at the bare path and under a fixed `/v1` alias (`/feeds` and `/v1/feeds` are the same route). Because of that alias, a leading `/v1` in a custom routePath is redundant and is STRIPPED at validate time as an auto-fix (`/v1/feeds` becomes `/feeds`, still reachable at both `/feeds` and `/v1/feeds`). Any OTHER version prefix (`/v2`, `/v3`, ...) is part of the route you authored and is kept verbatim: `/v2/me/settings` is mounted exactly as written (and, through the alias, at `/v1/v2/me/settings`). There is no per-API version field; a version is simply a path segment.  ## Verifying the calculated route  After writing your business APIs, the apply worker can call `getServiceBusinessApiList(serviceName)` to get the structured list of `{name, crudType, method, routePath, source}` for every API in the service — useful to confirm the auto-calculator produced the route shape you expected before triggering a build. Custom create/list routes also bind an undeclared :<dataObjectName>Id into this.<dataObjectName>Id for actions, even when the API does not address its main row by id. |
| `forcePOSTMethod` | `Boolean` | no | `false` |  |  | The http method will be set according to the crud type, use this setting if you want to force the HttpMethod to POST. Not recommended if you don't have a specific reason. |
| `acknowledgedShadowedFilterParams` | `String`[] | no |  |  |  | Per-API acknowledgment for the `FILTER_PARAM_SHADOWED_BY_ROUTE` warning. `isFilterParameter` is a PROPERTY-level flag, so a dual-use property — a route `:param` on one API and a genuine query filter on another (e.g. `creatorProfile.userId`: `:userId` on a nested get API, real filter on `adminListCreatorProfiles`) — would otherwise warn forever on the route-param API: clearing the property flag to silence it would break the filter on the sibling API. List the property name(s) here, on the API whose route deliberately shadows them, to record the dual use as intentional; the warning is silenced for the named segments on THIS API only and stays silenced through re-validation. Names that do not currently match a shadowed filter property on this API raise `FILTER_PARAM_ACK_STALE` so stale acknowledgments cannot rot silently. Leave null/empty when no route segment shadows a filter property. On list APIs the shadow warning is suppressed when queryFiltersActive is false or the route segment is an authored selectBy/custom request parameter. |

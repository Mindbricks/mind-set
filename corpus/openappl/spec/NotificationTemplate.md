# NotificationTemplate

**Level:** `section` · **Family:** [EventNotification](../ontology/families.md#eventnotification) (domain `NotificationService`)

**Ontology:** [NotificationTemplate in Part 1](../ontology/NotificationTemplate.md)

Defines a notification template used to render the content of event notifications. Templates are written in EJS. **Variable scope**: the template's variables are the notification metadata keys at TOP LEVEL — the triggering event RECORD's own fields (the unified envelope's `data`, the very same root `targetPathInData` reads), spread directly into the render scope. Write `<%= followerFullname %>`, NEVER `<%= data.followerFullname %>`: there is no `data` wrapper in templates — the bare `data` root exists only in the condition MScript slots — so a `data.` read throws a ReferenceError at render time, the render degrades to an empty string, and a notification whose subject and body are both empty because of a render error is recorded as a FAILED delivery instead of being sent. Besides the record's fields the scope carries `_old` (the envelope's previous-row image on update/delete db events, else null), `_actor` (the envelope actor, else null), `actionDeepLink`/`actionText` (the evaluated MScript values; each key is absent when its script fails), and — only when `eventDataSettings.dataViewName` is set — `dataSource`, the whole fetched DataView document as ONE nested object (`<%= dataSource.someJoinedField %>`; the record's fields stay at top level beside it). **Required locals**: every free root identifier of the compiled template body is REQUIRED unless the template proves it tolerates absence, either by mentioning it once as a `typeof` operand or by reading it only through the always-bound `locals` object. At render time a required local the bound context does not carry REFUSES the delivery and NAMES it (`renderErrorCode: 'NOTIF_TEMPLATE_MISSING_LOCAL'`, `missingLocals: [...]`), including when only the other slot rendered fine: nothing is sent and nothing is stored. A key bound to null counts as PRESENT, so `_old` never triggers this. At design time the same parse warns `NOTIF_TEMPLATE_ROOT_NOT_IN_CONTEXT` when a required root is neither a framework binding, nor a flat field of the producing event's record, nor a declared `includeData` key. A property the declared DataView projects is NOT a top-level local: the view document is bound only under `dataSource`, so a field the record does not carry is read as `<%= dataSource.<field> %>`, and the warning names that read.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `name` | `String` | yes |  |  | format [codeName](./value-formats.md#codename) | The unique name of the notification template. This is used to reference the template in event notifications. |
| `description` | `Text` | no |  |  |  | A brief description of the template's purpose and usage. |
| `subjectTemplate` | `Text` | yes |  |  |  | The EJS template text used to generate the notification subject line. Variables are the notification metadata keys at TOP LEVEL — the triggering event record's fields, addressed directly: `<%= followerFullname %>`, never `<%= data.followerFullname %>` (there is no `data` wrapper in templates; an undefined root identifier fails the whole render, and an error-empty render is recorded as a FAILED delivery, nothing is sent). Also available: `_old`, `_actor`, `actionDeepLink`, `actionText`, and `dataSource` (the DataView document) when eventDataSettings.dataViewName is set. Every bare root read here is a REQUIRED local: if the bound context does not carry it the delivery is refused and the local is named, even when the body rendered fine. Guard a genuinely optional local with `typeof someLocal !== 'undefined'`. |
| `bodyTemplate` | `Text` | yes |  |  |  | The EJS template text used to generate the notification body content. Variables are the notification metadata keys at TOP LEVEL — the triggering event record's fields, addressed directly: `<p><%= followerFullname %> followed you.</p>`, never `<%= data.followerFullname %>` (there is no `data` wrapper in templates; an undefined root identifier fails the whole render, and an error-empty render is recorded as a FAILED delivery, nothing is sent). Also available: `_old`, `_actor`, `actionDeepLink`, `actionText`, and `dataSource` (the DataView document) when eventDataSettings.dataViewName is set. Every bare root read here is a REQUIRED local: if the bound context does not carry it the delivery is refused and the local is named, even when the subject rendered fine. Guard a genuinely optional local with `typeof someLocal !== 'undefined'`. |
| `parser` | `String` | no | `"ejs"` |  |  | The template rendering engine. Currently, only 'ejs' is supported. |
| `variants` | [`NotificationTemplateVariant`](./NotificationTemplateVariant.md)[] | no |  |  |  | Per-language versions of THIS template. Each variant names a `language` and carries its own `subjectTemplate` / `bodyTemplate`; `subjectTemplate` / `bodyTemplate` on the template itself stay as the MANDATORY whole-template fallback used for every recipient whose language matches no variant. The framework renders each declared variant AT MOST ONCE per event (never once per recipient) and then maps each recipient to a variant by the user's language, so an email carries ONE language instead of both stacked. The recipient's language is read from the auth user record with the fallback chain `preferredLanguage`, `language`, `locale`, `lang` - none of those is a standard auth field, so declare the one you use in `authentication.userProperties[]`. Matching is case-insensitive and falls back from a regional tag to its base (`tr-TR` matches a `tr` variant). Leave empty for a single-language template. The `data-lang` span + regex picker convention is the interim workaround this supersedes. |
| `renderPerRecipient` | `Boolean` | no |  |  |  | Opt in to rendering this template INSIDE the recipient fan-out, once per recipient, with a `recipient` object (`{ userId, handle, language, channel }`) in template scope. The default (false) renders once per event, or once per declared `variants` entry, which is what almost every template wants: language is already handled by `variants`, and a hundred-recipient reminder event pays one render instead of a hundred. Turn this on ONLY for genuine per-recipient personalization (`<%= recipient.userId %>`-keyed content); the template author knowingly pays the N-render cost. `variants` still apply: each recipient renders the variant their language selects. |
| `whatsappTemplate` | [`NotificationWhatsAppTemplate`](./NotificationWhatsAppTemplate.md) | no |  |  |  | The WhatsApp TEMPLATE this notification sends on a jobType='whatsapp' event, instead of the rendered subject/body text. WhatsApp delivers free-form text only inside the 24-hour customer-service window (the 24 hours after the recipient last wrote to you); outside it Meta refuses the message (error 131047) and Twilio refuses it (error 63016) AFTER the API has accepted the request, so a business-initiated notification - order, shipment, refund, OTP - sent as text is recorded as delivered and never arrives. When this block is set the provider sends the approved template: Meta Cloud API sends `{ type: 'template', template: { name, language: { code }, components } }`, Twilio sends `{ contentSid, contentVariables }` with no body. The subject/body templates are still rendered (they are what the notification log and a stored Notification row show) but are not what the recipient receives. A recipient whose language selects a variant that declares its own whatsappTemplate gets that one; every other recipient gets this one, with the language defaulting to the selected variant's language. Ignored on every other jobType (design-time warning WHATSAPP_TEMPLATE_IGNORED). A whatsapp notification with no whatsappTemplate here raises the design-time warning WHATSAPP_FREEFORM_OUTSIDE_WINDOW. |

## Constraints

Property rules:

- `name`, `subjectTemplate`, `bodyTemplate` must be present. (`REQUIRED_FIELD_MISSING`)
- `name` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)

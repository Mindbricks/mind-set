# AgentEndpointSettings

**Level:** `section` · **Family:** [AIAgent](../ontology/families.md#aiagent) (domain `Service`)

**Ontology:** [AgentEndpointSettings in Part 1](../ontology/AgentEndpointSettings.md)

Controls how the agent is exposed as an API endpoint. Each agent can have a REST endpoint (synchronous) and/or an SSE endpoint (streaming). Authentication requirements and path customization are configured here.

## Properties

| Name | Type | Required | Default | Allowed values | Details | Description |
| --- | --- | --- | --- | --- | --- | --- |
| `hasRestEndpoint` | `Boolean` | no | `true` |  |  | When true, generates a POST REST endpoint at /agents/{name} (or custom basePath). Returns the full response synchronously. False closes the agent's public REST route (user and anonymous callers); an AgentCallAction from another service of the project still reaches the agent on a nodejs agentHub, since that call carries a verified service token. |
| `hasSseEndpoint` | `Boolean` | no | `true` |  |  | When true, generates a POST SSE endpoint at /agents/{name}/stream. Streams tokens (text), progress events (media generation), or step results (orchestrator) in real-time. |
| `basePath` | `String` | no |  |  |  | Custom base path override for the agent's endpoints. Default: '/agents/{name}'. Example: '/ai/chat' generates POST /ai/chat and POST /ai/chat/stream. |
| `authRequired` | `Boolean` | no | `true` |  |  | When true, the agent's endpoints require a valid JWT token. Set to false for public-facing agents (e.g., a chatbot widget). A public agent has no per-client or per-IP rate limit and a guest has no user id, so `dailyTokenBudgetPerUser` does not apply: bound it with `dailyCostCeilingUsd` and a rate limit in front of the route. |
| `chatSurfaces` | [`ChatSurfaceSettings`](./ChatSurfaceSettings.md)[] | no |  |  |  | Chat-surface interfaces for the agent - exposes it over messaging apps (Telegram, WhatsApp) alongside the REST/SSE interfaces. Each entry names a CHANNEL PROVIDER (`provider` -> a `projectSettings.notificationProvidersSettings.notificationProviders[].name` of kind `whatsapp` (Meta Cloud) or `telegram`); the surface type comes from the provider kind and every credential is the provider's, so one agent reached over Telegram and WhatsApp at once declares two entries naming a telegram and a whatsapp provider. The entry itself only carries the surface-specific binding (the identity strategy + an optional webhook-path override for Telegram + typingIndicator (default on)). A WhatsApp surface has no webhook: Meta calls the provider's one door on the notification service and the agent consumes the provider's inbound messages over Kafka (`<codename>-whatsapp-inbound-message`), replying with the provider's access token, phone number id and Graph API version. A Telegram surface is a webhook of the host service (`/agents/<agent>/telegram/webhook`), verified with the provider's `telegramWebhookSecret` and answered with its `telegramBotToken`. A provider backs at most ONE conversational consumer (an agent surface or an mcpbff exposure); the validator errors on a second one (CHAT_PROVIDER_MULTI_CONSUMER). The retired `chatProvider` (a chat-bot name) is converted on load to `provider`. |
| `surfaces` | `AgentSurfaceType`[] | no |  | `rest`, `sse`, `telegram`, `whatsapp`, `videoRoom`, `kafka` |  | Declarative surface registry for the agent (docs/ADR-aiagent-chat-surfaces.md 'Surface registry'). ABSENT or EMPTY = implicit mode (fully backward compatible): every surface is enabled by whatever wiring references the agent — REST/SSE from hasRestEndpoint/hasSseEndpoint, telegram/whatsapp from chatSurfaces[], kafka from kafkaControllers[], videoRoom from a room's meetingAgents[]. NON-EMPTY = declared mode: the list is the authority on which surfaces the agent is reachable over — REST/SSE routes, chat webhooks and kafka listeners are emitted only for declared surfaces, and the validator requires each declared surface's prerequisites (telegram/whatsapp need a chatSurfaces[] entry bound to a provider of that kind, kafka needs an enabled kafkaController, videoRoom needs a videoRooms[].meetingAgents[] reference in the service the agent deploys to). Wiring present for an UNdeclared surface is warned and suppressed (videoRoom: errored on the room, since its emission is room-driven). On the agentHub service the declared list also binds the hub wildcard routes: POST /agents/:agentName answers 404 (the same body as an unknown agent) for an agent whose list leaves out 'rest', and POST /agents/:agentName/stream for one that leaves out 'sse', so a kafka-only agent (surfaces ['kafka']) cannot be run by a signed-in caller over REST or SSE; the role-gated eval suite (fixed evalCases) still runs. In implicit mode the hub derives the same list from the legacy flags: hasRestEndpoint false leaves out 'rest' and hasSseEndpoint false leaves out 'sse', so those wildcard routes answer the same 404 (an implicit-mode agent with both flags on is served). These refusals govern PUBLIC exposure (user and anonymous callers): a call from another service of the project (an AgentCallAction, or any InterService call) carries an x-m2m-token, and a token the hub verifies and its caller lists admit runs any design-time agent on POST /agents/:agentName whatever its surfaces (the stream route and dynamic agents keep their rule). The agentHub service's own AgentCallActions run an agent it deploys without 'rest' in-process. An agentHub generated in java or dotnet still refuses such a service call, and an AgentCallAction that reaches such an agent over that hub is warned (AGENT_CALL_SURFACE_NOT_REST). |

## Constraints

Property rules:

- `surfaces` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- The items of `chatSurfaces` must have distinct names (`provider`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)

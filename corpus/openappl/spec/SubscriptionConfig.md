# SubscriptionConfig

**Level:** `subsection` · **Family:** [ObjectSettings](../ontology/families.md#objectsettings) (domain `DataObject`)

**Ontology:** [SubscriptionConfig in Part 1](../ontology/SubscriptionConfig.md)

Configuration for recurring subscriptions on a DataObject. Provider-binding via `providerName`. The framework wires up plan creation (where applicable), customer attachment, renewal webhooks, and cancellation flows. Requires the bound PaymentProvider to support subscriptions (capabilities.supportsSubscriptions=true). On a TOKENIZED provider (subscriptionSemantics 'tokenized', e.g. Adyen) the subscription opt-in also implies the object's `sys_<X>Payment` ticket table and the payment intent machine: the framework's recharge scheduler records every cycle's charge there (`orderId` = the subscription row id, `metadata.recharge: true`) and the provider webhook reconciles it, whether or not the object also opts into `checkout`. No checkout API (start / refresh / callback routes, ticket CRUD APIs) is added by the subscription opt-in alone; hosted and checkout-driven providers run their own cycle and get no extra table. 3-D SECURE ON STRIPE: a subscription whose FIRST payment needs the buyer (authentication, or a declined card) is created `incomplete`; the subscribe answer then carries `nextAction` (`requiresAction`, `clientSecret`, `paymentStatus`, `hostedInvoiceUrl`) for the frontend to finish with Stripe.js, and the row reads `past_due` (never an entitled state) until Stripe's `invoice.paid` makes it `active`; unfinished, Stripe expires it after 23 hours (`expired`). A RENEWAL that needs authentication reaches `afterInvoicePaymentFailed` with `resource.requiresAction: true` and `resource.hostedInvoiceUrl`, the page where the buyer authenticates. Grant the plan on `active` (`afterInvoicePaid` / `afterSubscriptionRenewed`), never on `afterSubscriptionCreated` alone. HOSTED SUBSCRIPTION FORM ON IYZICO: iyzico takes the card only on its hosted subscription Checkout Form, so a subscribe (the raw route or a SubscriptionAction `subscribe`) answers a row `pending_provider` under the `providerSubscriptionId` `pending:checkout:<token>`, plus `checkoutForm` (`token`, `checkoutFormContent`, `paymentPageUrl`, `tokenExpireTime`) for the frontend to show. iyzico POSTs the token to the service's own `/v1/payments/subscription-checkout-return/<provider>` (derived from SERVICE_URL), which reads the result from iyzico, never from the body: ACTIVE makes the row `active` and fires `afterSubscriptionCreated` once; another reported status (`past_due`, `trialing`) is stored without that hook; a refusal is `provider_failed`. The buyer's email, name and surname come from `metadata.buyer` or the caller's session (400 SUBSCRIPTION_BUYER_EMAIL_REQUIRED without an email). A `pending_provider` row grants nothing. A cancel first reads the form from iyzico: a form that produced no subscription closes locally, a confirmed subscription is canceled at iyzico under its real reference, and a failed read or provider cancel leaves the row available for retry.

When set, the framework writes the new status onto THIS object's row (the row `sys_<X>Subscription.orderId` names) whenever the subscription status changes: when the subscribe route opens the subscription, as provider webhook events advance the subscription state machine and, on a tokenized provider (e.g. Adyen), at the recharge scheduler's own status writes (renewed, dunned, parked, dunning exhausted; never on a replay or a lost race). | `lifecycleHooks` | [`LifecycleHook`](./LifecycleHook.md)[] | no |  |  |  | Designer-authored MScript handlers fired on subscription lifecycle events (afterSubscriptionRenewed, afterSubscriptionCanceled, afterSubscriptionPastDue, etc.). |
| `maxDunningAttempts` | `Integer` | no | `4` |  |  | Tokenized providers only (subscriptionSemantics 'tokenized', e.g. Adyen), where the framework's recharge scheduler owns the billing cycle: the maximum number of refused recharges the dunning loop retries before the subscription is closed out. A refused charge moves the row to `past_due`, counts one attempt on `sys_<X>Subscription.dunningAttempts` and schedules a retry one day later; when the count reaches this cap the row goes to the terminal state named by `dunningExhaustedState` and the scheduler stops selecting it. A successful recharge resets the count. Transport errors (the provider could not be reached) do not count. Hosted and checkout-driven providers run their own dunning and ignore this field. Minimum 1. |
| `dunningExhaustedState` | `DunningExhaustedState` | no | `"cancel"` | `cancel`, `pastDue` |  | Tokenized providers only: what the recharge scheduler does with a subscription whose refused recharges reached `maxDunningAttempts`. `cancel` (default) ends it: statusLiteral `canceled`, `canceledAt` stamped, a still-trialing row loses its trial entitlement (`trialEnd` clamped to now), and the recharge anchor is cleared. `pastDue` parks it: statusLiteral `past_due` with the recharge anchor cleared, so it is never charged again until an operator or a business API restores a payment method and re-stamps `nextRechargeAt`. Either way the exhausted row is logged once as `SubscriptionDunningExhausted`. |
| `storePaymentMethod` | `Boolean` | no | `false` |  |  | An EXPLICIT opt-in (default false) to store the buyer's payment method while paying: Adyen enrols it for recharges, Stripe attaches it, iyzico's hosted form lets the buyer save it. On a tokenized provider (subscriptionSemantics 'tokenized', e.g. Adyen), where the framework's recharge scheduler charges a STORED method merchant-initiated, it makes the customer-initiated payment which opens the subscription (a PaymentAction start / simple stage on the order object that carries this subscription block) enrol the customer's payment method at the provider (`storeMethod: true`, sent by the Adyen adapter as `storePaymentMethod: true`), so the recharge has a method to reference (`ContAuth`). Stripe (save the card while paying) sends it as `setup_future_usage: 'off_session'`: Stripe attaches the confirmed card to the buyer's Stripe customer and reports `payment_method.attached`, which role (2) below persists into `sys_paymentMethod`; a caller can never send `setup_future_usage` itself (refused as a provider option, PAYMENT_PROVIDER_OPTION_NOT_ALLOWED). The card is enrolled for off-session use; by default the framework makes no off-session Stripe charge of its own: the stored card serves the buyer's later payments with `paymentMethodId` (buyer present, 3-D Secure possible) and Stripe's own subscription renewals. Only a Stripe entry that opts in (savedCardOffSession 'verified' beside savedCardThreeDSMode 'verifyOnce') charges a stored card already 3-D Secure verified off-session (merchant-initiated, no liability shift, buyer-absent use only), and only from a PaymentAction start / simple stage declared buyerAbsent. The stored-credential contract sent with the enrolment (`recurringModel`) is DERIVED from this configuration, never from the request body: `subscription` when `planProperty` binds the object to a plan with a billing interval (a fixed schedule), `unscheduled` (card on file) when it does not. Storing a card changes the cardholder-facing behaviour, so it is never a silent default: with the opt-in off the provider call carries no store flag even when the request body asks for one, any `recurringModel` / `initiatedBy` in the body is ignored, and `validate` warns (SUBSCRIPTION_STORE_PAYMENT_METHOD_OFF) that recharges on this tokenized provider will have no stored method. The field has TWO roles and only the first is provider-specific: (1) ADAPTER ENROLMENT, where the adapter supports sending a store flag with the opening payment (Adyen and Stripe today; for iyzico see below) - other hosted and checkout-driven providers store methods through their own checkout, so they send nothing extra; (2) the RETENTION GATE of the webhook method mirror, which applies to EVERY provider including the hosted and checkout-driven ones: a provider-reported stored method (`method.attached` / `method.updated`) is written into `sys_paymentMethod` only when a payment object of the service carries this opt-in, otherwise the event is acknowledged, logged as `PaymentMethodRetentionSkipped` and not retained (`method.detached` always syncs, and the cardholder's own `POST /v1/payment-methods/add` persists regardless). A checkout-only order object opts in with its own switch, CheckoutConfig.storePaymentMethod; either switch counts, read as one design-time rule. The mirror files the method for the user who OWNS the provider customer's payment-customer mapping, through the identity owner's machine-only `attachPaymentMethodByCustomerIdForMachine` (the webhook names no user; the api reads it from the mapping, idempotent per customer and method). iyzico (save the card while paying on the hosted Checkout Form): on an iyzico-bound order object carrying this opt-in (or CheckoutConfig.storePaymentMethod), the mounted start route and a PaymentAction start / simple stage open the hosted form with the buyer's own card storage key (`sys_paymentCustomer.cardStorageKey`, read server-side from the buyer's mapping; none for a buyer who has no key yet), so iyzico lists the buyer's saved cards and offers to save the new one. A card the buyer saves on the form is taken when the payment settles (the browser return or iyzico's Checkout Form webhook, once): a card filed under another key than the buyer's is refused, a first-time buyer's minted key is stored once through the machine-only `setPaymentCustomerCardStorageKeyForMachine` (a lost race deletes the card filed under the minted key), and the card is filed in the ticket owner's `sys_paymentMethod` right away through the machine-only `attachPaymentMethodByCustomerIdForMachine` (the owner is read from the buyer's payment-customer mapping, never from the request). Without either switch the iyzico form is opened without a key and nothing it saves is recorded. |
| `checkRoles` | `String`[] | no |  |  |  | Roles required on the INJECTED subscription lifecycle routes of this object - POST /v1/subscribe<x>/:orderId, DELETE /v1/<x>subscription/:subscriptionId and PATCH /v1/<x>subscription/:subscriptionId. Same meaning as BusinessApi authOptions.checkRoles: the list RESTRICTS (a caller holding none of these roles is refused 403 PAYMENT_ROLE_REQUIRED) and it is combined with OR. It is NOT absoluteRoles, and the two are never normalised into each other: the surface keeps its own separate BYPASS list (admin / superAdmin, PAYMENT_ABSOLUTE_ROLES), and a verified inter-service (M2M) caller that carries no user identity is admitted because the lifecycle routes are mounted allowM2M and a machine caller holds no role (an M2M caller that names a user - a forwarded user token - is that user and faces the list and the ownership gate). Leave empty to let routeAccess decide: `inherit` (the default) derives the gate from this object's authored apis, `open` emits none. Setting this is the way to gate the injected routes differently from the authored ones - for example when the authored billing apis are tenantOwner-only but a tenantAdmin must also be able to cancel. It is ONE list for the three routes; subscribeRoles, changeRoles and cancelRoles give a single route its own list, so a buyer may subscribe without being able to re-price or cancel. |
| `routeAccess` | `SubscriptionRouteAccess` | no | `"inherit"` | `inherit`, `open` |  | What to do when checkRoles is empty: `inherit` (the default) derives the injected routes' role gate from this object's authored apis, `open` emits no role gate at all. See SubscriptionRouteAccess for the exact derivation rule and why it can never be stricter than the object's own authored surface. A project whose subscribe route is genuinely buyer-facing declares `open` here, which is also the one-key way to restore the earlier ungated render for an existing project. |
| `publishLifecycleEvents` | `Boolean` | no | `false` |  |  | Opt-in (default false; only a literal `true` on an ACTIVE subscription block counts) that makes the generated payment layer publish this object's normalized SUBSCRIPTION lifecycle events to Kafka (family `subscription`), one topic per event: `<projectCodename>-<service>-service-lcevent-subscription-<object lowercased>-<suffix>`, where the FIXED event list and its suffixes are `subscription.created` -> `created`, `subscription.renewed` -> `renewed`, `subscription.payment_failed` -> `payment-failed`, `subscription.past_due` -> `past-due`, `subscription.canceled` -> `canceled`, `subscription.expired` -> `expired`, `invoice.paid` -> `invoice-paid`, `invoice.payment_failed` -> `invoice-payment-failed`; on a nodejs service also `subscription.paused` -> `paused` and `subscription.resumed` -> `resumed` (state events announced only when the event MOVED the row into `paused` / `active`, so a second report of a pause the row already carries announces nothing; java and dotnet publish the fixed list only). Published by the subscription machine (provider webhooks) AFTER the sys_<Object>Subscription write and AFTER the designer lifecycle hooks, and - for a tokenized provider - by the framework's recharge scheduler at its own status writes (renewed when a charged cycle is stamped, never on a replay; past_due when a row is parked for a missing payment method; payment_failed for every refused recharge attempt; canceled or past_due when dunning is exhausted, per dunningExhaustedState), and on nodejs by a SubscriptionAction: every status move its cancel or refresh writes runs the subscription machine and publishes the event the subscription FSM makes that move with (canceled, expired, past_due, paused, resumed, renewed, created), and its subscribe of a framework-owned (tokenized) subscription publishes `subscription.created` once per journal row. A STATE event (renewed, past_due, canceled, expired, paused, resumed) publishes only when the row ENDS in the state it names; a FACT event (created, payment_failed, invoice.paid, invoice.payment_failed) publishes whenever it is processed. `data` = { eventType, family, object, providerName, providerEventId, occurredAt, orderId, previousStatus, status, dedupeKey, failureReason (payment_failed / invoice.payment_failed only), subscription (an ALLOWLISTED projection of the sys_<Object>Subscription row: id, orderId, customerId, providerName, providerSubscriptionId, planId, statusLiteral, failureReason, currentPeriodStart, currentPeriodEnd, cancelAtPeriodEnd, trialEnd, canceledAt, nextRechargeAt, dunningAttempts, ownerId, createdAt, updatedAt, the tenant column), invoice (invoice.* events: providerInvoiceId, subscriptionId, amount, currency, statusLiteral, periodStart, periodEnd, paidAt), record (this object's own row read by `orderId`, in the shape and unit its db-change event publishes) }; never the raw provider payload or the row's metadata. Delivery is AT LEAST ONCE through the service's lifecycle outbox: each event is written to `sys_lifecycle_outbox` (one row per `data.dedupeKey`, the built envelope plus its retry state) before it is sent, the send is not awaited on the payment path, and a send the broker refuses (logged `PaymentLifecycleEventPublishFailed`) is re-sent by the outbox sweeper with the same envelope id and dedupeKey (every PAYMENT_LIFECYCLE_OUTBOX_SWEEP_INTERVAL_MS, default 30 s; backoff up to one hour; parked `dead` after 50 refusals). A redelivery can repeat an event, and a process that dies between the status write and the outbox write loses that one event: dedupe on `data.dedupeKey`, and reconcile money from the rows, not from the stream. Envelope: `type` = the normalized event type; `actor.tenantId` = the row's tenant in a multi-tenant project. Off (the default) the generated code is byte-identical to a build without the field; the topics are listed by the kafka topic census and pre-created only while it is on. |
| `subscribeRoles` | `String`[] | no |  |  |  | Roles required on the injected subscribe route of this object, POST /v1/subscribe<x>/:orderId, and on that route only. Empty or unset: the route keeps the shared gate (checkRoles, else routeAccess). Declaring any of subscribeRoles / changeRoles / cancelRoles also makes nonOperatorReprice and nonOperatorImmediateCancel default to refusing. |
| `changeRoles` | `String`[] | no |  |  |  | Roles required on the injected CHANGE routes of this object: the re-price route `PATCH /v1/<x>subscription/:subscriptionId` and, on a tokenized iyzico subscription object, the buyer's card change `POST /v1/<x>subscription/:subscriptionId/payment-method` and its read `GET` on the same path (those two have no list of their own). To let a buyer change the card, put the buyer role here and leave nonOperatorReprice unset: plan changes stay operator-only, and the buyer may also toggle cancelAtPeriodEnd on the PATCH. The card change serves only the subscription's own buyer (anyone else gets 404). See docs-site/integrations/payment/iyzico-field-notes.md (Who may subscribe, re-price and cancel). |

| `nonOperatorReprice` | `Boolean` | no | `null` |  |  | May a caller who passes the PATCH /v1/<x>subscription/:subscriptionId gate but is NOT a platform payment operator change the plan (send a providerPlanId)? `true` admits it. `false` refuses it with 403 SUBSCRIPTION_OPERATOR_REQUIRED before the handler runs; the same caller may still change the other fields (cancelAtPeriodEnd). ## Constraints

Property rules:

- `dunningExhaustedState`, `routeAccess` must be one of the allowed values (compared case-insensitively). (`INVALID_ENUM_VALUE`)
- `providerName` must be in the [`codeName`](./value-formats.md#codename) format. (`INVALID_CODE_NAME_FORMAT`)
- `planProperty`, `customerProperty`, `trialDaysProperty`, `cancelAtPeriodEndProperty`, `statusProperty` must be a well-formed [`PropRefer`](./PropRefer.md) (a property of a data object). (`INVALID_PROP_REFER_FORMAT`)
- The items of `lifecycleHooks` must have distinct names (`name`, compared case-insensitively). (`DUPLICATE_ASSET_NAME`)

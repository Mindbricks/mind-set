# 9.9 Compute, graph and decision layers

Three advanced families extend services with heavy computation, a graph projection and
calibrated classification. Each is a separate family for profiles
([chapter 1](01-conformance-model.md#15-profiles-and-compile-time-refusal)); the
reference itself supports each on a subset of its targets and refuses it elsewhere.

## Compute

**Declared by** `service.computeJobs[]` (`ComputeJob`: type, execution mode, spec, input,
result, resource profile, retry policy) and `ServiceLibrary.calculations[]` (functions
called inline as `LIB.<name>(…)`, optionally off the request thread).

**Automatic APIs** on the hosting service:

| API | Type | Notes |
|---|---|---|
| `submitComputeJob` | create | returns a `jobId` at once; callable by other services with a machine token |
| `getComputeJob`, `listComputeJobs` | get, list | |
| `cancelComputeJob` | update | sets `status = cancelled`; cooperative |
| `getComputeArtifact`, `listComputeArtifacts` | get, list | results are always bucket references |
| `getComputeEvent`, `listComputeEvents` | get, list | |

**System objects:** `sys_computeJob` (`jobId`, `type`, `status`
`queued | running | succeeded | failed | cancelled`, `progress` 0..1, `attempts`, `error`,
timestamps), `sys_computeArtifact`, `sys_computeEvent` (idempotent per job and event id).

A submitted job is queued, picked by a bounded worker pool, retried by its retry policy,
and reports progress, result and completion through these records.

> **To verify:** the routes and methods of the compute APIs, and whether completion is
> announced on the bus by a dedicated topic or only by the data-change events of
> `sys_computeEvent`. The `serving` execution mode is not generated by the reference
> today.

## Graph

**Declared by** `projectSettings.graphProvidersSettings` (provider `neo4j`), a data
object's `graphProjection` (labels, identity, projected properties), edges (from relation
properties, edge objects, or `service.graphLayer.edges[]`), and named queries
(`service.graphLayer.queries[]`: reachable nodes, ancestors, descendants, shortest path,
neighbourhood, recommendation, effective permission and explanation, custom).

**What it produces:**

- No routes and no system objects. The graph is a rebuildable projection, never the
  source of truth.
- Every create, update and delete of a projected object **MUST** update the graph after
  the store write: merge the node by its identity with the projected properties; remove it
  on a hard delete; mark it inactive on a soft delete.
- A graph that is unreachable **MUST NOT** fail the write: the projection is skipped and
  counted, unless strict projection is configured.
- Each named query becomes a read function callable from actions and library code
  (`GraphQueryAction`), answering `{ records, keys, ok, status }`; `ok: false` signals an
  outage. Queries of a multi-tenant project are restricted to the caller's tenant except
  for shortest-path and custom queries.

## Decision layer

The decision layer is **not** a rule table. It binds a remote calibrated classifier (a
**decision provider**, `projectSettings.decisionProvidersSettings`) that answers typed
questions about a state with a confidence. Rules that are plain booleans stay in MScript
([chapter 8](08-mscript.md)).

**Questions** (`DecisionQuestion`) are `noul` (yes or no), `choice` (one of at least two
options plus an escape option) or `score` (a position on 2 to 10 ordered levels). The
provider's model **MUST** be pinned.

**Where decisions are used:** the `DecisionAction` of a business API; `decisionSource` on a
property (a decided value with confidence columns); fuzzy domain filters of list APIs;
agent decision gates; object and message moderation.

**What a `DecisionAction` produces** in the API context:
`this.decisions.<action>.<question> = { value, confidence, probabilities, model, undecided, undecidedReason }`
and `this.decisions.<action>._meta`. Below the confidence threshold the configured
`onLowConfidence` applies (escalate, reject, pass through, default answer); on provider
failure, `onProviderError` (fail open, fail closed, default answer).

Rules:

- **Undecided is an answer**: `value: null, confidence: 0, undecided: true`. It is never
  cached and never turned into a guess.
- A decision **MUST NOT** make an authorization decision.
- A narrowing use (a fuzzy filter, moderation) **MUST** fail closed: an undecided value
  is excluded.
- `decisionSource` adds the columns `<prop>DecisionConfidence`, `<prop>DecidedBy`,
  `<prop>DecidedAt`, `<prop>DecisionOverridden`; a provider outage never fails the write,
  and undecided values are filled in later by a background sweep.
- Without credentials, a stand-in answers every question undecided
  ([chapter 10](10-configuration-and-secrets.md#103-missing-provider-credentials));
  `GET /v1/decisions/mock-status` lists providers running on it.

# 9.2 Backend for frontend (data views)

The `bffService` section ([`BFFService`](../spec/BFFService.md)) declares **data views**:
read models that join a main object with aggregates of related objects, ready for a
frontend to list and show.

## Activation

When `bffService.dataViews` is not empty, the compiler **MUST** generate a service named
`bff` that maintains the stored views.

## What a data view is

A [`DataView`](../spec/DataView.md) has a main object, a list of projected properties
(empty means all), `aggregates` (child objects joined by a parent and a child key,
one-to-one or one-to-many, with optional conditions) and `stats`.

| `isStored` | Behaviour |
|---|---|
| `true` | The view is materialised as a search-projection index `<projectCodename>_<viewName>` and kept current from the projection-sync events of its source objects ([chapter 7](07-event-bus.md#72-topic-families)). |
| `false` (default) | The view is computed per request from the main object's record and its aggregates. |

- A deleted main record **MUST** remove its view document; a change to a child record
  **MUST** recompute its parent's document.
- A view may read another stored view. Cycles are validation errors.

## How clients read a view

Views are not read through the `bff` service. A get or list API of any service that sets
`apiOptions.dataViewName` returns the view's document instead of the stored record, with
that API's own authorization and where clause ([chapter 5](05-business-apis.md#54-success-envelope)).
A document that the where clause excludes answers **404**. Library code and event
notifications may also read views.

## Automatic APIs

The `bff` service has operator APIs only:

| Route | Purpose |
|---|---|
| `GET /admin/http-logs` | request log of the service (`bffHttpLog` records) |
| `GET /admin/views/:viewName/schema` | the declared shape of a view |
| `POST /admin/views/:viewName/repair` | rebuild one stored view from its sources |

There is no public route per view.

> **To verify:** an operator route `POST /admin/views/repair-all` exists on one reference
> target; whether it is part of the interface.

## Data objects and events

- `bffHttpLog`: `traceId`, `userId`, `viewName`, `path`, `method`, `statusCode`,
  `latencyMs`, `errorMessage`.
- The service consumes the projection-sync topics of the views' source objects, and
  publishes projection-sync events for a stored view only when another stored view reads
  it.

# PaymentAction

`PaymentAction` drives the **one-time-payment** lifecycle against a native payment provider, start, complete, refresh, callback. Other parts of the payment domain are handled by sibling actions: subscriptions by [`SubscriptionAction`](./subscription-action.md), refunds by [`RefundAction`](./refund-action.md), marketplace payouts by [`PayoutAction`](./payout-action.md). Use the right action for the operation, `PaymentAction` does not handle refunds or recurring billing.

A compiler uses one persisted ticket for payment ownership, customer
resolution and action recording. An addressed provider answer that cannot be
recorded leaves a replayable terminal event for that ticket's order and logs
`PaymentActionIntentUnrecorded` with `reason: record-failed`. An answer naming a
different payment leaves no fallback event. Identity-owner refusals preserve
their 4xx status and detail; only shared `M2M_` and `PAYMENT_` error codes pass
through that boundary.

## When to use it

A checkout opt-in on the order object already generates the start, refresh, browser-return and webhook routes, so most designs need no `PaymentAction` at all. Use one when:

- the start must run inside your own workflow (`stage: "start"` or `"simple"`), or the card must be saved while paying on Stripe or Adyen (a `storePaymentMethod` switch plus a `start` / `simple` stage);
- PayPal's capture after the buyer approved (`stage: "complete"`, in a session API your return page calls). It is the only provider whose completion needs an authored stage: Stripe completes in the browser, iyzico on its generated return routes, Adyen on its generated complete route, Mangopay by itself. `callback` is not needed for any native provider;
- a re-sync of the provider state belongs in your own workflow (`stage: "refresh"`; the generated refresh route does the same).

See [3-D Secure and buyer redirects](../capabilities/payment-3ds-and-redirects.md) for the per-provider matrix.

## Configuration

| Property | Type | Req | Description |
|---|---|---|---|
| `providerName` | `String` |   | Lookup key into `projectSettings.paymentProvidersSettings.paymentProviders[].name`. Selects which native adapter handles this action. When omitted, the provider bound by the order object's `checkout` block is used. |
| `stage` | `PaymentStage` |   | The lifecycle stage this action handles. Defaults to `start` when omitted, so an action without a `stage` starts a payment (it charges the buyer). See enum below. |
| `buyerAbsent` | `Boolean` |   | Default `false`. Declares that this action charges while the buyer is NOT in session: a scheduled or merchant-triggered charge, or a later charge the buyer agreed to in advance. Only such an action may be charged off-session on a Stripe entry with `savedCardOffSession: "verified"` (see **Off-session Stripe charge** below). A buyer-present checkout, a one-click purchase included, must not declare it. It is read at generation time; no request can set it. The off-session charge still needs a proven stored card: a scheduled or system run (cron, an internal call, a Kafka consumer declared `loginRequired: false`) proves it from the order owner through the identity owner's machine-only reads, an HTTP call with the buyer's token proves it with that token, and an anonymous HTTP call proves none and stays on-session. The framework does not check which user calls the API over HTTP: never put such an action on an API the buyer calls while paying. |

Plus the [`BusinessApiAction`](../../spec/BusinessApiAction.md) base properties.

### `stage` values for `PaymentAction`

| Stage | Use |
|---|---|
| `simple` | Single-call payment (no client-side hop). On Adyen the stage never confirms: an answer that asks the buyer for a redirect / 3-D Secure step is returned `started` with its `nextAction`, and the buyer finishes it through the complete route, exactly as after `start`. |
| `start` | Begin a payment; return provider intent / hosted-page URL to the client. |
| `complete` | Finalize after the client completes the provider step. |
| `refresh` | Re-sync the latest provider state for an existing payment. |
| `callback` | Handle the redirect callback after the provider posts back. |

`PaymentStage` also defines `refund`, `dispute`, `subscribe`, `cancelSubscription`, and `payout`, those belong to the dedicated `RefundAction`, `SubscriptionAction`, and `PayoutAction` types, not to `PaymentAction`. A `PaymentAction` that declares one of them is refused at validation with the ERROR `PAYMENT_STAGE_OFF_CONTRACT`: the generated action has no arm for those stages and would fall back to starting a payment, i.e. charge the buyer. Disputes have no action type at all; they arrive on the provider webhook.

## Behaviour

The runtime binds the resolved provider and runs the method of the stage (start, complete, refresh, callback). The provider adapter is selected by:

1. `providerName` if set, looked up in `paymentProvidersSettings.paymentProviders[]`.
2. Otherwise the provider the order object's `checkout` block binds.

The result of the action is the provider's response, typically `{ ticket, clientSecret, hostedPageUrl, … }` on `start`, the captured payment record on `complete`. Bind a `contextPropertyName` to keep the response for downstream actions, or set `writeToResponse: true` to return it to the client.

### The payment ticket (`start` / `simple` on a checkout object)

When the action's checkout target is a data object with `objectSettings.checkout.objectIsAnOrderObject: true`, the `start` and `simple` stages record the charge exactly as the generated start-payment route does, through the same per-object payment manager:

- **Before the provider is called**, the order row named by the `orderIdProperty` binding must exist (a caller's action answers `404 NOT_FOUND`, like an order outside its tenant scope), and the order must not already be paid (otherwise `400 PAYMENT_ALREADY_COMPLETED` ("Payment already completed")). A replayed workflow therefore cannot charge the same order twice. Trusted system appliers skip the caller authorization gate and retain the charge seam's `404 ORDER_NOT_FOUND` for a missing order.
- **The ticket is claimed before the charge.** The start writes the order's `sys_<X>Payment` ticket first, as a claim (`paymentStatus: start_claimed`), under the unique order index for a new order and as a compare-and-set on an existing ticket (a retry after a failed attempt). Of two starts of one order that overlap - two workflow runs, a double submit, this action and the generated start route at once - exactly one charges; the other answers `409 PAYMENT_START_IN_FLIGHT` without calling the provider. A claim older than the start-claim TTL (default 300000 ms: a start that crashed before recording) is taken over by the next start.
- **An open intent is resumed, never charged twice.** When the order's ticket still names an intent that waits for the buyer (a `started` ticket: a 3-D Secure challenge the buyer closed, a hosted page, an authorised intent awaiting capture), the start first reads that intent from the provider. Still open, and the start asks for the same order, the same amount and currency the ticket recorded and the same payment method (the ticket records `metadata.startMethodRef`, `none` or a digest of the saved method id): the start returns THAT intent (`pendingIntentReused: true`, the existing `paymentTicketId`, and its buyer step) without charging, claiming or writing anything, so the buyer finishes the same challenge. Stripe's step is read live (the current `nextAction.clientSecret` / `nextAction.raw`). iyzico's reads carry no step, so an iyzico ticket keeps it in `metadata.resumeAction` and the resume answers it until it expires: the hosted page's `paymentPageUrl` until its token expires (`tokenExpireTime`), or the 3-D Secure `threeDSHtmlContent` until the 3-D Secure action TTL (default 600000 ms); `nextAction.actionExpiresAt` names the instant (also inside `nextAction.raw`), and a 3-D Secure form over 32768 characters is not kept (logged WARN `PaymentResumeActionNotKept`; its resume answers no step). Still open but the amount, the currency, the order or the payment method changed (another saved method, a method where the first start had none, or none where it had one): `409 PAYMENT_START_INTENT_PENDING` until the first intent is completed, failed or canceled at the provider, the reason in the problem detail - the open intent is never answered for another method. iyzico is the exception where the open intent provably cannot capture any more: a hosted page whose token expired (plus 60 seconds) with no payment under way on it (the detail still reads `INIT_CHECKOUT_FORM`; a form whose detail reads `INIT_THREEDS` / `CALLBACK_THREEDS` is a payment in flight and answers the 409), or a 3-D Secure payment iyzico still reads `INIT_THREEDS` (the bank never answered, and the service sends `3dsecure/auth` only for the payment the ticket names). Then a changed method or amount, or a resume after the recorded step expired, is a NEW attempt instead (logged WARN `PaymentStartAttemptSuperseded` with the left-behind payment id); once the bank answered (`CALLBACK_THREEDS`) it is the 409. Stripe never re-confirms an open intent with another method from the start: pay it with another card by confirming it in the browser on its `client_secret`. The same 409 answers when the provider cannot be read (logged WARN `PaymentStartPendingIntentUnreadable`) - except on iyzico, where the SAME start (same order, amount, currency and method) is resumed from the step kept on the ticket while it has not expired (logged WARN `PaymentStartResumedFromRecordedStep`; a hosted form token and a 3-D Secure payment each capture at most once, so handing the same step back cannot charge twice) -, when the ticket was opened with another provider, and when the provider already captured the intent but its capture is not recorded yet (refresh the payment to record it). An intent the provider reports `failed` or `canceled` is a new attempt. On `simple` the resumed intent is returned as it is (not confirmed again). Adyen cannot be read back: its open action is resumed from the TICKET (the same payment id, redirect and action) while the action's local expiry (default 30 minutes) has not passed, and answers the 409 after it, until Adyen's failure / cancel notification of that attempt or an operator's reconciliation (the audited admin release route, see the Adyen notes of the [payment providers](../providers/payment.md)) frees the order.
- **The provider idempotency key is derived from the order.** Every charge of one start attempt is sent with `mbs-<orderId>-<attempt>` (stored on the ticket as `idempotencyKey`; it replaces a caller-supplied key). A start that takes over a stale claim reuses that attempt's key, so a charge that did land is answered again instead of taken twice; a new attempt (after a decline or a failed payment) gets a new key, so the buyer can retry with another card.
- **After the provider answers**, the `sys_<X>Payment` ticket is written (tenant and owner stamped from the persisted order row), and an intent the provider settled synchronously (`success` or `failed`) is recorded as a `payment.captured` / `payment.failed` row on `sys_paymentEvent` and dispatched before the action returns. That dispatch is what runs the checkout `lifecycleHooks` (`afterPaymentCaptured` / `afterPaymentFailed`). An intent that still needs the buyer (3-D Secure, a hosted page) leaves a `started` ticket; the provider webhook, the refresh route or the admin simulate-capture route completes it later. On iyzico the generated service completes both shapes itself when iyzico posts the buyer back: the hosted Checkout Form through `POST /v1/payments/checkout-return/<providerName>`, and a saved card's 3-D Secure through `POST /v1/payments/threeds-return/<providerName>`, which calls iyzico's `3dsecure/auth`. A hosted-form payment whose browser never comes back is settled the same way from iyzico's Checkout Form webhook. On an iyzico-bound order with a stored-method opt-in (`checkout.configuration.storePaymentMethod: true`, or `subscription.configuration.storePaymentMethod: true` on an order that also has a subscription block), the `start` / `simple` stage opens the hosted form with the buyer's own card key too, so the buyer can save the card while paying (the card is filed in the ticket owner's wallet when the payment settles). So an iyzico design authors no `complete` stage: the payment is captured or failed, and `afterPaymentCaptured` / `afterPaymentFailed` have run, before the buyer reaches the start's `return_url`.
- **Stored-method enrolment.** When the order object sets `storePaymentMethod: true` in its checkout configuration (`checkout.configuration.storePaymentMethod`, the switch a checkout-only order uses) or in its subscription configuration (`subscription.configuration.storePaymentMethod`), `start` and `simple` ask the provider to keep the buyer's card; either switch enrols. Adyen sends `storePaymentMethod: true`; Stripe sends `setup_future_usage: "off_session"` (Stripe attaches the card to the buyer's customer once the payment succeeds, and the `payment_method.attached` webhook files it in `sys_paymentMethod` for the user who owns that customer's payment-customer mapping); iyzico opens the hosted form with the buyer's own card key, as described above. It is never read from the request: with the opt-in off a body `storeMethod` is dropped, and a caller's `providerOptions.setup_future_usage` is refused with `400 PAYMENT_PROVIDER_OPTION_NOT_ALLOWED`. A Stripe payment that needs 3-D Secure is finished by Stripe after the browser step; no `complete` stage is needed for Stripe.
- **Off-session Stripe charge.** Off by default. When the Stripe entry sets `savedCardOffSession: "verified"` beside `savedCardThreeDSMode: "verifyOnce"`, a `start` or `simple` stage of an action declared `buyerAbsent: true` that names a proven stored card (the order owner's on a system run, the caller's own on an HTTP call), already marked 3-D Secure verified, is charged as a merchant-initiated transaction (`off_session: true`, `confirm: true`, no buyer step). Only such an action does it, never an action without `buyerAbsent` (the default) and never the generated start route; the request cannot ask for it (`providerOptions.off_session` stays `400`, and a body `buyerAbsent` is ignored). Typical buyer-absent actions are a scheduled renewal or card-on-file charge run by a cron job or an event consumer, an agreed top-up made on the buyer's behalf, and a later charge the buyer agreed to in advance, such as one an AI assistant confirmed earlier. A scheduled or system run (a trusted cron / internal transport, or a Kafka consumer declared `loginRequired: false`, recognised from the transport and never from the request) proves the card from the ORDER OWNER: the order row's owner column, the owner's payment-customer mapping and stored-method row read through the identity owner's machine-only APIs, and the provider's attachment of the card to that customer. It needs the `auth` identity owner and an owner column on the order object. An HTTP call proves the card with the caller's forwarded token as before; an anonymous HTTP call proves none and stays on-session. A buyer-present checkout must not declare it, and the runtime does not check which user calls the API over HTTP, so keep such an action off any API the buyer calls while paying. A declaration that can do nothing (another provider, a Stripe entry without `verified`, a `complete` / `refresh` / `callback` stage, a marketplace order, no checkout order object, an order object bound to a provider entry of another brand) draws the warning `PAYMENT_ACTION_BUYER_ABSENT_INERT`. It carries no 3-D Secure liability shift and is meant only for charges made while the buyer is absent, under a stored-credential agreement. An issuer that still wants the buyer answers `402` `PAYMENT_DECLINED` with `providerErrorCode: "authentication_required"`; the order's claim is released, so the buyer can pay on-session. See the [payment providers](../providers/payment.md) (Stripe, off-session charging).
- **A provider that refuses the charge** (a card decline thrown by the adapter) releases the claim: it leaves no ticket and no event (a retry's ticket gets back what it held), the same as on the route. Only a DEFINITE refusal releases it: a decline, or a refusal that proves the provider moved no money (a credential or permission failure, a request the provider rejected with a 4xx other than 408 / 409 / 425 / 429, or a refusal the provider answered in its body - iyzico's HTTP 200 `status: failure` - unless the status is a 5xx). **Any other failure keeps the claim and its key** - a lost connection, a timeout, a provider 5xx or throttle, an error nothing classifies - because the charge may have landed while its answer was lost. The caller gets the error (a lost provider answer is the retryable `502 PAYMENT_PROVIDER_UNAVAILABLE`); a retry inside the start-claim TTL answers `409 PAYMENT_START_IN_FLIGHT`, and the first start after the TTL takes the claim over and charges under the SAME key, so a provider that honours it answers the charge that landed instead of taking a second one (logged WARN `PaymentStartOutcomeUnknown` with the order and the key). A takeover whose charge is refused with anything but a decline keeps the claim too: its key already rode an earlier charge. Accepted edge: Stripe stores the answer of a keyed request that reached it, a `500` included, so after a genuine provider 500 the order's retries keep failing until the key expires (up to 24 h). The error reaches the caller, or with `checkout.onPaymentError: "continueRoute"` the action returns `{ success: false, statusLiteral: "failed", error }`. A failure to write the ticket for a charge that was taken is never turned into that failed outcome: it always reaches the caller.

The action's answer is the provider intent plus `paymentTicketId` (its `metadata` without the provider-only `buyer`, `billingAddress` and `shippingAddress` blocks, also inside a `providerOptions` or `paymentUserParams` block nested in it: the national identity number, the buyer ip and the addresses reach the provider and stay out of the answer the browser may receive), and `lifecyclePending: true` when the synchronous lifecycle did not settle within the synchronous settle timeout, or when the provider's capture webhook arrived before the ticket recorded the intent (that event is left for the replay worker, which runs the capture lifecycle once, instead of being settled with nothing run). The bound covers the whole synchronous path, including recording the event on `sys_paymentEvent`: a slow or stalled event store also answers `lifecyclePending: true` at the bound, and the event is still recorded and dispatched once the store responds.

**Answer shape, field by field** (`NormalizedIntent`, built for a checkout
order object by the per-object payment manager, otherwise by the common
payment manager). Its
`nextAction` is the **one client-facing buyer-step shape** every payment answer
carries: the generated `PATCH /v1/start<x>payment/:orderId` route, its
resume and the buyer status read answer the same block, built the same
way; see
[3-D Secure and buyer redirects](../capabilities/payment-3ds-and-redirects.md), "The common contract":

| Field | Meaning |
|---|---|
| `providerIntentId` | the provider's own intent/payment id |
| `providerStatus` | the raw provider-side status string |
| `statusLiteral` | `success`, `started`, `failed`, `amount_mismatch`, `captured_after_cancel` (a `complete` / `refresh` / `callback` of a payment canceled on this side that the provider reports captured: not paid, under review), ... |
| `amount` / `currency` | what the provider was charged |
| `nextAction.requiresAction` / `requiresRedirect` | booleans describing the buyer step |
| `nextAction.redirectToUrl` | navigate the browser there when `requiresRedirect` |
| `nextAction.clientSecret` | Stripe's client secret; on Adyen this slot is unused (the action carries Adyen's data in `raw`) |
| `nextAction.raw` | the provider-specific blob (Stripe's `next_action`, iyzico's `paymentPageUrl` / `threeDSHtmlContent`, Adyen's `action`). On a resumed iyzico/Adyen step it also carries `actionExpiresAt` |
| `nextAction.actionExpiresAt` | the instant the recorded buyer step stops being handed back (iyzico: the hosted page's token lifetime or the 3-D Secure TTL, also on the first start); `null` when none is recorded |
| `nextAction.requiresConfirmation` / `publishableKey` | further keys of this answer |
| `paymentTicketId` | the `sys_<X>Payment` ticket id |
| `pendingIntentReused` | additive `true` when `start` / `simple` resumed the order's open payment |
| `lifecyclePending` | additive `true`, as described above |

On a marketplace order object (a `marketplace` block with a `sellerAccountProperty`), the intent stages call the per-object manager starts the payment directly, which writes the same ticket. An action with no checkout object behind it (only an explicit `providerName`) has no ticket table and calls the provider only; its `start` / `simple` still send the signed-in buyer from the session (email, name, surname - never from the request), as the ticketed stages do, so an iyzico hosted form that may save the buyer's first card is opened for a signed-in buyer instead of refused `400 PAYMENT_BUYER_EMAIL_REQUIRED`, and its answer is stripped the same way. A saved payment method such a start / simple names must be the caller's own as well, proven before the provider is called by the same check the ticketed stages run (a checkout order object of the service hosts it; the first by name): another buyer's method answers `403 PAYMENT_METHOD_NOT_OWNED`, an absolute role included. In a service with no checkout order object there is no stored method to prove, so a saved-instrument id (PayPal, Adyen, iyzico, Mangopay, Paddle) is refused and a Stripe id passes only as a fresh token attached to no customer. The `complete` stage proves a payment method it names the same way before the provider's confirm (on a checkout order object through that object's own manager, otherwise as above): the caller's own proven stored method or a fresh token, else `403 PAYMENT_METHOD_NOT_OWNED` and nothing is confirmed. The customer the open payment was started with is no proof, and a system caller with no user proves nothing, so it may complete only without naming a saved method. The `complete`, `refresh` and `callback` stages address an existing intent by id: they never create a ticket, but on a checkout object they do record what they observed on the EXISTING one (below).

### The payment ticket (`complete` / `refresh` / `callback` on a checkout object)

On a checkout order object these stages hand what the provider answered to the per-object manager, which updates the order's EXISTING `sys_<X>Payment` ticket and, for a terminal outcome (`success` / `failed`), runs the capture lifecycle through the same seam the payment-layer routes use. That lifecycle is where the order-side effects of a capture live: the `afterPaymentCaptured` / `afterPaymentFailed` hooks, the settlement accrual, and the invoice bridge that `issuePolicy: "onPaymentCaptured"` rides on; all of them find the payment through the ticket. The lifecycle event is keyed on the provider intent, so this record, a later webhook and a route `refresh` for the same intent run the hooks once. A ticket already `success` is never downgraded or re-pointed (`order-already-captured`), and a recording failure is logged (`PaymentActionIntentUnrecorded`) while the stage's result is still returned. When the record itself fails (a database fault on the ticket write, after the provider answered) the stage never throws (a `500` would invite a second payment): a terminal answer of the payment the pre-provider gate resolved is still written as its synthetic terminal event row in `sys_paymentEvent` under the order that payment's ticket records, so the intent machine settles it or the replay worker re-drives it (the row is keyed by the payment, the outcome and the order, so a later record of the same observation finds it and the lifecycle runs once). That includes the one move described below for `complete` / `refresh` / `callback`: a captured payment the provider answers under another id than the ticket holds (an iyzico Checkout Form token answered under its numeric payment id), under the same conditions (a capture, the caller addressed the ticket's own payment id, the provider attributes the payment to the ticket's order). Its row names the ticket's payment id, so when the row is settled the ticket that still holds the token follows the captured payment before the capture lifecycle (and its capture-amount check) runs on it; an answer attributed to another order writes nothing. The fault is logged at ERROR as `PaymentActionIntentUnrecorded` with `reason: "record-failed"`, the payment id, the order the row is filed under (`orderId`, the ticket's order; the provider's own attribution rides as `providerOrderId` and the caller's claim as `callerOrderId`), and the event row's outcome (`eventOutcome`) or why it was not written (`eventError`).

**`complete`, `refresh` and `callback` are gated before the provider, as the generated routes are.** Before the provider is asked to confirm or read the payment, the stage checks what the generated refresh / complete routes check: the `sys_<X>Payment` ticket recorded for the payment id the caller sent must exist (otherwise `400 PAYMENT_NOT_STARTED`), its order row must exist (`404 NOT_FOUND`), the caller must own that order (the routes' ownership check over the order and the ticket: another user is `403 NOT_OWNER`, a request with no session `401 LOGIN_REQUIRED`, an absolute role and a verified service-to-service caller that carries no user identity are admitted; a service-to-service caller that forwards a user session is that user and is compared like one), a ticket that is still a start claim is `409 PAYMENT_START_IN_FLIGHT` (as the routes' complete / refresh answer it), and `complete` of an order already paid is `400 PAYMENT_ALREADY_COMPLETED` ("Payment already completed"). A payment id is not a credential. Only a system applier has no caller to compare (a trusted cron / internal transport, or a kafka consumer declared `loginRequired: false`): for it the ticket check runs and the ownership check does not, exactly as for [RefundAction](./refund-action.md). A hosted-checkout return that reaches the api without the buyer's session should use the generated checkout-return route, whose token is its credential; an iyzico 3-D Secure callback uses the generated threeds-return route, whose credential is the posted `paymentId` together with the attempt's `conversationId`. Under `checkout.onPaymentError: "continueRoute"` a gate refusal is the failed outcome, except the OWNERSHIP refusal (`403 NOT_OWNER`, `401 LOGIN_REQUIRED`), which is always the request's error (see "Where a refusal surfaces").

**`complete`, `refresh` and `callback` never choose the order.** These stages address an EXISTING payment by the id the caller sends, so the order that payment is recorded against comes from the provider's own answer (the order the provider's payment names) or from the ticket already recorded for that payment id - never from the caller's request. An `orderId` the caller sends is only checked: if it disagrees, nothing is recorded or dispatched and `PaymentActionIntentUnrecorded` is logged with reason `order-mismatch`. These stages also never create a ticket (`no-ticket` - only `start` / `simple` do) and never move a ticket to another payment (`ticket-bound-to-another-payment`), with one exception that mirrors the hosted-checkout return route: an open ticket follows a payment the provider itself attributes to the order and reports captured, only when the caller addressed the ticket's OWN payment id (an iyzico Checkout Form token answered under its numeric payment id). If that capture's amount or currency does not equal the ticket's, the ticket still follows the payment but is recorded as `amount_mismatch` (with `metadata.amountMismatch` and the `PaymentCaptureAmountMismatch` ERROR line), nothing is dispatched, and the stage answers `statusLiteral: "amount_mismatch"`.

**The payment id must be a string.** `complete`, `refresh` and `callback` accept the payment id (`providerIntentId`, else `paymentId`; on `callback` read from the request body, query and path parameters) only as a non-empty string. An array, object, number, blank or missing id answers `400` with `errorCode: PAYMENT_ID_INVALID` before the provider is called: several provider adapters build the vendor URL in a way that turns a one-element array back into a real payment id, while every comparison on the runtime side would have seen "no id".

**The provider records the runtime's order, amount and urls.** Every adapter writes the fields the runtime owns AFTER the caller's `metadata` / `providerOptions`: the charged amount and its currency, the order a provider payment is attributed to (Stripe `metadata.orderId`, Paddle `custom_data.orderId`, PayPal `reference_id` / `custom_id`, iyzico `basketId` / `conversationId`, Adyen `reference`, Lemon Squeezy `custom.orderId`), the return and callback urls, and the capture mode. Caller `providerOptions` can add provider extras (installment choices, descriptors, a `mockScenario`) but cannot change any of these. Money routing (a Stripe `transfer_data`, an Adyen `splits`, a PayPal `payee`, a Mangopay wallet or fee, an iyzico sub-merchant key in a basket item) is the runtime's as well, and a caller that sends it - or any key off the provider's accepted list - is refused with a typed `400` (`PAYMENT_ROUTING_FIELD_FORBIDDEN` / `PAYMENT_PROVIDER_OPTION_NOT_ALLOWED`) before the provider is called. So is the PAYMENT SOURCE - which saved card, token, vault id or customer pays, and whether the charge is merchant-initiated (Stripe `customer` / `payment_method` / `off_session`, Adyen `paymentMethod` / `shopperInteraction` / `recurringProcessingModel`, PayPal `paymentSource`, iyzico `paymentCard`): it comes only from the runtime's own resolution for the buyer. An accepted extra that is itself an object (Adyen `additionalData`, Stripe `payment_method_options` ...) is checked at every depth for the same keys, so a nested `additionalData.manualCapture` or `payment_method_options.card.capture_method` is refused too, naming its full path. 3-D Secure / SCA are the runtime's (Adyen `executeThreeD` / `scaExemption` / `threeDS2RequestData`, Stripe `request_three_d_secure`, iyzico `forceThreeDS`, Mangopay `secureMode` are refused), and Paddle always charges an inline price for the order amount, never a `metadata.priceId`. A key is checked for its structure first, at every depth (`metadata` included): a key containing `[` or `]`, which a bracket form encoder such as Stripe's would turn into a different parameter path, and the names `__proto__` / `constructor` / `prototype` are refused with `400` `PAYMENT_PROVIDER_OPTION_NOT_ALLOWED`; denied names are compared case-insensitively and inside arrays. A saved payment method the stage passes as `paymentMethodId` must belong to the calling user (one of their stored methods, or for Stripe a fresh token or a method on their own provider customer); another buyer's method answers `403` `PAYMENT_METHOD_NOT_OWNED` before the provider is called. Ownership is the stored method's `userId` against the caller's, so an absolute role cannot pay with a customer's card. On iyzico (one `cardUserKey` per buyer) the saved card id `<cardUserKey>:<cardToken>` must also carry the caller's own stored key (`sys_paymentCustomer.cardStorageKey`, written only by the runtime on the buyer's first save) and be listed by iyzico under it; a bare-token card id answers `400` `PAYMENT_METHOD_ID_INVALID` (save the card again). These iyzico rules follow the provider the stage actually runs on: a marketplace stage whose `providerName` names another provider on an iyzico-bound object keeps that provider's own id shape and ownership proof. The id is trimmed and that one value is checked and sent; a `paymentMethodId` that is not a non-empty string answers `400` `PAYMENT_METHOD_ID_INVALID`. Stripe `payment_method_options.card.moto` is refused like the other 3-D Secure keys.

**A capture that does not match the ticket is not paid.** Whatever a stage reports, a captured payment whose amount, currency or order differs from the ticket (the amount the runtime took from the order at start) is recorded as `amount_mismatch` instead of `success`: no `afterPaymentCaptured` hook, no invoice and no settlement accrual run for it, `PaymentCaptureAmountMismatch` is logged at ERROR, and the stage answers `statusLiteral: "amount_mismatch"` - so a later workflow step that branches on `success` cannot fulfil it. See [the capture-amount gate](../capabilities/payment-workflow.md#the-capture-amount-gate).

### Where a refusal surfaces: an error status or `actionFailures`

Most PaymentAction failures follow WHERE the action runs. Before the api's main write (a `get` api, or a stage that runs before the write) every error is the request's own answer with its status. After a create / update / delete api has committed its row (the usual `payOrder` shape: the update writes the order, then the PaymentAction starts the payment) the row stands, so a PAYMENT outcome comes back as a `2xx` with `actionFailures: [{ action, errorCode, error }]` (the post-write rule): `409 PAYMENT_START_INTENT_PENDING` (the open intent could not be resumed: a changed amount or method, or a step that cannot be proven open), `409 PAYMENT_START_IN_FLIGHT`, `400 PAYMENT_ALREADY_COMPLETED` ("Payment already completed"), a provider decline. The api did its own work and the payment did not start; the client branches on `actionFailures[].errorCode` and nothing was charged (`PAYMENT_ALREADY_COMPLETED` is the runtime's own refusal of an order that is paid or past the capture, never a provider decline; the generated start / complete routes answer it with the same code). An AUTHORIZATION refusal is different: it is a security answer, never a partial success, so it is the request's error at every position, after a committed write too, and whatever `checkout.onPaymentError` says - another buyer's saved method (`403 PAYMENT_METHOD_NOT_OWNED`), an order the caller may not pay or address (`403 NOT_OWNER`, `401 LOGIN_REQUIRED`, `403 OWNER_UNRESOLVED*`, another tenant's order `404`). The payment layer marks these errors  and the post-write boundary lets them through, exactly as it lets a ValidationAction refusal through; they are refused before the provider is called and before any ticket is claimed, so nothing started. (An action that declares `onActionError: completeApi` still swallows them into `actionFailures`: the designer asked for the api to complete.) A column the api's own main write sets - a `paymentStartedAt` in the update's dataClause - is written before the action runs, refused or not: write such a column after the action instead, from its answer (only when the answer carries no `pendingIntentReused: true` and the response no `actionFailures` entry for it) or from a payment lifecycle hook, so a repeated or refused start does not move it.

**A provider refusal names the provider's code.** When the provider itself turned the payment down - iyzico's HTTP 200 answer with `status: "failure"` (a decline such as `10051`, insufficient funds), or an iyzico `4xx` - the `actionFailures` entry is the one the generated start route answers as `422`: `errorCode: "PAYMENT_PROVIDER_REQUEST_REJECTED"`, the fixed `error` "The payment provider rejected the request", plus `providerErrorCode` (the provider's own error code, 1-64 characters of `[A-Za-z0-9_.-]`) and, for a card-validation refusal, `reason` (`card_number_invalid`, `card_expired`, `card_expiry_invalid`, `card_cvc_invalid`, `card_holder_name_invalid`, `card_not_supported`; the iyzico table of the [payment providers](../providers/payment.md)). The same rules decide both answers: a Stripe card decline keeps its `PAYMENT_DECLINED` pair ("The payment was declined by the provider") and carries Stripe's decline code (`insufficient_funds`; `generic_decline` for the codes Stripe asks merchants not to reveal) and, for a card-validation refusal, `reason` (the Stripe table of the [payment providers](../providers/payment.md)); any other decline the adapter classifies itself (`PAYMENT_DECLINED`), a runtime refusal and any other failure carry neither key, and the provider's sentence, which can quote card or buyer fragments or name live object ids, never reaches the response. Under `checkout.onPaymentError: "continueRoute"` the failed outcome (`{ success: false, statusLiteral: "failed", error }`, `error` being the same fixed sentence) carries the same `providerErrorCode` / `reason`. For any other failure the outcome's `error` is the detail the generated payment routes answer for the same error: a runtime refusal keeps its own sentence (`Payment already completed for <order>`), a provider-origin failure reads a fixed provider sentence, and an unclassified failure reads `Internal server error`; the provider's own text goes to the service log only. Before the api's main write (a `get` api, or a stage that runs before the write) the refusal is the request's own error, the start route's answer exactly: `422` (an iyzico `4xx` keeps its own status) problem+json with `errorCode: "PAYMENT_PROVIDER_REQUEST_REJECTED"`, the fixed `detail`, and `providerErrorCode` / `reason` as extension members; a Stripe card decline is the start route's `402 PAYMENT_DECLINED` with the same members. 

### Property bindings

The intent-creating stages (`start`, `simple`) build `CreateIntentInput` from the parent data object's [`CheckoutConfig`](../../spec/CheckoutConfig.md), `amountProperty`, `currencyProperty` / `currencyStaticValue`, `orderIdProperty` (`orderOwnerIdProperty` is not one of them: it is declarative, and no runtime code reads it). Each of those bindings is resolved, in order, against: the loop item (inside a [`LoopAction`](./loop-action.md)), the request parameters, the persisted order row, then the manager scope. An explicit request parameter of the same name therefore still overrides the declared binding.

**The provider customer is never the caller's.** The customer the provider charges is read from the persisted order row's `customerId` column only. It is never taken from a request parameter, the loop item or the manager scope, even when the api declares a parameter named `customerId` or `providerCustomerId` (the same rule [`SubscriptionAction`](./subscription-action.md) and the generated start route follow). Without it, a caller that also names a saved `paymentMethodId` could charge another buyer's stored card for their own order.

**The provider customer is resolved from the (user, provider) mapping, created on first charge; the order owner id is never a provider customer id.** `orderOwnerIdProperty` names the buyer's platform user id and is declarative: no runtime code reads it, and the ownership checks use the data object's owner field (sent as a customer id, Stripe would refuse every buyer with no stored customer as `No such customer: '<userId>'`). When the row carries no `customerId` and the provider keeps saved customers (Stripe), `start` and `simple` on a checkout order object resolve the paying user's customer exactly as the generated start route does: the `sys_paymentCustomer` mapping row for (user, provider) on the auth service, or, on a miss, one provider customer created and its mapping row written with the buyer's session. A provider without saved customers, or a project with no auth service, charges with no customer. A resolution that fails refuses the payment before the provider is charged: `401 PAYMENT_CUSTOMER_SESSION_MISSING` when no buyer session can be forwarded to write the mapping, `502 PAYMENT_CUSTOMER_UNRESOLVED` for unresolved server or transport failures. An identity-owner `4xx` keeps its status and public detail; only shared `M2M_` / `PAYMENT_` error codes are relayed. It never charges with an empty customer instead. An action run by a session-less system caller (a cron or internal-call controller, or a kafka controller declared `loginRequired: false`) maps the customer for the persisted order row's owner column (`sessionSettings.isOwnerField`) instead, through the auth service's machine-only `createPaymentCustomerForMachine`; on an order object with no owner column such an intent-creating action is the design-time ERROR `PAYMENT_SESSIONLESS_ACTION_ORDER_UNOWNED`. In a multi-tenant project a tenant-level order whose persisted row carries no tenant is refused `400 PAYMENT_ORDER_TENANT_UNRESOLVED` before the customer, the claim or the provider. A GLOBAL order of a multi-tenant project (an object with no tenant column) names no tenant for the auth service's machine-only payment-customer apis, which are tenant-scoped there: a bearer-less start on it is refused `400 PAYMENT_SESSIONLESS_TENANT_UNRESOLVED` before any owner or provider call, and an intent-creating action that a session-less system caller runs on such an object is the design-time WARNING `PAYMENT_SESSIONLESS_START_GLOBAL_ORDER` (run it from an api the paying user calls with their own session, or make the object tenant-level).

**Dotted paths are supported.** A `PropRefer` slot may name a nested path, `"order.total"`, `"customer.billing.currency"`, and the resolver walks it one segment at a time on each of those sources. A missing intermediate segment resolves to nothing (the binding falls through to the next source, then to `null`); it never raises a runtime error. The same rule applies to [`SubscriptionAction`](./subscription-action.md), [`RefundAction`](./refund-action.md), and [`PayoutAction`](./payout-action.md).

For the full two-call dance and how it integrates with system data objects (`sys_<X>Payment` rows, provider webhooks), see the [payment workflow](../capabilities/payment-workflow.md).

Missing and out-of-scope orders on a caller's `start` or `simple` action both
answer `404 NOT_FOUND` with detail `order not found`, including after the api's
main write has committed and under `onPaymentError: "continueRoute"`. They
refuse before any provider call or payment-ticket claim.

## Example

A "start payment" action that hands the provider's next step back to the client (on Stripe the PaymentIntent `client_secret`, on a hosted provider the hosted-page URL):

```json
{
  "name": "startCheckout",
  "providerName": "stripeProd",
  "stage": "start",
  "contextPropertyName": "checkoutTicket",
  "writeToResponse": true
}
```

On PayPal the capture after the buyer approved is a server step that no generated route makes, so a session business API called by the return page completes the same payment (it declares the payment id as a caller-supplied parameter, `paymentId` or `providerIntentId`). Adyen's details round trip is the generated `PATCH /v1/complete<x>payment/:orderId` route, not an authored API. Stripe has no such step: Stripe finishes the intent after the browser's 3-D Secure step and the generated webhook route records it (see the [payment providers](../providers/payment.md)), so a Stripe flow has no `complete` API.

```json
{
  "name": "capturePaypalOrder",
  "providerName": "paypalProd",
  "stage": "complete",
  "contextPropertyName": "paymentResult",
  "writeToResponse": true
}
```

A `start` on an iyzico entry with `directCardEntry: true` takes a card typed on your own frontend, but only through request parameters the API DECLARES: `cardInfo` (Object) and `saveCard` (Boolean), beside `return_url`. An undeclared card is silently dropped and the buyer gets the hosted form. A complete `payOrder` example, with the `return_url` guard, is in [Add a payment checkout](../cookbook/add-payment-checkout.md#a-card-entered-on-your-own-frontend-payorder-with-cardinfo-and-savecard).

## Errors

- Unknown `providerName`, throws at project validation time.
- `start` / `simple` on a checkout object whose order row does not exist, `404 ORDER_NOT_FOUND`, before the provider is called.
- `start` / `simple` on an order whose ticket is already `success`, `400 PAYMENT_ALREADY_COMPLETED` ("Payment already completed"), before the provider is called.
- `start` / `simple` while another start of the same order is in flight, `409 PAYMENT_START_IN_FLIGHT`, before the provider is called.
- `start` / `simple` on an order whose ticket still holds an open intent (3-D Secure pending) with a changed amount, currency, order or payment method, or whose intent cannot be read, `409 PAYMENT_START_INTENT_PENDING`, before any charge; with the same order, amount and method the open intent is returned instead, on iyzico also when it cannot be read, from the step kept on the ticket until that step expires. After a committed main write this reaches the caller as an `actionFailures` entry, while an ownership refusal (`403 PAYMENT_METHOD_NOT_OWNED`, `403 NOT_OWNER`) stays the request's error (see "Where a refusal surfaces"). On iyzico a changed method or amount opens a new attempt where the open intent provably cannot capture (an expired hosted page with no payment under way on it, a 3-D Secure payment at `INIT_THREEDS`). The claim of that new attempt also requires the ticket's status to be the one the decision read, so a capture recorded meanwhile is never overwritten (409).
- `complete` / `refresh` / `callback` addressing a payment id with no ticket, `400 PAYMENT_NOT_STARTED`; a payment of an order the caller does not own, `403 NOT_OWNER`; no session, `401 LOGIN_REQUIRED`; a ticket that is still a start claim, `409 PAYMENT_START_IN_FLIGHT`; `complete` of a paid order, `400 PAYMENT_ALREADY_COMPLETED` ("Payment already completed"). All before the provider is called.
- Any stage whose ticket write keeps losing to other writers of the same ticket (a callback, the webhook, a return route or a refresh moving it between this stage's read and its write, four times in a row), `409 PAYMENT_TICKET_CONTENDED`, AFTER the provider was called; nothing was written or announced by this call, so read the payment again.
- Provider does not support the requested stage, fails with a capability error from the bound adapter.
- Webhook signature verification is **not** done here, and no webhook-receiving API is needed for payment events: the generated `POST /v1/payments/webhook/<providerName>` route verifies them and runs the lifecycle hooks. A `complete` / `refresh` / `callback` stage refuses an anonymous caller (`401 LOGIN_REQUIRED`), so a provider webhook cannot drive it.

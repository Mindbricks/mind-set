# Object visits

**Also searchable as:** visitTracking, visitSettings, view count, read receipt, dwell time,
engagement signal, `_visit`, confirm visit, visit history, `sys_<Obj>Visit`.

**Object visits** record who consumed which object, how (`access` / `view` / `read` / `seen`) and
when - the raw behavioural history the recommendation engine, analytics and simple engagement
counters are all built from. Declare `objectSettings.visitTracking` once on the data object (the
storage decision - history, a quiet counter, retention) and `apiOptions.visitSettings` on each
Business API that is a real visit of it (the trigger decision, with its signal and, optionally, a
frontend-confirmed dwell).

A visit is an **analytics signal, never an authorization or billing input**. It is not the retired
`GetOptions.setAsRead` / `ListOptions.setAsRead` reborn under a new name - read state is one
narrow *output* of this pattern (see [Privacy and retention](#privacy-and-retention)), not its
purpose.

> **Reference:** [`VisitTracking`](../../spec/VisitTracking.md) ·
> [`VisitSettings`](../../spec/VisitSettings.md) ·
> [`VisitContextField`](../../spec/VisitContextField.md)

Not every compiler generates every part of this pattern. A declared field that a compiler does not
generate yet is reported at design time (`VISIT_TRACKING_NOT_YET_EMITTED`, a warning), and an object
whose service targets a language that does not generate the visits family at all gets
`VISIT_TRACKING_LANE_NOT_IMPLEMENTED` (see [What a compiler may not support](#what-a-compiler-may-not-support)).
Two pieces of the pattern are not generated by any compiler yet: automatic user-deletion cleanup and
`eventStream` ingestion.

---

## What a visit is, and is not

- **It is an engagement signal for analytics and recommendations.** The history row is raw material:
  who, what, when, which API, which signal, under what analytic context.
- **It is not `setAsRead`.** The retired `GetOptions.setAsRead` / `ListOptions.setAsRead` wrote a flag
  on the row with no declared transaction, ordering, failure or idempotency semantics, and no
  compiler ever emitted it. This pattern's own read-state projection (`actorState`,
  `ownerReadMapping`) declares all four.
- **It is never an authorization input.** No visit-derived value - the quiet counter column, the
  `sys_<Obj>Visit` history - may decide access. The validator (`VISIT_SIGNAL_ON_AUTHZ_SURFACE`,
  an error) scans the service's authorization surfaces for either name: every api's
  `authOptions` (including `permissionCheck`), its `membershipCheckActions`,
  `permissionCheckActions` and `objectPermissionActions`, and every object's
  `membershipSettings`. A visit is counted on a client-claimed visible time; a value that
  forgeable can never decide access.
- **It is never a billing meter.** Client-claimed visibility makes a visit count unfit for
  pay-per-view.
- **It is personal data.** See [Privacy and retention](#privacy-and-retention).

## Turning it on

Two blocks, at two levels - the same split used for object content
moderation (object-level capability) and saved filters (api-level trigger):

```
DataObject.objectSettings.visitTracking     - WHERE visits of this object go (storage)
BusinessApi.basics.apiOptions.visitSettings - WHICH call is a visit, and how (trigger)
```

An api with an enabled `visitSettings` whose object has no enabled `visitTracking` is a design-time
**error** (`VISIT_TRACKING_NOT_DECLARED`) - never an implicit enable. The storage decision (history,
retention, personal data) is made once per object, deliberately.

### `objectSettings.visitTracking` - object level

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `enabled` | Boolean | `false` | Turns tracking on. `false` leaves the block fully inert: no table, no column, no injected api. |
| `history` | Boolean | `true` | Keep the raw event log `sys_<Obj>Visit`. |
| `historyRetentionDays` | Integer? | `null` (keep forever) | Removes history older than the window in batches (500 rows per object every 30 seconds). Preserves state and counters. A compiler that has not ported retention warns. |
| `actorState` | Boolean | `false` | Maintain one read-state row per actor and object and a caller-scoped read-state API. |
| `counterProperty` | PropRefer? | `null` (no counter) | A host column incremented once per **counted** visit. Injected as a compiler-managed Integer column when the named property is not declared. |
| `uniqueCounterProperty` | PropRefer? | `null` | Incremented on the first counted visit per distinct actor and object, across signals; requires `actorState: true`. Quiet Integer column, injected when not declared. |
| `ownerReadMapping` | `[DataMapItem]`? | `null` | Quiet field mappings for an owner-field object, applied only when actor and owner match. Values are MScript over `{ now, signal }`. |
| `anonymousVisits` | Boolean | `true` | Record visits that carry only an anonymous session key; `false` drops them (no history row, no count). |
| `publishVisitEvent` | Boolean | `false` | Publish `<obj>.visited` after each recorded visit, outside the response path. |
| `elasticLog` | String? | `null` | Append every recorded visit to this declared ElasticLog through its existing writer. |
| `eventStream` | String? | `null` | Append every visit to a declared EventStream too. Not generated yet: pending the server-side ingest integration. |

A declared value of a field the compiler does not generate is accepted by the schema but reported as
`VISIT_TRACKING_NOT_YET_EMITTED` (warning) - a knob never silently does nothing.

### `apiOptions.visitSettings` - api level

| Field | Type | Default | Meaning |
| --- | --- | --- | --- |
| `enabled` | Boolean | `false` | Makes this api a visit source. Requires the object's `visitTracking.enabled`. |
| `signal` | `access` \| `view` \| `read` \| `seen` | `access` | See [signals](#signals-are-distinct-never-merged). `seen` records list-page impressions. |
| `confirmation` | `none` \| `frontend` | `none` | `none` counts the visit when the response is sent. `frontend` mints `_visit` and counts only once the frontend confirms. |
| `minVisibleSeconds` | Integer? | `null` | Frontend confirmation: required visible dwell time. One of this or `minScrollPercent` is required when `confirmation: frontend`. |
| `minScrollPercent` | Integer? | `null` | Frontend confirmation: optional scroll-depth criterion (0-100), a client claim, never part of the guard. |
| `confirmTtlSeconds` | Integer | `1800` | How long a pending visit stays confirmable. |
| `countPolicy` | `everyVisit` \| `oncePerSession` \| `oncePerActor` \| `oncePerActorPerWindow` | `everyVisit` | See [count policies](#count-policies). |
| `countWindowSeconds` | Integer? | `null` | Required by `oncePerActorPerWindow`; ignored otherwise. |
| `excludeRoles` | `[String]`? | `null` | Roles whose calls never record (admin / editor traffic is not consumption). |
| `controllers` | `[String]` | `["rest"]` | Which transports record. MCP, gRPC, Kafka, cron and internal calls do not unless listed. |
| `targetIdFrom` | MScript? | `null` | The id of the visited object. Required for an `access` / `view` / `read` signal on an api whose crudType is not `get`; on a `get` with `confirmation: none` it replaces the id of the resolved row; ignored on a frontend-confirmed `get` (see below). |
| `context` | `[VisitContextField]`? | `null` | `{ name, from }` analytic dimensions frozen on the row at visit time. |

`visitSettings` lives on `apiOptions` (not `GetOptions` - the retired key is not revived) because it
applies to a `get`, a `list` (`seen`), and any other crudType with `targetIdFrom`.

#### Which crudType a signal needs

- `access`, `view`, `read` record a visit of **one** object: a `get` api, or an api of any other
  crudType that supplies `targetIdFrom` (the MScript naming the visited id - there is no single
  resolved row for the api to take it from otherwise). Violating this is
  `VISIT_SIGNAL_CRUD_MISMATCH`.
- `seen` records **every row of a returned list page** (an impression) and needs crudType `list`.
- `confirmation: frontend` additionally requires crudType `get` (`VISIT_CONFIRMATION_REQUIRES_GET`):
  the confirm route hangs off the visit api's own route and must resolve the same row. On such a
  frontend-confirmed `get`, `targetIdFrom` is ignored (`VISIT_TARGET_ID_IGNORED` warning) - the
  visited id is the row the get and its confirm route address. On a `get` with `confirmation:
  none`, a declared `targetIdFrom` is evaluated and **replaces** the resolved row's id.
- Whatever the crudType, the visit is recorded into the history of the api's **own** object
  (`dataObjectName`), and that object must declare `visitTracking`. `targetIdFrom` names an id of
  that object; it cannot redirect the visit to another object.

### Example: a plain, unconfirmed `access` visit

A product detail page. `viewCount` is declared, so no column is injected; every successful call
counts, no history policy scoping.

```json
{
  "serviceSettings": { "serviceBasics": { "name": "catalog" } },
  "dataObjects": [
    {
      "objectSettings": {
        "basicSettings": { "name": "product" },
        "visitTracking": {
          "enabled": true,
          "history": true,
          "counterProperty": "viewCount",
          "anonymousVisits": true
        }
      },
      "properties": [
        { "basicSettings": { "name": "title", "type": "String" } },
        { "basicSettings": { "name": "viewCount", "type": "Integer" } }
      ]
    }
  ],
  "businessLogic": [
    {
      "basics": {
        "apiOptions": {
          "name": "getProduct",
          "crudType": "get",
          "dataObjectName": "product",
          "visitSettings": { "enabled": true, "signal": "access" }
        }
      }
    }
  ]
}
```

Validates clean (no `VISIT_*` errors or warnings).

### Example: a frontend-confirmed `read`, once per session

An article page: the visit only counts once the reader has actually scrolled through it, and a
re-read in the same browser session does not count twice.

```json
{
  "basics": {
    "apiOptions": {
      "name": "getArticle",
      "crudType": "get",
      "dataObjectName": "article",
      "visitSettings": {
        "enabled": true,
        "signal": "read",
        "confirmation": "frontend",
        "minVisibleSeconds": 20,
        "minScrollPercent": 70,
        "confirmTtlSeconds": 1800,
        "countPolicy": "oncePerSession"
      }
    }
  }
}
```

Validates clean.

### Example: `targetIdFrom` on a non-`get` api

A "contact seller" api is an `update` of the `listing` (it bumps an author-owned inquiry counter);
every call is also an `access` of that listing. An `update` has no single resolved row for the
visit to take its id from, so `targetIdFrom` names it - here the route's `:listingId` parameter:

```json
{
  "basics": {
    "apiOptions": {
      "name": "contactSeller",
      "crudType": "update",
      "dataObjectName": "listing",
      "visitSettings": {
        "enabled": true,
        "signal": "access",
        "targetIdFrom": { "js": "this.listingId" }
      }
    }
  }
}
```

Validates clean, with `listing` declaring `visitTracking.enabled`. The visit lands in
`sys_listingVisit` because `listing` is the api's own object; an api of another object (an
`interest` create, say) would record into **that** object's history, so model it on the visited
object or record the visit from the visited object's own `get`.

### Example: `oncePerActorPerWindow`

A "trending today" counter that only wants one countable visit per visitor per rolling day:

```json
{
  "basics": {
    "apiOptions": {
      "name": "getDeal",
      "crudType": "get",
      "dataObjectName": "deal",
      "visitSettings": {
        "enabled": true,
        "signal": "access",
        "countPolicy": "oncePerActorPerWindow",
        "countWindowSeconds": 86400
      }
    }
  }
}
```

Validates clean.

### Example: analytic context, excluded roles and an extra transport

A product page whose visits feed per-category and per-campaign analysis, where catalog staff
browsing the shop are not consumption, and where an MCP agent reading a product on a user's behalf
should count as well:

```json
{
  "basics": {
    "apiOptions": {
      "name": "getProduct",
      "crudType": "get",
      "dataObjectName": "product",
      "visitSettings": {
        "enabled": true,
        "signal": "access",
        "countPolicy": "oncePerActor",
        "excludeRoles": ["admin", "catalogEditor"],
        "controllers": ["rest", "mcp"],
        "context": [
          { "name": "category", "from": { "js": "this.product.categoryId" } },
          { "name": "campaign", "from": { "js": "this.request.query.utm_campaign" } }
        ]
      }
    }
  }
}
```

Validates clean. Each `context` MScript ([overview](../mscript/overview.md)) runs at visit time and its value is frozen into the row's
`context` JSON: a string is cut at 512 characters, a dimension whose MScript throws is stored as
`null` and one that cannot be serialized is dropped (neither fails the visit), and a context over
4 KB in total is not stored at all. A caller holding
any `excludeRoles` role (matched case-insensitively, any of a multi-role session) records nothing.

## Signals are distinct, never merged

| Signal | Produced by | Meaning | Strength |
| --- | --- | --- | --- |
| `access` | `get` success, `confirmation: none` | Served to this actor. | Weak - includes prefetch, refresh, crawlers. |
| `view` | `get` + frontend confirmation | On screen long enough. | Medium. |
| `read` | `get` + frontend confirmation (pair it with a completion criterion such as `minScrollPercent`) | Consumed. | Strong. |
| `seen` | `list` success | The row was in a returned page. | Impression only - never an interest signal. |

An `access` is not a `view`; a `seen` row is not a click. Every consumer (a recommendation source, a
counter) names the signal it reads, so a list built on `read` never silently includes mere
`access`es. Declaring `view` or `read` without a frontend confirmation records every serve under that
stronger name - the validator warns (`VISIT_SIGNAL_WITHOUT_CONFIRMATION`); use `access`, or add
`confirmation: frontend`.

## The history table

With `visitTracking.history: true` (the default), every tracked object gets `sys_<Obj>Visit`: a
lazily created analytics **fact table** - no CRUD surface, no db events, no Elasticsearch
projection. It is the source of truth; the quiet counter (below) can always be rebuilt from it.

| Column | Meaning |
| --- | --- |
| `id` (= `visitId`), primary key | Minted per visit (a random UUID). |
| `objectId` | The visited row's id. |
| `tenantId` | Stamped from the session, never from the client. |
| `actorKey`, `userId?`, `sessionId?` | See [the actor rule](#count-policies). |
| `signal`, `status` | `status` is `counted` \| `pending` \| `confirmed` \| `expired` (`expired` is written lazily - see [the confirmation flow](#the-frontend-confirmation-flow-end-to-end)). |
| `apiName`, `controller` | Which declared api produced the row. |
| `listRequestId?`, `position?` | `seen` rows: the list response id and the row's zero-based rank within the returned page. |
| `attribution?` | The `?rec=<listRequestId>` query value the visit call arrived with. Recommendation impressions carry that id in their `listRequestId` column; click-through reporting over both inputs belongs to the recommendation engine. |
| `reportedVisibleSeconds?`, `reportedScrollPercent?` | Client claims on confirm - kept for analysis, never trusted for counting. |
| `context` (JSON) | The declared `context` fields, frozen at visit time. |
| `countApplied` | Whether this row reserved a count under the api's `countPolicy`; with a Redis-backed counter, delivery reaches the host counter on a later flush. |
| `createdAt`, `confirmedAt?` | Server clock. |

On a relational database the table has a UUID id, a JSON context, timestamp columns, and two indexes
on `(objectId, createdAt)` and `(objectId, actorKey, signal)`. On MongoDB it is one collection of the
same name, `_id` = the `visitId`, the same field names as document properties, with indexes on
`{ objectId: 1, createdAt: 1 }` and `{ objectId: 1, actorKey: 1, signal: 1 }`. The insert is
idempotent on `visitId` on every database.

### The counter column is quiet

`visitTracking.counterProperty` names a host Integer column (injected, read-only, default `0`, when
not already declared) incremented by `COALESCE(col, 0) + delta` directly on the model, where delta
is one direct visit or a coalesced batch total, bypassing hooks and the `updatedAt` column. It therefore **emits no
`<svc>-dbevent-<obj>-updated`, triggers no Elasticsearch re-projection and invalidates no entity
cache** - a hot product page recording a visit on every request would otherwise be exactly the write
amplification the pattern exists to avoid. The injected column is also `indexedInElastic: false`: a
projected copy of a value nothing re-projects would only ever be stale.

With a Redis-backed counter, counted visits accumulate per object and a 30-second job applies one
quiet update per object per tick. Counts are eventually consistent within the flush interval during
normal operation; failures and backlogs can extend the delay. Without Redis, the quiet increment
applies directly after the response. A list, search result or cached copy may show an older counter
than a fresh `get`. Never write it from an authored action or use it as a gate.

Delivery of a counted visit to the counter is recoverable: a durable queue is the claim authority
(Redis accumulation is only a scheduling hint), a retry after a failed write reuses the same
sequence, and a delivered delta is never applied twice. Each tick handles a bounded number of objects
and queued visits per object; backlogs continue on later ticks. Applied queue rows remain as replay
receipts independently of raw-history retention. The once-per count-policy decision across different
visit ids on MongoDB remains best effort (see [count policies](#count-policies)), and the
actor-state and distinct-counter projection updates remain separate operations. For how the generated
service delivers counters, see [the compiler specification](../../compiler/index.md).

## Actor read state and distinct actors

With `actorState: true`, the generated service maintains `sys_<Obj>VisitState` with `actorKey`, `objectId`,
`tenantId`, `firstSeenAt`, `lastSeenAt`, `firstReadAt`, `lastReadAt` and `visitCount`.
A unique `(actorKey, objectId)` index keeps one row per pair; state changes only for counted
signals. The first counted visit of a pair also increments `uniqueCounterProperty`, when declared,
so a later visit from the same actor under another signal does not increment the distinct count.
The state uses the same lazy database initialization as history; it exposes no general write API.
`firstSeenAt` and `lastSeenAt` cover all counted signals; `firstReadAt` and `lastReadAt` change
only for a counted `read` signal. On MongoDB the state upsert and quiet counter writes are separate
operations: delivery of the total visit counter is recoverable, but the distinct-counter and
actor-state projection updates remain best effort.

For a tracked `product` object, the injected `listMyProductVisitStates` business API is
`GET /products/visits/my-read-state` (also under `/v1`). It accepts the standard list `page` and
`pageSize` parameters (defaults 1 and 20; maximum pageSize 200) and answers the usual list envelope:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "data": [{ "actorKey": "user-id", "objectId": "product-id", "tenantId": "tenant-id", "firstSeenAt": "2026-11-08T12:00:00.000Z", "lastSeenAt": "2026-11-08T12:00:00.000Z", "firstReadAt": null, "lastReadAt": null, "visitCount": 1 }], "paging": { "page": 1, "pageSize": 20, "totalCount": 1, "totalPages": 1 } }
```

The API returns only the caller's rows in the current tenant. It derives the actor from the session
user id, or the persisted anonymous `X-Session-Id` under the same guest-cart rule as recording.
The request cannot choose another actor or tenant. State updates happen after the visit response;
an immediate read can still show the previous state. Anonymous state is not merged into a user's
state after login.

`ownerReadMapping` is the single-recipient case: the object must declare a property with
`sessionSettings.isOwnerField: true`, otherwise validation reports `VISIT_OWNER_MAPPING_WITHOUT_OWNER`.
The generated service applies the mappings only when the counted visitor's actor key equals the row's owner.
Each mapping is a [`DataMapItem`](../../spec/DataMapItem.md) such as `{ "name": "isRead", "value": { "js": "true" } }` or
`{ "name": "readAt", "value": { "js": "this.now" } }`; values read `{ now, signal }` through
`this.now` and `this.signal`.
It writes these fields quietly in the same post-response step as the
counters, without ordinary update events, projection work or cache invalidation.
Targets must be declared ordinary properties; missing fields, owner fields and compiler-managed columns
report `VISIT_OWNER_MAPPING_INVALID_PROPERTY`.

## Seen list pages

On a `list` API, declare `visitSettings: { "enabled": true, "signal": "seen" }`. A successful page
records every returned object in **one batched history insert**, with a zero-based `position`
within the page and one shared `listRequestId`. The list response carries:

```json
{ "_visit": { "listRequestId": "page-request-id" } }
```

The normal list payload is preserved. Keep the request id when linking a later visit with
`?rec=<listRequestId>`; the visit history already stores that attribution. A `seen` impression
does not mean the user clicked, viewed or read the item, and is never an interest signal.
There is no frontend confirmation for a seen page.

When a response mapping replaces whole rows with new objects, retain each object's `id` so
the impression can be associated with its source object. Removing response fields from existing
rows, filtering them or reordering them preserves their visit identity.

## Count policies

Judged per **(objectId, signal)** - an `access` and a `view` of the same object are never merged -
across every api that feeds the object (a web and a mobile detail api are one product page):

| Policy | Counts |
| --- | --- |
| `everyVisit` (default) | Every recorded visit. |
| `oncePerSession` | One counted visit per session id (falls back to the actor key when there is no session id - an authenticated caller with no session). |
| `oncePerActor` | One counted visit per actor (user id, or anonymous session key), ever. |
| `oncePerActorPerWindow` | One counted visit per actor per `countWindowSeconds`. |

Every visit is still kept in the history regardless of policy; only `countApplied` (and the counter)
is affected.

**The actor and the guest-cart rule.** `actorKey` is the user id when logged in; otherwise the
anonymous session key, read exactly like the shopping cart's guest-cart rule:
`session.sessionId ?? session.id ?? req.headers['x-session-id']`. A frontend without a logged-in user
must mint a random id once (`crypto.randomUUID()`), persist it, and send it as `X-Session-Id` on both
the visit api call and its confirm - the confirm is only accepted from the actor the visit was
minted for. A caller with neither a user nor `X-Session-Id` records nothing: there is no generic
anonymous-visitor id to fall back to.

**Sessions.** `oncePerSession` keys on the session id when the caller has one; it is not the same
thing as `oncePerActor` for a logged-in user who has several concurrent sessions (e.g. two tabs,
two devices) - each session counts once. Anonymous rows are **not** re-keyed when the visitor later
logs in (an explicit non-goal; stitching is a privacy-reviewed later step).

**On a relational service** the judgement, the `countApplied` flip and the counter increment run in
ONE transaction, with the host row locked for the transaction (`SELECT ... FOR UPDATE`) - two
concurrent first visits of one actor cannot both find "not counted yet".

**On MongoDB, a once-per policy is best effort** (maintainer ruling). There is no
transaction: the "is there already a counted row in this scope" read and the `countApplied` write are
two separate operations, so two concurrent first visits of one actor (or session) may both find "not
counted yet" and both count. The confirm claim itself stays exactly-once (one atomic `updateOne`) -
only the *count policy* judgement is affected, not double-recording or a double-confirm. An atomic
count-policy coordination across different visit ids remains a later step. The durable counter queue
recovers an already claimed total-counter delta. The `VisitSettings.countPolicy` field documentation
carries the best-effort note, and the frontend guidance for every tracked object whose visit apis
use a once-per policy repeats it.

## The frontend confirmation flow, end to end

With `confirmation: frontend` (a `get` api only), the visit becomes a two-step, exactly-once
protocol:

1. **The `get` succeeds.** Before the response is built, the service mints a `visitId`
   (a random UUID) and the response carries:

   ```json
   {
     "_type": "article",
     "id": "a1b2...",
     "_visit": {
       "visitId": "6f1c6e2a-...",
       "confirmPath": "/articles/a1b2.../visits/6f1c6e2a-.../confirm",
       "minVisibleSeconds": 20,
       "minScrollPercent": 70,
       "expiresAt": "2026-10-05T12:30:00.000Z"
     }
   }
   ```

   `_visit` is absent when the call was not a visit at all (an error answer, an idempotent replay, a
   miss, a transport not in `controllers`, an excluded role, no identifiable actor, an anonymous
   caller on an object with `anonymousVisits: false`) - the frontend then does nothing. Only the pending history row is written
   after the response leaves; the handle itself rides the response with no extra latency.

2. **The frontend measures VISIBLE time**, not wall-clock time: pause the clock while the tab is
   hidden (the Page Visibility API) and while the content element is off-screen
   (`IntersectionObserver`). When `minScrollPercent` is set, also track scroll depth through that
   element.

3. Once the visible time reaches `minVisibleSeconds` (and the scroll depth reaches
   `minScrollPercent`, when set) and before `expiresAt`, `POST` to `confirmPath` **once**:

   ```js
   async function confirmVisit(baseUrl, visit, claims, headers) {
     const res = await fetch(baseUrl + visit.confirmPath, {
       method: 'POST',
       headers: { 'Content-Type': 'application/json', ...headers }, // the session's auth, or X-Session-Id
       body: JSON.stringify(claims), // { visibleSeconds, scrollPercent }
     });
     return res.status === 200 ? res.json() : Promise.reject(res);
   }
   ```

4. **`200 OK`** answers the record's envelope plus the outcome:

   ```json
   { "_type": "article", "id": "a1b2...", "visit": { "visitId": "6f1c6e2a-...", "status": "confirmed", "alreadyConfirmed": false, "counted": true } }
   ```

   `alreadyConfirmed: true` answers a **retry** of a confirm that already went through (a network
   error, a remount, a double click): treat it as success - it is never counted twice.
   `counted: false` means the visit was confirmed but the count policy did not move the counter (a
   repeat visit under `oncePerActor`, for instance) - still not an error.

5. **Refused claims**, all `problem+json` with an `errorCode`:
   - **`404 VISIT_NOT_FOUND`** - no pending visit with this id for this caller on this record. This
     covers an unknown id, a malformed (non-UUID) id (checked and refused before any query runs, so
     it is a clean 404 rather than a database error), a foreign actor's visit, and an object
     mismatch. Drop it silently; never show it to the user.
   - **`409 VISIT_CONFIRM_TOO_EARLY`** - the server measured less elapsed time than
     `minVisibleSeconds` since the mint (clock drift, or a confirm fired early); the body carries
     `errors.retryAfterSeconds` - wait that long and `POST` again.
   - **`410 VISIT_EXPIRED`** - past `expiresAt` (the TTL, `confirmTtlSeconds`); drop it, never retry.

A pending row that is never confirmed is counted nowhere and stays in the history (still visible to
analysis as "visited but not confirmed"). There is no expiry sweep: the row keeps `status: pending`
until a confirm arrives after its TTL, which answers `410` and flips that row to `expired`. Analysis
should therefore treat a `pending` row older than `confirmTtlSeconds` as expired.

**Anonymous visitors on a frontend-confirmed api** need `X-Session-Id` on *both* the original call and
the confirm - the confirm route checks that the confirming actor is the one the visit was minted for.

**The confirm route is an injected api**, `confirm<Api>Visit` (for `getArticle`:
`confirmGetArticleVisit`), a `POST` on `<visit api route>/visits/:visitId/confirm` over the same
object. It inherits the visit api's gate - its `loginRequired` and `ownershipCheck` as authored, and
its `checkRoles` / `absoluteRoles` / `permissionCheck` never wider than the parent - so a caller who
could not read the row cannot confirm a visit of it. It is REST only (no MCP tool, no M2M) and raises
no api or db event. Its body takes the two optional claims `visibleSeconds` (capped at 86400) and
`scrollPercent` (capped at 100), both stored and never trusted.

---

## Failure behaviour

A visit record (the `counted`/`pending` insert and, when it applies, the count-policy judgement) runs
**after the response has already been sent** - never slowing a read down - and never throws into the
controller. On a failure, the visit is logged and handed to the **action outbox** under
action name `$visit`, keyed by the `visitId`, with the full `{ spec, row }` as its payload; the
outbox sweeper replays it later through the same insert path. The insert is idempotent on the
`visitId`, and the count-policy claim flips `countApplied` only once - a replay never
writes or counts a visit twice.

**Known limitation:** the action outbox supports PostgreSQL and MongoDB only; on a service backed by
another database (MySQL, for example) the outbox degrades (logs a warning, answers `false`) and a
failed visit record - like any other outbox obligation on that service - is dropped rather than
replayed. A visit record that succeeds on the first try is unaffected; this only matters for a write
that throws (a connection blip, a transient lock) on such a database.

## Optional downstream sinks

Set `publishVisitEvent: true` on `objectSettings.visitTracking` to publish every
recorded visit as `<obj>.visited` in the standard event envelope. The Kafka topic
follows the service event convention: `<serviceCodename>-dbevent-<obj>-visited`.
The envelope's `id` is the visit id; `actor` carries the stored user, anonymous
session and tenant identity. `data` contains the visit fields, `_type` and
`objectName`, with `createdAt` serialized as ISO text. `requestId` is null because
the stored visit does not carry request correlation.

Set `elasticLog: "visitLog"` to append the same visit document to the declared
`visitLog` ElasticLog using its existing writer. The log declaration supplies
its mapped fields and index alias; the visits layer does not create an ES client.
An undeclared log has no writer and is treated as unavailable.

Both sinks start after the history write commits and run after the response, so
they add no response latency. They receive pending frontend visits and repeated
visits even when `countPolicy` suppresses the counter. Confirmation does not append
a second event or log line: read the history row for its final confirmation state.
With `history: false`, the sinks run after the quiet counter/projection step.

A failed sink does not reverse a stored visit or stop its peer. Rejected calls and
`false` results defer only the failed sinks to the action outbox; replay does not
write history or increment counters again. Delivery is best effort and can repeat;
consumers deduplicate by visit id. Kafka replay preserves the original envelope.
The action-outbox availability and database limitations described above also
apply to these retries. History remains the source of truth.

`eventStream` is still pending. It requires a server-side ingest function
that supplies actor and tenant from the session; it is not generated yet.

Every check below runs only while the relevant block's `enabled` is `true`.

| Code | On | Meaning |
| --- | --- | --- |

### Validating the errors

Enabling `visitSettings` on an api of an object that never declared `visitTracking` is the most
common mistake:

```json
{
  "basics": {
    "apiOptions": {
      "name": "getReview",
      "crudType": "get",
      "dataObjectName": "review",
      "visitSettings": { "enabled": true, "signal": "access" }
    }
  }
}
```

Against an object `review` with no `visitTracking` block, this reports exactly one error,
`VISIT_TRACKING_NOT_DECLARED`, and the api records nothing until `review` declares
`visitTracking.enabled: true`.

## What a compiler may not support

The visits family is generated per target language, and a compiler may support only some languages
and only some of the pattern's parts (history and the confirm claim, read state, seen pages, counter
delivery and retention, events and ElasticLog). A service whose target language is not covered, and
that declares a tracked object, gets the design-time warning `VISIT_TRACKING_LANE_NOT_IMPLEMENTED`:
no history table and no visit hook; the counter column is still injected but stays at its default
`0`, and the injected confirm api is a plain `get` that confirms nothing. Individual declared fields a
compiler has not ported are reported with `VISIT_TRACKING_NOT_YET_EMITTED` /
`VISIT_SETTINGS_NOT_YET_EMITTED`. A compiler that supports the pattern must reproduce the behaviour this guide
documents (the gate, the actor rule, the history table, the quiet counter, the confirm claim, the
outbox replay). See [the compiler specification](../../compiler/index.md) for which languages and
parts a given compiler supports.

## Privacy and retention

**What is stored about the actor:** the user id when logged in (plus the session id when the session
has one), or the anonymous session key (`X-Session-Id`) otherwise; never more than that identifies
who visited. The two client-reported
claims (`reportedVisibleSeconds`, `reportedScrollPercent`) are stored for analysis, bounded, and never
trusted for anything else. `tenantId` is stamped from the server-side tenant and `actorKey` from the session (for an
anonymous caller, the `X-Session-Id` header); neither can be supplied by the request body, and a
visit row can never be written for another tenant.

**What is not stored:** no IP address, no user agent, no device fingerprint, no free-text. The
declared `context` dimensions are whatever MScripts the author wrote (e.g. `category`, `campaign`)
- no dimension is collected implicitly.

**Retention:** `historyRetentionDays: null` keeps raw history forever. A positive
window deletes history strictly older than the cutoff in batches of 500 per object on each
30-second tick. This includes anonymous history. Actor state and host counters are preserved.

**User deletion:** the bounded store cleanup removes authenticated history by `userId` and
actor state by `actorKey`; it never decrements host counters. Automatic integration with the
user-deletion event is still pending. Until it lands, services must run their own user-erasure
cleanup. Anonymous history is governed by retention. The current state schema does not
distinguish a user key from an identical anonymous session key; automatic state erasure needs
that distinction resolved along with the event integration.

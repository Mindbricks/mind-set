# Bucket providers: behaviour rules

This page states the provider behaviour that every conforming compiler must honour for the
bucket (object storage) family: what a blueprint can rely on when a `RemoteBucket` binds a
bucket provider, how presigned URLs, CORS, cache headers, encryption and bucket names behave per
brand, and how provider failures surface. The configuration keys of every brand are in the
generated catalogue, [bucketProvider](../../spec/providers/bucketProvider.md); this page does not
repeat them.

## Family rules

### Declaration and selection

- A bucket provider is a named entry of `projectSettings.bucketProvidersSettings.bucketProviders[]`
  with a `name` (`codeName`, unique in the list), a `provider` brand (`s3`, `r2`, `s3Compatible`,
  `gcs`, `azure`; default `s3`) and a flat `configuration` object (not the `[{ name, value }]` list
  of the other families). Only the fields relevant to the brand are read; the others are ignored.
  Several entries may share a brand.
- There is no bucket service. Upload, signed-URL and delete routes are compiled into the service
  that owns the bucket, and the provider entry is the credentials catalogue those routes use.
- A `RemoteBucket` names its provider in `bucketStorage.providerName`; there is no default
  bucket provider. A missing `providerName` is the error `REMOTE_BUCKET_PROVIDER_MISSING`; a name
  that resolves to no entry is the warning `REMOTE_BUCKET_PROVIDER_NOT_FOUND`.
- When `bucketStorage.remoteBucketName` is omitted (or `null`) the provider's `defaultBucketName`
  applies. A bucket whose effective name is empty is the error `REMOTE_BUCKET_NAME_EMPTY`.
- The physical bucket (container) must already exist. A compiler never creates it.
- Bucket configuration values are taken literally: they are not `$ENV:`-dereferenced. Secret
  fields are left blank in the blueprint and supplied by the deployment.
- Missing credentials never block a build. A generated service answers
  `GET /v1/buckets/mock-status` to report its bucket providers' fallback state; where a provider's
  credentials are missing the service falls back to the native store (see the GCS rules below).
- Self-hosted storage that the hosting platform manages needs no provider entry: declare a
  [native bucket](../composition/native-buckets.md). The `s3Compatible` brand is only for storage
  operated outside the platform.

```json
{
  "bucketProvidersSettings": {
    "bucketProviders": [
      {
        "name": "mainStorage", "provider": "s3",
        "configuration": { "region": "us-east-1", "defaultBucketName": "myco-uploads", "accessKeyId": "", "secretAccessKey": "" }
      },
      {
        "name": "videoArchive", "provider": "r2",
        "configuration": { "region": "auto", "endpoint": "https://abc123.r2.cloudflarestorage.com", "defaultBucketName": "myco-videos", "accessKeyId": "", "secretAccessKey": "" }
      }
    ]
  }
}
```

```json
{
  "name": "ticketAttachments",
  "bucketBasics": {
    "name": "ticketAttachments",
    "maxFileSizeMb": 25,
    "allowedMimeTypes": ["image/png", "image/jpeg", "application/pdf"],
    "virusScan": true,
    "virusScanMode": "block"
  },
  "bucketStorage": {
    "providerName": "mainStorage",
    "remoteBucketName": null,
    "keyPrefix": "tickets/",
    "presignTTLSeconds": 3600,
    "serverSideEncryption": true
  }
}
```

### Routes and operations

For each bucket the owning service serves:

- `POST /bucket/<bucketName>/upload-url`: a presigned PUT URL, valid for
  `bucketStorage.presignTTLSeconds`, returned as `{ uploadUrl, storageKey, expiresAt, headers }`.
  The client must send **every** entry of the returned `headers` map on the PUT, never a fixed
  list; the content type it sends must equal the one signed, or the provider rejects the
  signature.
- `POST /bucket/<bucketName>/upload`: a through-server upload. The bytes pass through the
  service, which is the path used when virus scanning or MIME sniffing is enabled.
- `GET /bucket/<bucketName>/download/:key`: a `302` to a presigned GET URL. The redirect itself is
  `no-store`.
- `DELETE /bucket/<bucketName>/object/:key`: delete.

Storage keys are generated by the server. When a multipart upload's file part has no nonblank
original filename, its `fileKey` is used as a filename hint for content classification and
extension selection; `originalName` still describes the file part. Multipart (multi-GB) uploads to
the provider are not offered by any brand.

### Cache-Control

Every stored object carries a `Cache-Control`: the bucket's `bucketStorage.objectCacheControl`
when it declares one, `public, max-age=31536000, immutable` otherwise (a missing or blank value is
the default). The stored metadata and any signed download override resolve the same value, so they
never disagree. Image variants and the provider fallback keep the bucket policy. Whether a value set
later re-labels objects written earlier depends on the brand (S3 and Azure: yes, through a signed
response override; GCS: no).

### Bucket names

Names are shape-checked per brand, on `configuration.defaultBucketName` and on a RemoteBucket's
`remoteBucketName` (judged by the brand of the provider it binds). A name the brand can never
accept is the error `BUCKET_NAME_INVALID` (details `brand`, `value`, `rule`); for `s3Compatible`
it is a warning, because self-managed stores' rules vary. The exact placeholder `REPLACE_ME` is
the warning `BUCKET_NAME_PLACEHOLDER` instead. The per-brand rules are under each brand below.

### Failures

- A provider answer that the configured bucket does not exist (S3 `NoSuchBucket`, GCS 404 on the
  bucket, Azure `ContainerNotFound`) is a `503` `application/problem+json` with
  `errorCode: "BUCKET_NOT_FOUND"` and `provider` / `bucket` members naming the provider and the
  configured bucket; never the generic `500 INTERNAL_ERROR`.
- A transient provider failure (S3 `InternalError`, `ServiceUnavailable`, `SlowDown`, a provider
  HTTP 5xx) is a `503` `application/problem+json` with `errorCode: "BUCKET_PROVIDER_UNAVAILABLE"`
  and `retryable: true`, its detail naming the provider (or the native store).
- No answer carries raw driver text or a credential. A provider adds no retries of its own.

### Served content type

A DbBucket proxy validates the stored content type before serving it: after trimming it must be a
printable ASCII media type with valid parameters, at most 255 characters; any other value is served
as `application/octet-stream`. The attachment disposition, `nosniff` and the active-content
sandbox headers still apply.

## Amazon S3 (`s3`)

The reference brand; `r2` and `s3Compatible` follow its behaviour through a custom `endpoint`.

- `region`, `accessKeyId` and `secretAccessKey` are required (the secrets may be blank in the
  blueprint). `endpoint` is optional (for example a private VPC endpoint,
  `https://bucket.vpce-...`); `forcePathStyle` is normally `false` (virtual-host addressing).
- **Presigned PUT** signs the content type, plus the server-side encryption header when enabled.
- **Presigned GET** signs a `ResponseCacheControl` override with the bucket's Cache-Control, so an
  object stored without one is still served with it, and a per-bucket value re-labels objects
  written before it was set (the override wins over the stored property).
- **Server-side encryption**: `bucketStorage.serverSideEncryption: true` adds
  `ServerSideEncryption: 'AES256'` to the PUT and the matching header to the presigned URL. It
  defaults to `false`; only the literal `true` emits it, so a store without an SSE-S3 key is never
  handed one.
- The service never lists objects. It needs object put, get and delete, plus read and write of the
  bucket's CORS for the merge below.
- Limits: 5 TB per object, 5 GB per single PUT; the provider's standard rate limits (3500 PUT/s and
  5500 GET/s per prefix).
- Bucket names: 3-63 characters; lowercase letters, digits, dots and hyphens; begin and end with a
  letter or digit; no `..`; not shaped like an IP address; no `xn--`, `sthree-` or
  `amzn-s3-demo-` prefix; no `-s3alias`, `--ol-s3`, `.mrap`, `--x-s3` or `--table-s3` suffix.

**CORS merge.** A browser reading a presigned GET URL, or PUTting a presigned upload URL with its
`headers` map (a preflighted request), needs a bucket CORS rule for that method. Before the first
upload or download presign per (client, bucket) per process, the service:

1. reads the bucket's CORS. No configuration counts as no rules; **any other read error writes
   nothing** and logs one warning, so a configuration the service cannot read is never
   overwritten;
2. looks for `GET`, `HEAD` and `PUT` in the existing rules; a method any rule already names, for
   any origins, is left alone (the origin list is never widened);
3. when a method is named by no rule, writes the existing rules back unchanged **plus one rule**
   with a fixed, compiler-chosen ID, allowing only the missing methods from `*`, with
   `AllowedHeaders: *` and the `ETag`, `Content-Length`, `Content-Type`, `Last-Modified`,
   `Accept-Ranges` and `Content-Range` response headers exposed. When nothing is missing it writes
   nothing, so a restart finds the merged rule and writes nothing.

Both presigns wait for this check before returning the URL; a read or write failure warns once per
(client, bucket) and the URL is still returned. CORS management uses the service's internal
endpoint, signing uses the configured public base. `*` is the origin only because the language has
no origin setting: the signature grants access, not CORS. To restrict origins, author your own
`GET` / `HEAD` / `PUT` rules; the service then adds nothing for those methods. Without the CORS
permissions presigned URLs still work for non-browser callers. An earlier behaviour replaced the
whole configuration with one `GET, HEAD` rule on every start; a bucket that carries that rule gets
only a `PUT` rule merged next to it.

## Cloudflare R2 (`r2`)

- Same operations as S3; the `endpoint` override is the only runtime difference.
- `endpoint` is required: `https://<accountId>.r2.cloudflarestorage.com`. `region` is `auto` (a
  formality; R2 is single-region per bucket). `forcePathStyle` is usually `false`.
- CORS: R2 honours the CORS read and write calls, so the S3 merge applies unchanged; the token
  needs permission to read and write the bucket's CORS, and a refused read writes nothing.
- Public buckets are served from a separate public domain or a custom domain, which the service
  does not configure; private reads use presigned URLs, which always use the R2 endpoint, whatever
  public domain is attached.
- Limits: 4.95 TB per object, 5 GB per single PUT; about 300 operations per second per bucket,
  so sustained heavy writes need keys spread across prefixes.
- Bucket names: 3-63 characters; lowercase letters, digits and hyphens; begin and end with a
  letter or digit.

## S3-compatible store (`s3Compatible`)

- Any external store that speaks the S3 API (a self-managed cluster or appliance). Same operations
  as S3; the presign sequence works against any SigV4 store.
- `endpoint` is required (`http://<host>:<port>` or `https://...`). `forcePathStyle` should be
  `true` and is compiled as `true` by default for this brand: most self-managed stores do not
  support virtual-host addressing. `region` is still demanded by the signer; `us-east-1` is
  conventional unless the store enforces another. Validation requires `endpoint` and
  `forcePathStyle: true`.
- URL shape is path style: `http://<endpoint>/<bucketName>/<key>`, and the presign output matches.
- CORS: the S3 merge applies; a store that lacks CORS support (or refuses the read) gets nothing
  written, one warning, and browser uploads and downloads then need a manual CORS configuration.
- Keep `serverSideEncryption: false` (the default) unless the store has SSE-S3 configured: a store
  without it answers `500 InternalError` to a PUT carrying `x-amz-server-side-encryption: AES256`.
- Presigned URLs over plain HTTP expose the signature to network observers; use TLS outside a
  private network.
- Bucket names follow the S3 rules, but a violation is a warning here.

## Google Cloud Storage (`gcs`)

- `projectId`, `clientEmail` and `privateKey` are all required. There is deliberately no fallback
  to ambient credentials: V4 signed URLs need a private key, so an ambient-credential walk could
  only fail later. A provider missing one of the three raises `RemoteBucketCredentialsMissingError`
  by name (the service has already fallen back to the native store before that point).
- `privateKey` is the PEM block; literal `\n` sequences are normalised to newlines.
- `apiEndpoint` optionally overrides the API endpoint (for example an emulator). It must be an
  absolute HTTP(S) URL with a host and optional port; a path, query string or credentials in the
  URL are refused. An HTTP endpoint skips the provider's authentication (no token exchange); an
  HTTPS custom endpoint keeps service-account authentication. Signed URLs are still signed locally,
  so even an emulator needs a valid PEM key.
- **Presigned PUT** (V4, `write`) binds only the content type into the signature. `Cache-Control`
  is returned in the `headers` map but not signed: the provider stores an unsigned-but-sent
  `Cache-Control`, and omitting it costs the object its cache header and nothing else.
- **Presigned GET** (V4, `read`) has **no** cache-control response override: the provider honours
  only `response-content-type` and `response-content-disposition`. An object stored without
  Cache-Control metadata is served with the bucket default and cannot be re-labelled at read
  time, so a per-bucket `objectCacheControl` applies only to objects written after it is set.
- The through-server upload stores the object non-resumably with the bucket's Cache-Control.
- Signed URLs use the `storage.googleapis.com/<bucket>/<object>` shape; custom domains do not
  apply to them.
- **CORS merge.** On the first download presign per (client, bucket) the service reads the
  bucket's `cors` list; a read failure writes nothing and logs one warning. `GET`, `HEAD` and `PUT`
  that no existing entry names are added as one extra entry `origin: ["*"]`, `maxAgeSeconds: 3600`,
  `responseHeader` listing `Content-Type` and `Cache-Control` plus the exposed response headers;
  every existing entry is written back unchanged. A method already named by an entry is left
  alone; nothing missing writes nothing. A write failure (typically a missing bucket-update
  permission) is logged once and tolerated.
- `serverSideEncryption` is accepted and has no effect: the provider encrypts at rest by default,
  and customer-managed keys are bucket configuration outside the language. Resumable uploads and
  HMAC-key authentication are not offered.
- Bucket names: lowercase letters, digits, `-`, `_` and `.`; begin and end with a letter or digit;
  3-63 characters (up to 222 with dots, each dot-separated part at most 63); not IP-shaped; do not
  begin with `goog` or contain `google`.

## Azure Blob Storage (`azure`)

- `defaultBucketName` and `remoteBucketName` name a **container**, not a storage account. One
  storage account per provider entry; several containers map to several `RemoteBucket`s.
  Containers are flat: `/` in a key is only a visual hierarchy.
- Exactly one authentication mode must be configured; zero is `AZURE_AUTH_MODE_REQUIRED`, more
  than one `AZURE_AUTH_MODE_AMBIGUOUS`, and a half pair `AZURE_ACCOUNT_KEY_PAIR_INCOMPLETE`:

| Mode | Fields | Signing |
|---|---|---|
| Connection string | `connectionString` (secret) | `AccountName` and `AccountKey` are parsed from it for SAS signing; a string missing either is refused at the first call. |
| Managed identity | `useManagedIdentity: true`, `accountName` | No secret; the host supplies the identity. The service URL is `https://<accountName>.blob.core.windows.net`; SAS URLs are signed with a lazily fetched user-delegation key. |
| Shared key | `accountName`, `accountKey` (secret) | A shared-key credential built directly, no string parsing. |

- **Presigned PUT** is a SAS with write permission and the content type. It returns the headers the
  client must send: `Content-Type`, `x-ms-blob-type: BlockBlob` (without it the provider rejects
  the PUT with HTTP 400) and `x-ms-blob-cache-control` with the bucket's Cache-Control. A SAS
  signs no headers, so that header is the only way the blob gets its `Cache-Control`.
- **Presigned GET** is a SAS with read permission that signs the Cache-Control as the `rscc`
  response override, so blobs stored without one are served with it and a per-bucket value
  re-labels earlier blobs. SAS tokens set `startsOn` 5 minutes in the past to tolerate clock skew.
- The through-server upload stores the blob with its content type and the bucket's Cache-Control.
  Delete is idempotent (delete-if-exists). A metadata read of a missing blob answers
  `{ exists: false }`, not an error.
- Blob URLs are `https://<account>.blob.core.windows.net/<container>/<key>`; SAS URLs add the
  signature and expiry as a query string. SAS URLs work whatever the container's public-access
  level (`Off`, `Blob`, `Container`).
- **No CORS merge.** CORS is a storage-account setting, too broad to change per download, so the
  service leaves it to the operator.
- `serverSideEncryption` is accepted and has no effect: blobs are encrypted at rest by default,
  and customer-managed keys are storage-account level.
- Limits: 200 GB per block blob (5 TB with append or page blobs), 5 GB per single PUT; block-list
  uploads are not offered.
- Container names: 3-63 characters; lowercase letters, digits and hyphens; begin and end with a
  letter or digit; no `--` (`$root`, `$web` and `$logs` are accepted).

## Operations

Environment variables, console configuration, credential setup (account permissions, access keys,
service accounts, managed identities) and the go-live checklist are operations of a compiler and
are not part of the language. Read the documentation of your compiler for them.

For the Genesis compiler, these operations (environment variables, console configuration, credential setup, webhook registration and the go-live checklist) are in the `genesis-set` package, which installs next to mind-set.
